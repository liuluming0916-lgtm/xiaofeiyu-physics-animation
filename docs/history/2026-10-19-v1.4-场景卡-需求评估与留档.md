# v1.4 场景卡：需求评估与留档

> 记录时间：2026-10-19
> 状态：**只评估、只留档，不开工**。
> 版本安排（按你 2026-10-19 的新口径）：v1.2 = 示例题库；v1.3 跳过；v1.4 = 写卡工作台 + 场景卡。

---

## 0. 一句话结论

**场景卡 = 题型命中后，告诉 AI“这道题该用哪几张元件卡、按什么顺序、摆成什么关系”的装配说明。**

- 它**不教**单个元件怎么画（那是元件卡的事）；
- 它**不写**完整动画代码（那是模型的事）；
- 它管的是**元件之间的摆放、顺序、关系、边界**；
- 它按**题型**命中，不按单个元件命中；
- 它需要**社区**才能写完，因为“题型 × 变体”太多，核心团队写不完。

这是一个正确的、比“旧场景卡”更聪明的设计。但它是一个**第二层**，必须建立在“元件卡工作台”稳定之后；建议 v1.4 分两段做：先元件工作台，再场景卡。

---

## 1. 对齐：一张场景卡长什么样（传送带例子）

题目：水平传送带 + 物块，求共速时间、位移、相对位移、摩擦生热。

### 元件卡负责什么（已有）

- `wb_el_belt`：`Draw.belt([0, 0.2], [4, 0.2], { ticks: 16 });`
- `wb_el_block`：`Draw.box([state.x, 0.15], 0.4, 0.3);`
- `wb_el_ground`：`Draw.ground(-1.5, 2.5);`
- `wb_el_vector`：摩擦箭头怎么写、必须给 `mag`；
- `wb_el_measuring_tool`：相对位移标注怎么写。

### 场景卡负责什么（要新建）

```md
# 场景·传送带 + 物块（共速 / 相对位移 / 摩擦生热）

## 适用题型
题面出现“水平传送带 + 物块”，求共速时间、位移、相对位移、摩擦生热；
不适用于倾斜传送带、传送带上的多个物块。

## 需要哪些元件（按顺序）
1. ground（地面）
2. belt（传送带）
3. block（物块）
4. vector（只画摩擦力，滑动段）
5. measuring_tool（相对位移标注，滑动段）

## 摆放与关系
- 带面水平；左端留 0.15 m，右端 = u·duration + 0.7 m；
- 物块中心在带面上方 r + 半高；块宽 0.34 m；
- 地面在带面下方 r；
- 物块 x 与带面 beltX 用**同一个 t**；
- 相对位移 = beltX − x，不是 x 本身。

## 过程顺序
- 先画地面 → 带面 → 物块；
- 滑动段：摩擦箭头 + 相对位移标注；
- 共速后：摩擦箭头消失；相对位移冻结/隐藏。

## 最容易拼错
- 带长写成“看起来合适”，不是 u·duration；
- 物块中心算到带面里（穿模）；
- 共速后还画摩擦箭头；
- 把“物块位移”和“相对位移”画成同一个标注。

## 生成后自检
- [ ] 物块中心 = 带面 y + r + 半高；
- [ ] 相对位移 = beltX − x；
- [ ] 共速后 f = 0，摩擦箭头不再出现；
- [ ] 带长 = u·duration + 0.7 m。
```

**注意它没有写**：`Draw.belt` 的参数怎么给、`Draw.arrow` 的 `mag` 怎么算、8 槽位怎么排。
这些是元件卡/常驻范例的事。场景卡只回答“用哪些、摆哪、什么顺序、什么关系”。

## 2. 它和现有五种东西的区别

| 东西 | 管什么 | 按什么命中 | 有没有代码 |
|---|---|---|---|
| **元件卡**（30 张） | 一个对象怎么画 | 元件 id（`elements`） | 有 `drawFrame` 示例 |
| **场景卡**（本需求） | 多个对象怎么摆、什么顺序、什么关系 | **题型**（`concepts`/`tags`） | **不写画法代码**；只引用元件卡 |
| **旧“场景卡”**（Gemini 里那种） | 一张卡包一整道题的完整程序 | 题型 | 有完整程序 |
| **`wb_scene_stages`**（已有） | 通用的“多段过程怎么分阶段” | 常驻/通用 | 有阶段表示例 |
| **物理规范**（用户层可写） | 这道题必须守什么物理规律 | 考点 | 可能没有代码 |
| **常驻范例**（提示词里的） | 一份合格 8 槽位程序长什么样 | 每道题 | 有完整程序 |

> 关键区别：**场景卡不重复元件卡的 API，也不重复常驻范例的骨架。**
> 如果场景卡里出现 `Draw.xxx(...)`，它就开始“抢元件卡的活”，两张卡会互相打架。

## 3. 为什么它必须靠社区

- **组合爆炸**：30 个元件、几十个考点、每类题还有变体（水平/倾斜传送带、单/多物块、有无摩擦……）。核心团队写不完。
- **教学经验在老师手里**：“这题该怎么摆、先画谁、哪里最容易错”是一线老师的强项，不是代码能推出来的。
- **一张场景卡的好坏，要用真实题验证**：老师手里有题，社区才有“用例”。
- **但社区不是第一天就能跑**：需要仓库、投稿、审核、版本、撤销。先做本地工作台 + 导出/导入，再上仓库。

所以：

- **v1.4 先做本地工作台**：能写、能试画、能导出/导入场景包；
- **v1.5 再做仓库/社区**：让别的老师投稿、安装、更新；
- 但在 v1.4 设计数据格式时，就要按“将来要共享”来设计（id、版本、components、demo、license）。

## 4. 现有架构能不能直接支持？

### 4.1 现在的命中规则

`core/worldbook/engine.mjs` 的 `matchByConcepts()` 现在有两种命中：

- **解题侧**：`concepts ∩ 模型考点 ≠ ∅`，且（`tags ∩ 模型题型 ≠ ∅` 或 `tags` 为空）；
- **动画侧**：`elements ∩ 模型元件 ≠ ∅`，再用 `concepts` 收窄。

`elements` 的语义是“**有任意一个元件命中就算**”。
如果场景卡也把 `elements` 当命中条件，那么只要题里出现“物块”，所有场景卡都会命中——**不行**。

### 4.2 所以需要第三类命中

场景卡需要：

- `kind: 'scene'`（新字段）；
- `concepts` / `tags` 作为**题型命中**条件；
- `components`（新字段）作为**装配清单**，**不参与命中**；
- 命中后：注入场景卡，再注入它列出的元件卡（或降级为 API 摘要）；
- **最多一张场景卡**；多张命中时按“具体程度”选一张并告警。

### 4.3 需要动的地方

| 位置 | 改动 |
|---|---|
| `contracts/worldbook-entry.schema.json` | 新增 `kind` / `components`；`additionalProperties: false`，必须改契约并重新生成 |
| `core/worldbook/store.mjs` | `validateEntry` 校验 `kind`、`components`（官方 id、≥2、不重复） |
| `core/worldbook/engine.mjs` | 新增场景命中分支；最多一张；与元件卡的优先级/预算 |
| `core/prompts/templates.mjs` | `scene_code` 加一句显式优先级：关系以场景卡为准，调用形式以元件卡为准 |
| `core/worldbook/engine.mjs` 的预算 | 场景卡 + 元件卡 + 示例的总预算；场景卡不重复 API |
| 门禁 | 场景卡不得含 `Draw.`；最多一张；components 必须官方；demo 必须过 C1–C9 |

> 这是**契约级改动**，不是“加一张卡”那么简单。v1.4 要做，就要接受 schema 版本号变化和一轮迁移。

## 5. 数据模型建议（最小可用）

### 5.1 新增字段

```json
{
  "kind": "scene",
  "id": "scene.conveyor-block",
  "title": "场景·传送带 + 物块（共速 / 相对位移 / 摩擦生热）",
  "origin": "user",
  "category": "scene_modeling",
  "enabled": true,
  "constant": false,
  "recursive": false,
  "keys": ["传送带", "共速", "相对位移", "摩擦生热"],
  "secondary_keys": { "logic": "AND_ANY", "list": [] },
  "concepts": ["conveyor_belt"],
  "tags": [],
  "components": ["ground", "belt", "block", "vector", "measuring_tool"],
  "insertion_slot": ["scene_code"],
  "order": 500,
  "priority": "high",
  "content": "…（§1 那种装配说明）…",
  "code_examples": []
}
```

规则：

- `kind`：`element`（默认）/ `scene` / `rule`；
  - 30 张元件卡 = `element`；
  - 4 张教学/约定卡 = `rule`；
  - 场景卡 = `scene`。
- `components`：只对 `scene` 有效；必须是官方元件 id；至少 2 个；不重复；**不作为命中条件**。
- `code_examples`：场景卡**必须为空**。场景卡不教 API；要教 API 就写元件卡。
- `content`：禁止出现 `Draw.` / `Phys.` 调用（门禁可查）；只写题型、元件清单、摆放、顺序、关系、易错、自检。
- `insertion_slot`：只进 `scene_code`；场景卡不进解题槽。
- `category`：可以沿用 `scene_modeling`；真正区分靠 `kind`，不靠 category。

### 5.2 迁移

- 现有 34 张卡：30 张 `element`，4 张 `rule`；需要一次性补 `kind`；
- 旧用户卡没有 `kind`：默认 `element`（兼容）；
- 契约版本从 1 升到 2；导入旧包时自动补默认值；
- 世界书哈希会变，导出/溯源的 `worldbookHash` 会变；门禁基线要更新。

### 5.3 触发词与“题型”

场景卡的命中靠 `concepts` / `tags`。这里有两个选择：

- **A. 复用现有考点/题型词表**：`contracts/worldbook-concepts.json` 里已有 60 多个考点、若干题型标签；好处是不新增词表；坏处是有些“场景”比考点更细（比如“倾斜传送带”不是独立考点）。
- **B. 新增“题型/场景”词表**：更贴切，但要走“词表治理”（谁能加、怎么审核、和考点什么关系），成本更高。

**建议 v1.4 先用 A**：场景卡的 `concepts/tags` 复用现有词表；如果一个场景细到现有词表装不下，先用 `keys` 字面量兜底，等词表治理成熟再扩。这样不阻塞第一版。

## 6. 工作台：场景卡怎么写、怎么试画

### 6.1 编辑器

场景卡编辑器比元件卡多三块：

1. **题型**：选 `concepts` / `tags`（或填 `keys`）；
2. **元件清单**：从 30 个官方元件里多选，**可排序**（顺序就是“先画谁后画谁”）；
3. **装配说明**：摆放、关系、过程顺序、易错、自检。

可以先用“结构化表单 + 文本域”，不做拖拽画布。拖拽排布是 v1.5+ 的事。

### 6.2 校验

- `components` 必须是官方 id、≥2、不重复；
- `content` 不得含 `Draw.` / `Phys.`；
- 必须有“适用题型”“需要哪些元件”“摆放与关系”“生成后自检”；
- 至少一张“示例题面 + 示例程序”（见 §6.3）；
- 同一题型只允许一张场景卡（或告警）；
- 场景卡与元件卡不得重复同一关系的描述（overlap warn）。

### 6.3 试画：场景卡不能只靠文字预览

元件卡可以“抽一段 stateAt/drawFrame 试画”；场景卡不行——它本身没有画法代码。
所以场景卡的预览需要一个**示例程序**（完整 8 槽位，能过 C1–C9）。

三种做法：

| 做法 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| **A. 作者手写示例程序** | 质量可控 | 对老师太难；等于让老师写代码 | 不推荐作为唯一方式 |
| **B. 工作台调模型生成示例程序** | 老师只写“装配说明 + 一道样例题”，模型生成 demo；通过 C1–C9 才保存 | 要调模型、要花钱；可能多轮 | **推荐**，作为主要方式 |
| **C. 不试画，只显示元件缩略图** | 简单 | 无法证明场景卡“能落地”；老师没信心 | 不推荐 |

**B 的流程**：

1. 老师写场景卡 + 贴一道样例题；
2. 点“生成示例并试画”；
3. 工作台用“场景卡 + 元件卡 + 样例题”调一次 `scene_code`；
4. 过 C1–C9 → 画出动画；不过 → 显示错误，老师改场景卡或让模型修；
5. 老师满意 → 把这份 8 槽位程序存成 **demo 侧车**（`data/card-studio/scene-demos/<id>.json`），**不塞进世界书词条**；
6. 以后打开这张场景卡，直接播 demo，不重新调模型。

> 为什么 demo 放侧车、不放词条：
> 一份完整程序 3–5k 字，塞进词条会把它变成“范文”，既吃预算又容易让模型整段照抄；
> demo 只用于预览/评测，不进提示词。

### 6.4 这张场景卡“有没有用”的验收

- demo 能过 C1–C9（证明“按这张卡能拼出来”）；
- 同一道样例题，**有场景卡 vs 没有场景卡**各跑一次：
  - 有场景卡时，元件用对了吗？摆放/顺序对了吗？人工评分更高吗？
  - 没有场景卡时，模型是不是还在“猜”？
- 如果加了场景卡反而更差，说明卡写得太细/太泛，或者和元件卡打架。

## 7. Prompt 分层：场景卡在前，元件卡在后

命中场景卡后，`scene_code` 的上下文顺序建议：

```
【本阶段指令】
【场景卡：题型 / 元件清单 / 摆放与顺序 / 关系 / 易错 / 自检】
【元件卡：只给 components 里列出的元件，降级为 API 摘要 + 最小画法】
【示例：demo 或 1 段相关示例】
【题目 / 解题 / 步骤 / 答案】
```

显式优先级（必须写进 prompt）：

> **关系与顺序以场景卡为准；具体调用形式以元件卡为准。**
> 场景卡不重复 API；元件卡不重复场景摆放。两者冲突时，先按场景卡，再用元件卡补调用细节。

预算：

- 场景卡 ≤ 4000 字；
- 元件卡降级为“API 摘要 + 一行画法”，不整篇注入；
- 示例不超过 1 段；
- 总预算仍受 `WORLDBOOK_BUDGET` 约束；
- 一张场景卡 + 5 张元件卡 + 1 段示例，应该能塞进现有 40000 字池子。

冲突：

- 最多 1 张场景卡；
- 多张命中：按 `concept+tag` > `concept` > `keys` 选最具体的一张，并告警“另外 N 张未注入”；
- 场景卡与元件卡都提到同一关系：告警，逼作者改卡，而不是让模型猜。

## 8. 评测：场景卡必须用“真题”证明自己

- 用 v1.2 建的“示例题库”（你自己的压测题集）做评测集；
- 每张场景卡配 1–3 道题；
- 对比：
  - 有场景卡 / 无场景卡；
  - C1–C9 一次通过率；
  - 修复轮次；
  - 元件使用是否正确（有没有漏画、多画）；
  - 人工评分（摆放/顺序/关系是否合理，1–5 分）。
- 先做 10–15 张种子场景卡（传送带、斜面、滑轮、碰撞、圆周、带电粒子、电磁感应、波形、折射、气体……）；
- 每张都要有 demo + 1 道评测题；
- 没有评测题的场景卡，不进“推荐库”。

> 这也是为什么 v1.4 依赖 v1.2：**没有自己的题库，场景卡的好坏无法判断。**

## 9. 工作量

### 9.1 场景卡这一层（假设元件卡工作台已经做好）

| 工作 | 人日 | 说明 |
|---|---:|---|
| 契约/引擎/命中/预算 | 6–10 | 新字段、新命中、最多一张、优先级、迁移 |
| 场景卡编辑器 | 8–12 | 题型、元件多选排序、装配说明、校验 |
| demo 生成 + 试画 | 5–8 | 调模型、C1–C9、侧车、画布 |
| 门禁/测试/文档 | 5–7 | 契约、负例、overlap、预算、截图 |
| 种子场景 + 评测 | 8–12 | 10–15 张卡 + 每张 1 道题 |
| **合计** | **32–49** | 约 6–10 周（单人全职） |

### 9.2 如果元件卡工作台也在 v1.4 从零做

元件卡工作台（手动写 + 校验 + 试画 + 保存）约 **18–26 人日**。
所以 v1.4 全包约 **50–75 人日（10–15 周）**——这就是为什么建议拆段：

| 段 | 内容 | 人日 | 日历（单人全职） |
|---|---|---:|---:|
| **v1.4.0** | 元件卡工作台（手动 + 试画 + 保存 + 导入导出） | 18–26 | 4–5 周 |
| **v1.4.1** | 场景卡（契约 + 编辑器 + demo 试画 + 10–15 张种子） | 32–49 | 6–10 周 |
| **v1.4.2** | 场景包导出/导入（没有仓库也能分享） | 4–6 | 1–1.5 周 |
| **v1.5** | 卡片仓库/社区（浏览/安装/投稿/审核） | 15–23 | 3–5 周 |

> 如果你希望“v1.4 一个版本号全包”，那就按 **50–75 人日** 估；不要按 32–49 估，因为元件工作台不是凭空存在的。

## 10. 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **场景卡变成“完整程序”** | 作者图省事，把 `Draw.*` 和 8 槽位塞进场景卡，分层失效 | 门禁：场景卡 `content` 不得含 `Draw.`；`code_examples` 必须为空 |
| **场景卡与元件卡打架** | 两边都讲“块要贴着斜面”，模型不知道听谁的 | 显式优先级 + overlap 告警；场景卡不复述 API |
| **题型命中不准** | 考点/题型词表太粗，场景卡命中错题 | 先复用现有词表 + `keys` 兜底；多张命中选最具体；评测验证 |
| **预算被吃光** | 场景卡 + 5 张元件卡 + 示例超过 40000 字 | 场景卡 ≤4000；元件卡降级摘要；示例 ≤1 段；超了告警 |
| **demo 生成不稳定** | 模型生成的 demo 过不了 C1–C9 | 失败就显示错误、让作者改卡/重试；不保存坏 demo；demo 只用于预览 |
| **社区质量** | 场景卡写错、教错 | 审核 + 评测题 + 撤销名单；没有评测题的卡不进推荐库 |
| **过拟合** | 场景卡只对种子题有效 | 留出题；同一张卡测 1–3 道不同变体 |
| **契约迁移** | 旧卡没有 `kind`/`components` | 默认值 + 迁移脚本 + 导入兼容；一次性更新哈希基线 |
| **没有仓库** | 场景卡只能自己用，无法“写完” | v1.4 先做导出/导入场景包；v1.5 上仓库 |

## 12. 需要你拍板

1. **场景卡要不要强制带一份 demo（示例程序）？**
   - 推荐：要。没有 demo 就无法试画，也无法证明“按这张卡能拼出来”。
   - demo 由工作台调模型生成，通过 C1–C9 才保存。

2. **场景卡允许不允许写代码？**
   - 推荐：**不允许**。场景卡只写关系/顺序；`Draw.*` 一律进元件卡。
   - 否则两张卡会打架，分层失效。

3. **题型用什么词表？**
   - 推荐：先用现有 `concepts` / `tags` + `keys` 兜底；不新造词表。
   - 如果现有词表不够细，先记录“缺哪些场景词”，v1.5 再做词表治理。

4. **v1.4 是“一个版本全包”还是拆 v1.4.0/1.4.1/1.4.2？**
   - 推荐拆。全包 50–75 人日，风险太高。

5. **种子场景做多少张？**
   - 推荐 10–15 张，覆盖力学/场电/波光热；每张 1 道评测题。
   - 不要一上来做 50 张——没有评测，做多错多。

6. **没有仓库时，场景卡怎么共享？**
   - 推荐：v1.4.2 做“场景包导出/导入”（一个 JSON 或文件夹），先让老师之间传文件；v1.5 再上仓库。

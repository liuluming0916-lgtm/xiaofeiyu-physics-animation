> 归档说明：2026-10-23 v1.1.17 发布时移入 `docs/history/`。文中“当前/现在”均指 2026-10-22~23 的代码状态；
> 门禁步数等数字以 [`项目现状与路线.md`](../../项目现状与路线.md) 为准，本文不再回填。

> 这份文档描述**当前代码真正在跑的流程**，不是旧版设计稿。

> 验证命令：`node tools/verify-all.mjs`（当前全绿）。

---

## 1. 一句话总览

```text
读题 → 解题 → 分步讲解 ∥ 物理分析 → 写 drawFrame → 程序组装 → Dry-Run → 失败按类型修复
```

模型只负责**五段文字/代码**：

```text
read_problem → solve → breakdown → analysis → scene_code(drawFrame)
```

`stateAt / VIEW / setup / readouts / STEPS / PROBLEM` 都由程序生成或原样保留；
`ANSWERS` 已删，保留为空串只为兼容 8 槽位形状。

---

## 2. 用户看到的主流程

1. 用户输入题面，可附题图；可再附一份老师的参考答案/解析。
2. 页面按阶段链显示进度：
   `读题 → 解题 → 答案讲解 → 物理分析 → 动画代码 → 校验 → 自愈修复`
3. 解题页显示：
   - 解题过程（`solve`）
   - 分步讲解（`breakdown`，按 `title / tex` 行式表解析）
   - **不显示** `analysis`（运动表只在后台用）
4. 动画页使用最终程序：画布 + 左侧「原题 / 第 N 步」页签 + 曲线图。
5. 校验失败会进入修复：画图错误最多重画 3 轮，物理错误最多重跑 2 轮；仍不过则带告警横幅交付。

---

## 3. 阶段链

固定链条（`PHASE5_STAGES`）：

```text
read_problem
→ solve
→ breakdown ∥ analysis（并行）
→ scene_code
→ dry_run
→ repair（只在需要时真正执行）
→ couple（只在有可播放程序时执行）
```

其中需要调用模型的是前 5 个主阶段 + `couple`（`MODEL_STAGES` 只含前 5 个）；
`dry_run` 是本地沙箱，`repair` 是失败后的循环，`couple` 是交付前的步骤耦合。

> v6：`breakdown` 与 `analysis` 只依赖 `solve`，所以**真正并发**；
> `scene_code` 等两者都完成再开始。事件流里会先收到两个 `stage_start`，
> 两段各自的 `stage_done` 按完成顺序到达。

### 3.1 每段吃什么、吐什么

| 阶段 | 输入 | 输出 | 带图？ | 失败时 |
|---|---|---|---|---|
| `read_problem` | 题面、用户手打描述、已知条件、判定词表 | 结构化几何 + 动画元件/场景判定 | 题图 | 视觉门控：端点不支持视觉就停 |
| `solve` | 题面（+ 参考答案/解析） | 完整解题过程 | 题图 + 解析图 | 模型报错就停；解析与题目不一致时停 |
| `breakdown` | 题面 + `solve` | `title / tex` 行式表（2–6 步） | 否 | 模型报错就停（analysis 可能已完成） |
| `analysis` | 题面 + `read_problem` 几何 + `solve` | 只有 MOTIONS 运动表 | 题图 | 解析失败 → `analysis.invalid`，停（breakdown 可能已完成） |
| `scene_code` | 题面 + `analysis` 表 + `read_problem` + 状态键映射 | 只有 `drawFrame` 函数体 | 示意图（没有就整图） | 输出不能组装 → 停 |
| `dry_run` | 程序 8 槽位 | 校验报告 + 可装配程序 | 否 | 进入 `repair` |
| `repair` | 画图错误：失败项 + 上一轮 `drawFrame`；物理错误：题面/读题/解题 | 画图：新 `drawFrame`；物理：重跑 read_problem/solve/analysis/scene_code + 新 breakdown | 示意图 | 画图 3 轮 / 物理 2 轮；仍不过 → 横幅交付 |

> `analysis` **不吃** `breakdown`。用户 2026-10-22 的裁决：分步讲解是“教学步骤”，
> 不是“物理运动阶段”，混进去会让模型把讲解步骤误当运动分段。

### 3.2 事件流（前端靠它显示进度与结果）

```text
run_start
→ stage_start / stage_delta / stage_done   （每个模型阶段）
→ judgement_done                           （读题判了什么）
→ knowledgecard_done                       （知识卡命中了什么）
→ diagram_done                             （示意图裁没裁出来）
→ dry_run 的 stage_start
→ dryrun_done                              （首次校验，失败也要发）
→ [repair 的 stage_start / stage_done / repair_round / dryrun_done] × ≤3
→ repair_done                              （如果进过修复）
→ couple 的 stage_start / stage_delta / stage_done
→ coupling_done                            （stepTimes / fallback / warning）
→ run_done
```

异常时：

```text
stage_error → run_done(error)
cancelled   → run_done(cancelled)
```

## 4. `read_problem`（读题与判定）

### 4.1 它做什么

当前有 v1 / v2 两版，服务端默认用 **v2**（`knowledgecardVersion: 2`）。

**v2（默认）只做四件事**：

1. **看几何**：画面里有哪些物体、谁在左/右、水平还是倾斜、往哪动；
2. **给示意图范围**：四个 0–1 小数 `x0,y0,x1,y1`，供程序裁图；
3. **判动画元件**：从《动画元件词表》里逐字取 id；
4. **判场景**：从《场景词表》里逐字取 id（通常一个，判不出写“无”）。

v2 明确要求：

```text
不要解题
不要复述题文
不要写任何数值（角度、长度、质量、速度、时间都不写）
```

v2 输出小标题：

```text
【题目】
【物体】
【相对位置】
【姿态】
【运动方向】
【示意图范围】
【动画元件】
【场景】
【判定依据】
```

`【题目】` 由模型起名，长度不限；本地解析后只用于**动画页标题 / 导出文件名**，
缺失或空 ⇒ `未命名题目`。标题不进入后续 Prompt。

**v1（旧版，仅旧配置/旧测试使用）** 才会输出【题面复述】等完整转写。

### 4.2 它为什么总是跑

即使是纯文字题也跑。原因是“元件/场景”不可能都字面写在题面里，
必须由模型看题后判；代价是纯文字题也多一次模型调用。

### 4.3 视觉门控

如果带了图，但当前端点 `supportsVision !== true`：

```text
stage_error: vision-unsupported
run_done: error
一次模型调用都不发
```

不会把图偷偷发给不看图的模型。

### 4.4 判定留痕

`stage_done` 之后发 `judgement_done`：

```text
concepts[] / tags[] / elements[] / scenes[]
unknowns{} / problems[] / why / empty
```

判定为空也照发，退化成纯字面 keys，不把链路打崩。

### 4.5 切图

如果 `read_problem` 给了 `【示意图范围】`，程序会真裁图：

```text
diagram_done { ok, reason?, bbox?, width?, height?, fallbackWhole? }
```

裁不出来就退回整幅原题图；只要题目带了图，`scene_code` 始终能看到一张图。

## 5. `solve`（解题）

- 没有参考答案：按题面正常解。
- 有参考答案：system 换成“按解析整理”，数值/符号照抄，不重算、不“更正”。
- 解析没给、后面又需要的量：写“解析未提供”，不许自己补数。
- 解析与题目明显不是同一道题：只输出一行：

```text
【解析与题目不一致】
```

程序看到这个标记后：

```text
stage_error: reference.mismatch
run_done: error + referenceMismatch=true
停在 solve 之后，不再拆步骤/画动画
```

---

## 6. `breakdown`（分步讲解）

- 输出 2–6 步，每步两字段：

```text
title: 这一步发生了什么
tex:   讲给学生听的话（可含公式）
记录之间空一行
```

- 多行 `tex` 可以用 `"""` 包裹。
- 这份输出有两个用途：
  1. 生成 `STEPS` 槽位（只给模板页签；C5 / C6 已改读 analysis）；
  2. 解题页的「分步讲解」面板直接读它。

> `ANSWERS` 已删，所以 `breakdown` 不再需要给 `at_t / step / symbol`。

## 7. `analysis`（物理分析，v6 核心）

### 7.1 它只输出 MOTIONS

```text
assumption: 为没有数值的符号赋值        （可选；题面全给数值就省略）

=== 元件运动表 (MOTIONS) ===

element: block_A
type: block
segment: 1
t0: 0
t1: 1.0
x0: 0
y0: 0
vx0: 0
vy0: 0
ax: 2
ay: 0
x: 0.5*2*t^2
y: 0
note: 受滑动摩擦力向右匀加速
```

同一元件多段就重复一条记录，`segment` 从 1 连续编号。

### 7.2 字段含义

| 字段 | 含义 |
|---|---|
| `element` | 元件 id，同一元件多段保持一致 |
| `type` | 词表元件 id（block / ball / board / …）；多段一致；拿不准写 unknown |
| `segment` | 段号，从 1 开始 |
| `t0 / t1` | 本段起止时间，秒 |
| `x0 / y0` | 本段初位置（米） |
| `vx0 / vy0` | 本段初速度（m/s） |
| `ax / ay` | 本段加速度（m/s²） |
| `x / y` | 位置关于 `t` 的表达式 |
| `yA / yB` | 可选；水银柱等两个液面的高度表达式 |
| `note` | 这段物理过程说明 |
| `kind` | 可省略；当前只接受 `closed` |

### 7.3 坐标约定

- 原点取核心运动起点或题目自然原点；
- `x` 向右为正，`y` 向上为正，单位米；
- 每段的 `x / y` 写该段真实的运动轨迹；
- 同一元件相邻段在交界时刻位置连续（`y` 不能为了绘图被强行归零）。

### 7.4 表达式白名单

变量只允许 `t`。

允许：

```text
+  -  *  /  **（^ 会自动转成 **）
括号
sin cos tan asin acos atan atan2
exp log sqrt abs pow min max floor ceil round sign
常量 pi / PI / E
```

不允许：

```text
属性访问、数组、对象、字符串、函数定义、赋值、三元表达式
其他变量（如 x / vx）
单位（表达式里只能有数）
```

### 7.5 程序会做的校验

`core/analysis/parse.mjs` 在解析时逐条检查：

1. `element` 非空，长度 ≤ 40；
2. `segment` 是 ≥1 的整数；
3. `t0 ≥ 0`，`t1 > t0`，`t1 ≤ 3600` 秒；
4. 六个初态字段都是纯数字；
5. `x / y` 能通过表达式白名单编译；
6. 在 `t0 / 中点 / t1` 三个时刻算出的值必须是有限数；
7. 声明初态必须和表达式一致：

```text
x(t0) == x0
y(t0) == y0
```

8. 同一元件的段号必须从 1 连续；
9. 相邻段必须首尾相接：上一段 `t1` = 下一段 `t0`；
10. 相邻段交界处位置连续（相对 1e-4 / 绝对 1e-6）；
11. 最多 200 段；
12. `T_phys = max(所有段的 t1)`。

任何一条不过，`analysis` 阶段直接：

```text
stage_error: analysis.invalid
run_done: error
不生成程序，不跑 Dry-Run
```

### 7.6 `assumption` 规则

题面只给符号、没给数值时，先声明一组示意值：

```text
assumption: 取 m_A=1 kg、m_B=2 kg、μ=0.2、g=10 m/s²
```

偏好：

- 小整数（1、2、3…），保持题设比例；
- 物理常数用常规值（`g=10`）；
- 无量纲量用常见值（`μ=0.2`、`η=0.8`），不要取违反物理约束的值；
- 角度用 30°/45°/60°；
- 整张表共用这一组数；
- 题面已经给了的数照抄，不改。

程序不会“解”这些赋值，只把它当文本记下来并给一条 `assumption-used` 警告。

### 7.7 ODE：当前明确不支持

如果某段无法写成初等函数，提示词要求模型：

```text
kind: ode
x: ODE
y: ODE
ax / ay: 微分方程右端
```

但当前程序只接受 `kind: closed`，遇到 `kind: ode` 会直接报：

```text
unsupported-kind
本版只接受 kind: closed；收到 "ode"。ODE（数值积分）尚未接入，不要用假闭式代替。
```

然后 `analysis.invalid` 停下。**不会**偷偷用假闭式糊过去。

## 8. 程序组装：8 槽位

`analysis` 解析通过后，程序调用 `generateProgramSlots()` 生成 8 个槽位：

| 槽位 | 谁生成 | 内容 |
|---|---|---|
| `PROBLEM` | 程序 | 用户题面原文 |
| `STEPS` | 程序 | 从 `breakdown` 的 `title / tex` 拆出来；**不再带 `t0 / t1`** |
| `ANSWERS` | 程序 | **空串**（C7 已删，只为兼容形状） |
| `VIEW` | 程序 | `SIM = { duration, bodies, phases }` |
| `setup` | 程序 | `const T_PHYS = ...;` |
| `stateAt` | 程序 | 按 analysis 分段生成的分段位置函数 |
| `readouts` | 程序 | 每个元件的 x / y / vx / vy |
| `drawFrame` | **AI** | 只负责“怎么画” |

### 8.1 `stateAt` 怎么生成

每个元件：

```text
tt = clamp(t, 本元件第一段.t0, 本元件最后一段.t1)
if (tt <= 第1段.t1) 用第1段表达式
else if (tt <= 第2段.t1) 用第2段表达式
...
else 用最后一段表达式
state.e0 = { x, y }
```

注意：**每个元件独立夹取自己的时间范围**，不是全题共用一个总时长。

### 8.2 状态键

按 analysis 里元件第一次出现的顺序编号：

```text
block_A → e0
block_B → e1
...
```

`scene_code` 的提示词里会明确给出这张映射表。

### 8.3 `VIEW`

```js
SIM = {
  duration: 3,                 // = T_phys
  bodies: [
    { id: 'e0', at: (s) => [s.e0.x, s.e0.y] }
  ],
  phases: [{ t0: 0, t1: 1 }, { t0: 1, t1: 3 }]
};
```

运行时会根据 `bodies` 自动求导画 v / a 箭头，所以 `drawFrame` **不要自己画 v/a**。

### 8.4 `STEPS`

- 从 `breakdown` 拆出 `title / tex`；
- **不再带 `t0 / t1`**：物理时间由 analysis 负责；
- C5 只查 `VIEW.duration == analysis.T_phys`，C6 查 analysis 段边界；
- 模板页签只显示文字，不显示秒数、也不跳动画。

### 8.5 `readouts`

每个元件输出四条：

```text
e0.x / e0.y / e0.vx / e0.vy
```

速度用 `stateAt(t±1e-4)` 差分算，避免让 AI 再写一套运动学。

## 9. 清洗与组装

`drawFrame` 回来后，程序把它塞进 8 槽位模板：

```text
/* @slot:PROBLEM */
...
/* @end */
...
```

然后 `buildProgramFromText()`：

1. 按 `@slot` / `@end` 标记切分；
2. 允许 `ANSWERS` 为空，但其它槽位为空仍报错；
3. 套用清洗规则（代码围栏、`console.log`、函数外壳等）；
4. 生成 `program.slots` 与行号偏移表。

如果切分/形状失败：

```text
dryrun_done: fail
stage: cleaner
C1 失败
run_done: fail
不进入 Dry-Run
```

## 10. Dry-Run 校验

### 10.1 执行方式

- 默认在 `worker_threads + node:vm` 沙箱里跑；
- 起不了 Worker 时退回同进程 `vm`，报告里如实写 `fallbackReason`；
- 预算：

```text
墙钟 10 s
内存 512 MB
步长 dt = 1/240 s
最大帧数 200000
```

### 10.2 当前真正执行的检查

| 检查 | 管什么 | 强度 |
|---|---|---|
| `C1` | 8 槽位形状、语法/API 白名单、箭头契约、`state`/`context` 接线对账 | 硬拦（未知全局名降告警） |
| `C2` | 执行能否在预算内正常结束 | 硬拦 |
| `C3` | 所有数值有限（无 NaN / Infinity） | 硬拦 |
| `C4` | 绘制坐标在世界盒内、相邻帧位移不爆炸 | 告警 |
| `C5` | `VIEW.duration` 是否等于 `analysis.T_phys` | 硬拦 |
| `C6` | analysis 段边界的位置连续 | 告警 |
| `C7` | **已删除，不再执行** | — |
| `C8` | `readouts` 稳定（不 undefined / 不空） | 告警 |
| `C9` | 画面有活性（不是全程不动） | 告警 |

> `CHECK_IDS` 里仍保留 `C7` 这个**冻结编号**，但当前 `dry-run` 不生成 C7 结果。
> 新链路没有 `ANSWERS`，C7 已失去输入。

### 10.3 扩展检查（不阻塞）

| 扩展 | 管什么 |
|---|---|
| `C10` | `SIM.regions` 声明的物理包络（越界/圆周偏离等） |
| `X1` | 跨槽位导出键与 STEPS 字段同名 |
| `X2` | `Draw.raw` 使用率 |
| `X3` | 箭头起点是否落在实体上 |

这些放在 `extensions[]`，`blocking: false`。

### 10.4 判定

```text
pass                 全过
pass-with-warnings   有非阻塞告警
fail                 有阻塞失败
cancelled            用户取消
```

## 11. 自愈（repair）

### 11.1 什么时候进

首次 Dry-Run 不是 `pass`，并且没有关闭自愈、不是开发模式。

### 11.2 先分类，再修

失败不是一股脑重画 `drawFrame`，而是先分类：

```text
画图错误：C4 / C8 / C9，或 C1/C2 诊断指向 drawFrame
物理错误：C3 / C5 / C6，或诊断指向 stateAt / setup / VIEW
混合：先修物理（物理一变，画法可能跟着变）
未知：按物理处理，不赌
```

**画图错误：只重画 `drawFrame`**

1. 发 `stage_start(repair, mode='draw', slots=['drawFrame'])`；
2. 修复提示词只带题面、analysis 表、`read_problem` 几何、状态键、失败项、上一轮 `drawFrame`；
3. 模型回一段新的 `drawFrame`；
4. 程序用**同一份 analysis + breakdown** 重新生成 8 槽位；
5. 重跑 Dry-Run；
6. 通过就停，不通过继续，最多 **3 轮**。

物理/数据槽位（`PROBLEM / STEPS / ANSWERS / VIEW / setup / stateAt / readouts`）
在画图修复前后**逐字节不变**。

**物理错误：重跑物理链路**

1. 发 `stage_start(repair, mode='physical')`；
2. 重跑 `read_problem → solve → breakdown/analysis → scene_code`；
3. 重新生成 8 槽位；
4. 重跑 Dry-Run；
5. 最多 **2 轮**。

物理修复后，`breakdown` 和 `stepTimes` 都会重新生成；
不能沿用旧时间轴。

> 当前边界：物理重跑会更新 `read_problem / solve` 的文本供下游使用，
> 但不会重新发 `judgement_done / diagram_done`，也不会重新抽知识卡；
> `scene_code` 仍用第一次裁出的示意图。这一层留到后续收口。

### 11.3 失败交付

物理 2 轮仍不过，或画图 3 轮仍不过：

```text
run_done: fail
banner: warning
converged: false
delivery.playable: 仍然按槽位是否齐全算
```

不会把失败包装成成功；横幅会写清失败检查号、修复轮数、“请人工复核”。

### 11.4 事件

- 首次 Dry-Run 也发 `dryrun_done`（否则用户看不到第一次为什么没过）；
- 每轮修复后各发一次带 `round` 的 `dryrun_done`；
- 每轮发 `repair_round`；
- 最后发一次 `repair_done`（带 `banner` / `stoppedReason`）。

### 11.5 开发模式

`devMode === true` 时：

- 校验照做；
- 不触发自愈；
- 不阻止交付；
- `verdict` 降为 `pass-with-warnings`；
- `gatesBypassed` 记录被放行的检查号。

### 11.6 `couple`（步骤耦合）

- 位置：`repair` 之后、`run_done` 之前，最后一段。
- 只在**有可播放程序**时执行：
  - `pass` / `pass-with-warnings` → 跑；
  - `fail` 但 `delivery.playable === true` → 跑；
  - `fail` 且不可播放 → 标 `skipped`，不产出 `stepTimes`。
- 输入：`analysis` 运动表 + `breakdown` 的 `title/tex` + `T_phys`。
- 输出：`program.stepTimes = [{ step, t0, t1 }]`。
- 失败重试一次；仍失败按步骤均分回退 + `warning`。
- 事件：`stage_start` / `stage_delta` / `stage_done` / `coupling_done`。
- 用 `scene_code` 端点（当前单端点架构下即 `snapshot.endpoint`）。

`stepTimes` 规则：

- 只记录有时间区间的步骤；纯概念步可省略；
- 按 step 升序、不重叠、落在 `[0, T_phys]`；
- **不要求覆盖整段时间**。

## 12. Prompt 系统

### 12.1 目录

主 Prompt（5 份）：

```text
analysis
scene_code
couple
solve
breakdown
```

扩展 Prompt（2 份）：

```text
repair
read_problem
```

`read_problem_v2` 是 v2 读题变体；服务端默认 `knowledgecardVersion: 2` 时用它。

### 12.2 三段结构

每次请求：

```text
[固定前缀] + [条件段（本阶段指令 + 命中的知识卡）] + [任务段（题面/前序产物）]
```

固定前缀按阶段取：

- `read_problem` / `solve` / `breakdown` / `analysis` / `couple`：角色 + 输出纪律；
- `scene_code` / `repair`：角色 + 输出纪律 + SDK 签名摘要；
- 不再有“8 槽位模板骨架”。

`promptHash` 只由固定前缀决定：

- 换题、换图、换知识卡命中 → **不变**；
- 改某阶段指令 / 改前缀 → **变**。

### 12.3 覆盖

规则工作区可以整份覆盖某份 Prompt。
覆盖只改**条件段**，不改固定前缀，所以 `promptHash` 不变；
题目运行中的快照冻结，下一题才生效。

Prompt 编辑器当前 7 项：

```text
read_problem / solve / breakdown / analysis / scene_code / repair / couple
```

## 13. 知识卡（旧称“世界书”）

> “世界书”是早期叫法。界面现在统一叫**知识卡**；代码内部仍叫 `knowledgecard`。
> 知识卡是总称，包含元件卡、动画规范卡、场景卡，以及设置页里的提示词卡 / 本地规则卡。

v6 **运行链路只有一个槽位**：

```text
scene_code
```

`read_problem` 先判出动画元件/场景；只有 `scene_code` 阶段会注入知识卡。

> 数据契约里仍保留 `solve` 作为**旧包读取兼容**，但当前 pipeline / v2 runtime / UI
> 都不再使用它；旧包里的 `solve` 不会进入任何 Prompt。
>
> `concepts / tags` 也属于旧 v1 字段；当前 v2 读题只判 `elements / scenes`，
> 运行时不再用 concepts/tags 触发。

- `read_problem` 先判出动画元件/场景；
- `scene_code` 阶段：按读题几何 + 解题过程触发，注入元件卡 / 规范卡 / 场景卡；
- `analysis` / `breakdown` **不注入**知识卡词条；
- `solve` 槽：**运行时已删除**；数据契约保留旧包读取兼容，当前不注入、不参与 UI。

事件：

```text
judgement_done      模型判了什么
knowledgecard_done  实际命中哪些知识卡、进了哪个槽、有没有空槽/截断
```

## 14. 配置快照与取消

### 14.1 每题一份快照

运行开始时冻结：

```text
promptIds / endpoint / apiKey / regexRules
知识卡词条 / 预算
Prompt 覆盖 / 清洗规则覆盖
maxRepairRounds / devMode
```

运行中改配置不影响这一题；下一题才生效。

### 14.2 取消

- 取消会 abort 当前模型请求；
- 不再进入后续阶段；
- 不执行 Dry-Run；
- 发 `cancelled` + `run_done(verdict=cancelled)`；
- 取消不当成错误（不报红）。

## 16. 失败路径总表

| 情况 | 结果 |
|---|---|
| 带图但端点不支持视觉 | `stage_error: vision-unsupported`，0 次模型调用 |
| `read_problem` 判定为空 | 照常跑，退化字面 keys，`judgement_done.empty=true` |
| 参考答案与题目不一致 | `stage_error: reference.mismatch`，停在 solve 后 |
| `analysis` 表解析失败 | `stage_error: analysis.invalid`，不生成程序 |
| `analysis` 用了 `kind: ode` | `unsupported-kind`，明确报“未接入数值积分” |
| 模型请求失败 | `stage_error` + `run_done: error` |
| 8 槽位切分失败 | `dryrun_done: fail`（C1）+ `run_done: fail`，不跑沙箱 |
| Dry-Run 有阻塞失败 | 按类型进 repair：画图只重画，物理重跑链路 |
| 画图 3 轮 / 物理 2 轮仍失败 | 带 warning 横幅交付，`converged=false` |
| couple 两次都失败 | 按步骤均分回退 + `coupling_done.warning`，不阻断交付 |
| 没有可播放程序 | `couple` 标 `skipped`，无 `stepTimes` |
| 用户取消 | `cancelled` + `run_done: cancelled` |
| 开发模式 | 校验照做，不修不拦，`pass-with-warnings` |

## 17. 当前明确的限制

1. **ODE 没接**：`kind: ode` 会被明确拒绝，不会用假闭式代替。
2. **C7 没跑**：编号还在冻结表里，但新链路没有 `ANSWERS`，C7 不再执行。
3. **C11 没实现**。
4. **analysis 不在 UI 显示**：只在后台生成程序用。
5. **C4 / C6 只告警**：它们有已知误报，不阻塞交付。
6. **C10 / X1 / X2 / X3 是扩展**：不阻塞。
7. **couple 端点**：当前是单端点架构，实际用 `snapshot.endpoint`（即 scene_code 使用的那个）；尚未做真正的“按阶段选端点”。

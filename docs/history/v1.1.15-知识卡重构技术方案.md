## 0. 一句话结论

**方向可行，但必须按“契约 → 引擎 → UI → 迁移 → 发布”的顺序做。**

## 1. 我对聊天记录的理解（先对齐，避免歧义）

### 1.1 触发

- **删除 `keys` 字面触发**：新卡不再靠关键词碰运气。
- 触发只来自 **词表**：
  - 元件卡：`elements: [elementId]`；
  - 场景卡：`scenes: [sceneId]`；
  - 动画规范卡：`constant: true`，不参与触发。
- `read_problem` 第一阶段输出 **`【动画元件】` + `【场景】`**（不再输出考点/题型）。
- 引擎按这两个字段匹配；模型不再“自己选卡”。

### 1.2 词表

- 词表是**单源真相**，卡片只能引用词表里的 id。
- 教师可以**新增词表项**（元件/场景），新增后卡片才能引用它。
- 新建卡时，**先选词表项，再写卡**；不再出现“三栏全空、永远不触发”的卡。
- 元件词表项必须对应一个**已有 `Draw.*` 原语**；不新增 SDK 函数。
- 场景词表项是“题型/装配”的受控 id，不绑定 `Draw.*`。

### 1.3 删除

- 删除：`keys`、`secondary_keys`、`concepts`（考点）、`tags`（题型/细考点）、`category`、`insertion_slot`、`recursive`。
- 删除 UI：解题槽/双槽/未挂槽位筛选，考点/题型/次级键编辑，分类下拉，槽位勾选。
- 保留：`id`、`title`、`kind`、`enabled`、`constant`（仅动画规范卡）、`order`、`priority`、`content`、`code_examples`、`origin`（内部，用于覆盖/恢复）。
- 所有卡只进 **`scene_code`**；`solve` 槽退役。

### 1.4 场景

- 新增**场景词表**与**场景卡**。
- 场景卡按 `scenes` 命中；第一版场景卡只写“装配说明”，**不自动拉取元件卡**。
- `components`（场景卡列出需要的元件、自动注入）放到 **v2.1**，不塞进第一版。

### 1.5 UI

- 知识卡页面重构：词表管理上移；卡片列表按 `kind` 分组；编辑器只留“触发 + 内容 + 示例”。
- 删除旧筛选行、旧字段、旧占位。
- 新增“新建卡向导”和“为什么没触发”的诊断。

### 1.6 测试

- 仍然用真实题测试，按结果改卡。
- “顺应模型”指**用模型容易执行的写法**（正面示例、具体几何、一卡一件），不是放弃物理正确性。
- 验收仍是：C1–C9 + 物理正确 + 你的“能不能上课用”评分。

### 1.7 非目标

- 不做 AI 帮写、卡片仓库、SDK 新函数、三维/流体。
- 不在本期做 `components` 自动注入。
- 不把 57 个考点搬成 57 个场景；场景先做 **5–8 个**，从 10 道题里长出来。

## 2. 目标数据模型 v2

### 2.1 知识卡条目（Entry v2）

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 稳定 id；保存后不可改 |
| `title` | 是 | 仅显示 |
| `kind` | 是 | `anim_rule` / `element` / `scene` |
| `enabled` | 是 | 启用/停用 |
| `constant` | 否 | 仅 `anim_rule` 可为 true；其他卡必须 false |
| `elements` | 条件 | `kind: element` 必填，1..n 个官方/用户元件 id |
| `scenes` | 条件 | `kind: scene` 必填，恰好 1 个场景 id |
| `order` | 否 | 同类型注入顺序；默认 100 |
| `priority` | 否 | `high` / `normal`；预算不足时 high 先保留 |
| `content` | 是 | 卡正文 |
| `code_examples` | 否 | 元件卡必须非空（源校验）；场景卡可为空 |
| `origin` | 是 | `builtin` / `user`；内部字段，UI 不编辑 |

**删除的字段**：`keys`、`secondary_keys`、`concepts`、`tags`、`category`、`insertion_slot`、`recursive`。

**跨字段校验**：

- `kind: anim_rule` ⇒ `constant: true`，`elements`/`scenes` 必须为空；
- `kind: element` ⇒ `elements` 非空，`scenes` 为空，`constant: false`；
- `kind: scene` ⇒ `scenes` 恰好 1 个，`elements` 为空，`constant: false`；
- 所有 id 必须在合并后的词表里；
- `code_examples` 必须能过 C1（元件卡）。

### 2.2 词表 v2

内置：`contracts/knowledgecard-concepts.json` 改为：

```json
{
  "format": "od-knowledgecard-vocab",
  "version": 2,
  "elements": [
    { "id": "block", "name": "物块/滑块", "aliases": ["物块", "滑块"], "primitive": "Draw.box" }
  ],
  "scenes": [
    { "id": "conveyor_block", "name": "传送带 + 物块（共速/生热）", "aliases": ["传送带", "共速", "摩擦生热"] }
  ]
}
```

用户：`ai-rules/vocab.json`（同一格式，可只写 `elements`/`scenes` 的一部分）。

合并规则：

- 内置 + 用户，按 id 合并；
- 用户**不能覆盖**内置 id；
- 用户新增 id 必须唯一；
- 别名冲突要报 warning，不静默；
- 用户元件必须有 `primitive`，且必须是 `sdk/signature-summary.json` 里已有的 `Draw.*`；
- 场景不绑定 primitive。

### 2.3 触发

`read_problem` 输出：

```
【动画元件】belt、block
【场景】conveyor_block
【判定依据】题面有水平传送带和物块，求共速与生热。
```

引擎：

1. 过滤 `enabled`；
2. 加入 `constant`；
3. 按 `elements` 交集注入元件卡；
4. 按 `scenes` 交集注入场景卡；
5. 按预算裁剪；
6. 注入顺序：`anim_rule → element → scene`（v2.0 保持现有顺序；v2.1 有 components 时再改 scene → element）。

**没有 `keys` 扫描，没有次级键，没有递归唤醒。**

### 2.4 注入阶段

- 只有 `scene_code` 收卡。
- `solve` 槽退役；旧卡挂 `solve` 的在迁移时改为 `scene_code`。

## 5. 迁移规则（v1 → v2）

| 旧卡 | 新卡 |
|---|---|
| 30 张内置元件卡（有 `elements`） | 保留 `elements`；删 `keys`/`category`/`insertion_slot`/`recursive` |
| 3 张内置动画规范卡 | `kind: anim_rule`，`constant: true` |
| 用户卡有 `elements` | 保留；删 `keys` |
| 用户卡只有 `keys` | **停用 + 报告**；不猜映射 |
| 用户卡有 `concepts`/`tags` | 停用 + 报告（无场景词表可映射） |
| 用户卡挂 `solve` | 改 `scene_code` |
| 用户卡挂双槽 | 改 `scene_code` |
| 旧 `scene` 卡 | 若有 `concepts`/`tags`，停用+报告；等场景词表建立后重绑 |
| 旧包导入 | 同上；整包不静默丢卡；报告写清哪张停用、为什么 |

**原则**：宁可停用+报告，不静默改触发；老师能看到“哪张卡没迁移成功”。

## 7. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 删 `keys` 后模型漏判 | 卡不触发，成画率下降 | 3 道基线先量；漏判时先改 `read_problem`/词表，不要偷偷加回 keys |

| UI 大改丢功能 | 导入/导出/恢复内置坏 | UI 分步；每步手动验收；保留旧 API 兼容 |
| 契约 v2 破坏旧包 | 老师数据丢 | v1 导入迁移；不静默丢；备份 |
| Git 基线缺失 | 无法回滚 | Phase 0 必须先 commit/tag；否则不开工 |
| 计数/文档腐化 | 门禁红、老师困惑 | 一个事实一处；发布前全量搜索“33/30/3/47” |

### Q2. 用户新增词表的边界

- **默认**：教师可以新增**元件**和**场景**；新元件必须选一个已有 `Draw.*` 原语（不新增 SDK 函数）；新场景不绑定 primitive。
- 如果老师要“斜面+挡板”这种组合，应该建**场景**，不是新元件。

### Q3. 场景卡第一版要不要 `components`

- **默认**：v2.0 场景卡只写“装配说明”，**不自动拉取元件卡**；`components` 自动注入放 v2.1。
- 这样第一版工程量可控；场景卡仍能命中，只是元件卡还要各自命中。

### Q4. 旧字段是“删掉”还是“隐藏”

- **默认**：**schema v2 真删** `keys`/`secondary_keys`/`concepts`/`tags`/`category`/`insertion_slot`/`recursive`；旧包导入时迁移/停用+报告。
- 如果你只想先隐藏 UI、保留字段，工程量会小一半，但“删 keys”就不彻底。

### Q5. 只有 `keys` 的旧用户卡怎么处理

- **默认**：**停用 + 报告**，不自动猜映射；老师可以手动重建成词表卡。
- 备选：按关键词自动匹配到最接近的词表 id（不推荐，容易错绑）。

### Q6. 导出包要不要带用户词表

- **默认**：**要带**。导出卡片时，把它引用的用户词表项一起写进包；导入时先合并词表，再导入卡。
- 否则 A 老师导出的新元件卡，到 B 老师机器上会变成“未知 id”。

### 额外默认（可不回）

- 注入顺序先保持 `anim_rule → element → scene`；有 `components` 后再改 `scene → element`。
- 场景先做 5–8 个，不一次做 57 个。
- 版本号直接 `1.1.12 → 1.1.15`；不补 1.1.13/1.1.14。

---

## 9. 开工顺序（一句话）

**先 Phase 0 打基线；再 Phase 1 词表/契约；再 Phase 2 引擎/Prompt；再 Phase 3 UI；再 Phase 4 迁移/场景；最后 Phase 5 门禁/发布。**
任何一阶段门禁红，就停在这一阶段修，不往下推。

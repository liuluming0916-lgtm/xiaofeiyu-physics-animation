## 0. 先对账：代码现在实际是这样

下面 7 条，可能和你以为的不一样。先看一眼，再回答后面的问题。

1. **答案讲解与物理分析现在是串行的**
   实际顺序是：

   ```text
   read_problem → solve → breakdown → analysis → scene_code
   ```

   `breakdown` 跑完才跑 `analysis`，虽然两者都只依赖 `solve`，已经具备并行条件。

2. **动画联动现在是关掉的**
   模板页签只换文字，不跳时间；时间轴也不翻页签。
   之前的“动画联动”开关已经从页面删掉。

3. **`STEPS` 的 `t0/t1` 是程序“平均取点”算的，不是“第 1 步对应第 1 段”**
   程序把 `[0, T_phys, 所有段边界]` 排序后，按步数均匀取点。
   所以步数一多，可能出现两步落在同一个时刻，或者某一步跨了好几段。
   这就是“直接恢复联动会跳错”的根本原因。

4. **“世界书”这个名字还在代码和界面里**
   契约里它叫 `knowledgecard`，UI 里叫“世界书”。
   但里面的卡已经基本是“动画卡”（30 张元件卡 + 3 张动画规范卡），不是早期那种题海知识库。

5. **`solve` 槽位还没删**
   契约 `KNOWLEDGECARD_SLOTS` 现在仍是：

   ```text
   ['solve', 'scene_code']
   ```

   引擎里也还有 `solve` 槽分支。
   只是**内置卡全部只挂 `scene_code`**，所以 `solve` 槽实际注入是空的。
   也就是说：逻辑上已经不用它，但代码里还没删干净。

6. **`read_problem_v2` 不做完整题面转写**
   当前默认 v2 只写：

   ```text
   物体 / 相对位置 / 姿态 / 运动方向
   示意图范围
   动画元件 / 场景
   判定依据
   ```

   它明确要求“不要复述题文、不要写数值”。
   完整题面转写是 v1 旧口径。

7. **修复段只重画 `drawFrame`**
   物理槽位（`stateAt / VIEW / readouts / STEPS`）由 analysis 生成，修复时冻结。
   如果失败根因在 analysis（比如 C3 非有限、C5 时间对不上、C6 边界跳变），
   现在会反复重画 `drawFrame`，但**修不好根因**。

## B. 动画联动（把“步骤”和“时间”重新绑起来）

- **D**：其他。

### B3. 步骤和时间怎么对应（最关键）

现在 `STEPS` 的 `t0/t1` 是程序平均取点，**没有语义**。可选：

- **A**：让 `breakdown` 每步多写一个 `phase` 字段（第几步对应 analysis 的第几个全局阶段）。

理由：`breakdown` 是教学步骤，`analysis` 是物理分段，两者数量经常不等；

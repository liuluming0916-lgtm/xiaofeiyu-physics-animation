|---|---|

## 一、总体架构

```text
┌─────────────────────────────────────────────┐
│ 渲染进程（React）                             │
│ 解题页 / 动画页 / 设置页 / 导出菜单            │
└───────────────┬─────────────────────────────┘
                │ HTTP（127.0.0.1，随机端口）
┌───────────────▼─────────────────────────────┐
│ 主进程（Electron）                            │
│ 本机服务 · 规则工作区 · 账本(SQLite) · 导出   │
│ 编排器：八阶段链路 · 事件流(SSE)              │
└───────┬───────────────────────┬─────────────┘
        │                       │
┌───────▼────────┐   ┌──────────▼────────────┐
│ 模型网关        │   │ 校验与执行             │
│ 流式/重试/脱敏  │   │ 九项判据 + Worker 沙箱 │
└────────────────┘   └───────────────────────┘
```

**四个关键设计决定：**

1. **本机 HTTP 服务而不是 file://**：页面与主进程用 HTTP 通信，`/api/*` 才能工作；端口用 0 由系统分配，不写死；
2. **进程内隔离**：模型产出的代码在 Worker 沙箱中试运行，超时、内存、死循环都被拦住，不污染主进程；
3. **配置快照**：每道题开始运行时冻结一份配置与规则快照，运行中改配置不影响本次；
4. **数据全本地**：题目、密钥、历史、导出物都在本机目录，只有模型调用出网。

## 二、生成链路（编排器）

| 序号 | 阶段 | 执行方 | 产出 |
|---|---|---|---|
| 1 | read_problem | 模型 | 题面转写、元件/场景判定、几何转写 |
| 2 | solve | 模型 | 解题过程 |
| 3 | breakdown ∥ analysis | 模型（并行） | 步骤文本 ∥ 运动方程表 |
| 4 | scene_code | 模型 | 逐帧绘制函数 |
| 5 | dry_run | 本地 | 判据结果 + 试运行帧 |
| 6 | repair | 模型 | 只重画画面 / 重算物理 |
| 7 | couple | 模型 | 步骤 → 时间区间 |

并行点：第 3 步的两支互不依赖，同时发起；任一支失败不影响另一支的结果保留。

## 三、关键模块

| 模块 | 职责 |
|---|---|
| 编排器 | 串阶段、发事件、控制修复轮次与上限 |
| 模型网关 | 流式解析、错误分类（鉴权/限流/超时/断流）、Key 与路径脱敏 |
| 清洗切分 | 把模型输出按标记切成 8 个槽位，保证行号可反查 |
| 物理分析生成器 | 把运动方程表编译为位移/速度/加速度代码（模型不参与计算） |
| 判据引擎 | 九项静态与数值判据（C1–C9）+ 一项物理包络扩展（C10） |
| 沙箱 | Worker 中执行，限制时间、内存、逃逸调用 |
| 修复分类器 | 按失败检查号判定“画图错”还是“物理错” |
| 导出器 | 单文件网页（内联运行时与公式）、GIF 编码 |
| 账本 | SQLite 记录运行指标与审计 |
| 观测 | 运行记录、失败复现包、开源日志（全脱敏） |

## 四、数据存储

### 4.1 目录

| 目录 | 内容 |
|---|---|
| `%APPDATA%\xiaofeiyu-physics-animation\data\` | 规则、密钥、账本、观测记录 |
| `…\data\ai-rules\knowledgecard\` | 用户知识卡 |
| `…\data\ai-rules\prompts\` | 用户覆盖的提示词 |
| `…\data\history.db` | SQLite 账本 |
| `文档\小肥鱼物理解题动画\导出\` | 导出产物 |
| 软件目录\`开源日志\` | 每次运行的日志（脱敏） |

### 4.2 数据库表

| 表 | 用途 | 关键字段（概括） |
|---|---|---|
| `runs` | 一次运行的汇总 | 运行 ID、版本、模型、判定、耗时、检查号分布、token 估算、时间戳 |
| `run_stages` | 逐阶段明细 | 运行 ID、阶段名、耗时、状态、错误类型 |
| `audit_log` | 审计留痕 | 类型（导出/配置变更/密钥变更）、摘要、时间 |
| `meta` | 结构与版本 | 结构版本号、维护时间 |

**约束：**

- `runs` 与 `run_stages` 为父子关系，删除运行记录时级联清理；
- **密钥不落库**：写入前按已知 Key 值、`Bearer` 形态、`sk-` 形态三重脱敏；
- 同一运行 ID 重写为覆盖语义（先删后插），避免重复计数；
- 老库按字段改名迁移（历史字段）并在 `meta` 中记录结构版本。

## 五、安全设计

| 面 | 措施 |
|---|---|
| 渲染进程 | 关闭 nodeIntegration、开启 contextIsolation、开启 sandbox |
| 进程间 | 预加载只转发三个固定通道，不透传任意 channel |
| 本机服务 | 只绑 127.0.0.1；写操作校验 Origin；导出落盘路径限定在导出目录内 |
| 模型产出 | 静态判据拦 `require`/`eval`/`Function`/原型链逃逸；沙箱拦死循环与超内存 |
| 数据 | Key 单独存文件、不随配置导出；日志与账本全脱敏 |
| 网络 | 外链交系统浏览器打开，页面禁止导航到非本机地址 |

## 六、性能设计

| 指标 | 目标 | 手段 |
|---|---|---|
| 单题生成 | ≤3 分钟 | 并行两支、修复轮次上限、超时按“未收到新数据”计 |
| 界面响应 | 生成中不卡顿 | 全程事件流（SSE），前端增量渲染 |
| 导出 | ≤5 秒 | 公式构建期预渲染，运行时内联 |
| 启动 | ≤5 秒 | 本地服务随机端口，先起服务再开窗 |

## 七、技术选型

| 选型 | 理由 |
|---|---|
| Electron | 需要本机文件、SQLite、子进程能力，且要单 exe 分发 |
| React + TypeScript | 界面状态多（阶段、步骤、时间轴），类型约束降低改坏风险 |
| better-sqlite3 | 同步 API、无需额外服务、单文件数据库 |
| MathJax | 公式质量与离线渲染能力 |
| Worker 沙箱 | 模型代码必须在隔离环境试运行 |

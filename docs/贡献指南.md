# 贡献指南

## 一、先跑起来（10 分钟）

```bat
:: 1) 依赖
npm install
cd web && npm install && cd ..

:: 2) 构建前端（开发形态）
node tools\web-build.mjs

:: 3) 总门禁：必须全绿再动手
node tools\verify-all.mjs
```

跑完看到 **`✓ 全部门禁通过`** 才算环境对了。红了先别改代码，按 [门禁都盯什么](门禁都盯什么.md) 对照。

---

## 二、提交什么最容易通过

按"好上手"排序：

| 想做的事 | 改哪里 | 门槛 |
|---|---|---|
| 加/修一张**元件卡** | `core/worldbook/source/93-elements.json`（由 `tools/build-animation-cards.mjs` 生成） | 低：会写一段能过检查的示例代码 |
| 补一条**物理规范** | `core/prompts/stage-rules.mjs` | 低：物理要准 |
| 修**文案**（界面说明、错误提示） | `web/src/` | 低：中文说清楚 |
| 修**导出/打包** | `core/export/`、`tools/` | 中：要先懂生成链 |
| 改**判据 C1–C9** | `core/lint/`、`core/dryrun/` | **高：先开 issue 说清楚为什么，别直接提 PR** |

> ⚠ **判据和门禁的口径不欢迎"顺手改"**。它们是这个项目的信誉所在。
> 想放宽一条检查，必须在 issue 里说清"它误报了什么题、证据是什么"。

---

## 三、一次提交的规矩

1. **一件事一次提交**。不要"顺手把格式也改了"——diff 会看不清。
2. **提交信息说清三件事**：改了什么 / 为什么 / 跑了哪条命令验证。
3. **生成物要么一起提交，要么一条命令能重建**。别让仓库停在一个"重建不出来"的状态。
4. **别提交**：密钥、`release/`、`node_modules`、`web/dist/`、第三方素材（见 [.gitignore](../.gitignore)）。

---

## 四、写代码的几个约定

| 约定 | 为什么 |
|---|---|
| 注释写**为什么**，不写"这行在干什么" | 后来的人（包括你）需要的是当初的判断依据 |
| 别删别人的"坑"注释 | 那是踩过之后留下的路标，删了会有人再踩一次 |
| 断言要能自己解释 | 门禁报告是给人看的，不是给机器看的 |
| 新增文件先想：它是**源**还是**生成物** | 两类文件的改法完全不同 |

---

## 五、遇到"门禁红了但我不懂"

按这个顺序查，八成能定位：

1. 报告最后会写 **`✗ 失败明细`**，先看那几行；
2. 若是"逐字节相等"类 → 你改了源但没重跑生成命令；
3. 若是"契约不一致" → `node contracts\generate-contracts.mjs`；
4. 若是"世界书"类 → 先跑 `node tools\build-animation-cards.mjs`；
5. 还不行就开 issue，**把命令输出原样贴上**（别只说"跑不过"）。

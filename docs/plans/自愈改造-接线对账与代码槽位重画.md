# 自愈改造：接线对账 + 代码槽位重画（设计与施工口径）

> 状态：**实施中**（v1.1.16 探针版）
> 起因：两次真实运行里，自愈把“画面问题”修成了“检查绿、画面崩”——第 1 次把物理解析换成编造曲线，第 2 次为了补 `state.yB` 把滑轮抬到 3.0、B 沉到地下。
> 结论：**问题不在提示词写得不够细，而在自愈的“目标”和“权限”错了。**

---

## 1. 两条原则

### 原则 A：自愈只准修“数据”，不准修“画法”

| 槽位 | 归类 | 坏了怎么办 |
|---|---|---|
| `STEPS` / `ANSWERS` | 数据 | **补丁**（现有做法） |
| `VIEW` / `setup` / `stateAt` / `drawFrame` / `readouts` | 代码 | **整段重画 `scene_code`**，禁止局部补丁 |

理由：几何是全局的。抬一个滑轮会改变绳的走向、悬挂物的位置、与地面的关系；
局部补丁必然“按倒葫芦起了瓢”。判据只看**要改的是哪类槽位**，不看画面长什么样——因此不涉及任何“对题”的规则。

### 原则 B：跨槽位的名字必须对账

同一份程序里，A 槽位“提供”的名字与 B 槽位“消费”的名字必须一致：

| 提供方 | 名字 | 消费方 |
|---|---|---|
| `stateAt` 的 return 键 | `state.<k>` | `drawFrame`、`readouts`、`VIEW.bodies[].at` |
| `setup` 的 `RETURN(k, …)` | `context.<k>` | `stateAt`、`drawFrame`、`readouts` |

对不上就是**接线错误**。它现在只有“跑到画图才炸”这一种暴露方式，而且报错指向**消费方**（`drawFrame` 第 N 行 NaN），
把自愈引到错误的地方去改。所以要在**生成完、画之前**就把差集报出来，并且指明“该去哪个槽位补”。

## 2. 改动二：自愈分模式

### 2.1 判定

`planRepair()` 已经算出本轮要改哪些槽位。新增：

```
mode = 与 CODE_SLOTS 相交 ? 'regenerate' : 'patch'
```

### 2.2 两种模式的差别

| | patch（数据） | regenerate（代码） |
|---|---|---|
| 发的提示词 | `buildRepairTask`（只改列出的槽位） | **`scene_code` 的原始提示词** |
| 附带 | 失败检查 + 诊断 + 已试轮次 | **上一轮为什么没过** + **上一轮代码（可整体重排）** |
| 要求 | 只输出被改动槽位 | 输出完整 8 槽位（允许整体重排，不要求保留结构） |
| 合并 | 合并返回的槽位 | **只采纳代码槽位**；`PROBLEM/STEPS/ANSWERS` 强制保留上一版 |
| 图片 | 不带 | **带**（题图 / 示意图，和首次生成一致） |
| 事件 | `repair_round{mode:'patch'}` | `repair_round{mode:'regenerate'}` |

### 2.3 为什么数据槽位仍然允许补丁

`STEPS/ANSWERS` 是行式表，局部改一行不会破坏别处；重画反而可能把已经对的答案改掉。
（“只抄不推/缺量留空”两条规则仍由解析模式把关。）

### 2.4 预算

仍然总共 3 轮；`regenerate` 也计 1 轮。连续两轮同一失败签名仍按现有规则停止。

## 3. 改动三：接线对账（通用，不做单点）

### 3.1 采集

在 Dry-Run 里、**画第一帧之前**：

1. `stateAt` 提供的键：在 `t = 0, duration/2, duration` 各跑一次，取 `Object.keys()` 的并集；
2. `context` 提供的键：`setup()` 跑完后 `Object.keys(program.context)`，去掉运行时内置名
   （`SIM/STEPS/ANSWERS/MODE/Draw/Phys/at/duration`）；
3. `state` 消费的键：静态扫 `drawFrame` / `readouts` / `VIEW` 源码里的 `state.<name>`；
4. `context` 消费的键：静态扫全部代码槽位里的 `context.<name>`。

### 3.2 判定与报错

- `消费 − 提供` 非空 ⇒ **C1 失败**（阻塞），逐条诊断：
  - `rule: 'state-key-missing'`，`slot: 'stateAt'`，`message: 'drawFrame 读了 state.yB，但 stateAt 的 return 里没有它——请在 stateAt 补上（不要改 drawFrame 去凑）'`
  - `rule: 'context-key-missing'`，`slot: 'setup'`，同形。
- 只在“确实读到了”时报告；`state?.[k]`、`context?.[k]` 这类可选读取**不算消费**（避免误报）。

### 3.3 为什么做成通用

公测里同类问题会有很多（`readouts` 键 vs `ANSWERS.symbol`、`STEPS.step` vs `ANSWERS.step`……）。
这里先把“名字对账”这一层做出来，后续同类只需往同一张表里加一对（提供方、消费方），不再各写一条检查。

---

## 4. 不做什么（明确边界）

- ❌ 不做“沉地/绳脱节/长宽比”这类画面质量启发式——那是按题型写规则，属于“对题”。
- ❌ 不让自愈“顺手改善画面”。
- ❌ 不新增 C10 之类的评分；接线错误挂在 C1 下，不改变 C1–C9 的冻结口径。

---

## 5. 验收

1. **单元**：构造一个 `drawFrame` 读 `state.yB`、`stateAt` 不返回 `yB` 的程序 → C1 必须报 `state-key-missing` 且指向 `stateAt`；
2. **策略**：构造一个“只有 C2 失败、且要改代码槽位”的场景 → 自愈必须走 `regenerate`，且 `STEPS/ANSWERS` 不被改写；
3. **回归**：`node tests/orchestrator-selftest.mjs`、`node tests/prompts-selftest.mjs`、`node tools/verify-all.mjs` 全绿；
4. **实跑**：同一道传送带题再跑一次，观察 `repair_round.mode` 与最终画面。

---

## 6. 已知代价

- `regenerate` 更贵（一次完整 `scene_code`，约 8k–12k tokens、2–3 分钟）；
- 接线对账只覆盖“名字”，覆盖不了“几何语义”（比如绳该接切点）——那属于将来的“画面审阅”，本期不做。

# 手动补充打回 —— 难度、风险与方案（评估稿）

> 状态：**未开工**。本文件只做评估与方案，不含实现。
> 相关：`docs/history/v1.1.17-发布说明.md`、`docs/history/ROADMAP-旧版-2026-10-19.md` §3（教师反馈→重绘，已定方向）、
> `core/orchestrator/pipeline.mjs`（自愈循环）、`core/repair/plan.mjs`（重发计划/回灌文本）。
> 评估时间：2026-10-20。

---

## 0. 一句话结论

**这件事技术上不难，难在"归因"和"版本"。**

- 现有自愈循环已经把 80% 的管道铺好了（重发计划、回灌文本、合并、复检、留档），
  教师反馈只是"多一个输入端"；
- 但教师的一句话里，可能混着**四类完全不同的病灶**（画法 / 物理 / 清洗 / 判据），
  其中两类**根本不该发给模型**。不先分流，反馈会变成"越改越糟"；
- 真正的成本不在代码，在**版本管理**（旧版/新版/采纳哪版）和**反馈样本的留档口径**。

**工期**：MVP 3–4 人日；完整版 7–10 人日（含门禁与手测）。建议先做 MVP。

## 1. 先对齐：已有决定与新需求的差别

`ROADMAP-旧版` §3 已经定过一版：

| 已定 | 内容 |
|---|---|
| 入口 | 动画页「这里画得不对」→ 一句话描述 |
| 范围 | **只重绘，不重解**；`PROBLEM / STEPS / ANSWERS / VIEW` 逐字节保留 |
| 判据 | 仍须过 C1–C9，不是绕过检查的通道 |
| 对比 | 前后两版并存，**不静默替换** |
| 轮次 | 建议 3 轮，超过提示"可能不是画法问题" |
| 留档 | 每条反馈是"最高价值的样本"，按条目统计 |

这次的新说法有三处扩展，**不推翻上面，但会改变形态**：

1. **触发点是"自愈失败之后"**（banner 显示"已自动修复 3 轮仍未通过"）——不是随时可点；
2. **反馈是多类混装**："比例异常 / 不符合物理 / 清洗掉了格式"——其中"清洗"根本不在模型手里；
3. **回灌内容要"连同解题、拆分、代码一齐"**——这句话本身就意味着**可能不止重绘**。

> 所以第一件事不是写代码，是把"这句话到底该发给谁"分清楚。

## 2. 四类病灶：必须先分流

教师看到的是画面，但画面的错可能来自四个地方。**只有前两类该发给模型。**

| 类 | 典型说法 | 真正的病灶 | 该发给谁 | 发错的后果 |
|---|---|---|---|---|
| **A 画法/几何** | "块没贴着斜面""箭头方向反了""弹簧穿模" | `drawFrame` / `stateAt` / `VIEW.bodies` | **模型**（重发 scene_code） | — |
| **B 物理/数据** | "共速时刻不对""答案和 STEP 对不上""状态量算错" | `solve` / `steps` / `answers` | **模型**（重解链，需显式确认） | 只重绘 → 画面更漂亮但还是错的 |
| **C 清洗/格式** | "公式掉成一行了""`**` 没去掉""切分把句子劈开了" | `core/cleaner/*`（确定性正则/切分） | **不进模型**，进清洗规则/工单 | 模型会"补偿"一个它看不见的过程 → 输出更乱 |
| **D 判据/渲染** | "明明对却说错""画面比例怪"（AutoView） | C1–C9 误报 / 视口计算 | **不进模型**，记录争议 | 模型会为了讨好判据写畸形代码 |

**为什么 C 类绝不能发模型**：清洗是本地确定性的（`core/cleaner` 的 marker-split / regex-rules / policy），
模型看不到清洗过程，也不知道自己哪一步被削掉了。让它"把格式改好"，它只能猜，
猜错就把本来正确的槽位一起改坏——这是最典型的"越修越烂"。

**为什么 D 类不能发模型**：AutoView 的视口与归一化在运行时（`sdk/runtime`），
模型改坐标只会把物理量改错来"凑画面"。比例问题十有八九是视口/边距，不是 `Draw.box` 的宽高。

> 落地建议：反馈表单**类别必选**，选 C/D 时**不出现"重绘"按钮**，改为"记一条问题"。

## 3. 现状盘点：能复用什么

| 能力 | 位置 | 能否直接复用 |
|---|---|---|
| 重发槽位决策（诊断→槽位表） | `core/repair/plan.mjs` `planRepair` / `CHECK_TO_SLOTS` | ✅ 直接复用；教师反馈走"补充输入"而不是替代诊断 |
| 回灌文本骨架（原题+检查+诊断+已试轮次+只许改这些槽位+当前代码） | `buildRepairTask` | ✅ 加一段"教师意见"即可，结构不动 |
| 合并（未涉及槽位逐字节不变） | `mergeRepairOutput` | ✅ 正是"只重绘"要的语义 |
| 复检 | `runDryRun` + C1–C9 | ✅ 原样 |
| 每轮留档（对话/8 槽/诊断） | 开源日志 `createRunLog` | ✅ 加 feedback 字段 |
| 运行记录 | `history.db` `runs`（`record_json`） | ⚠️ **没有父子关系**，需要加 `parent_run_id` 或写进 `record_json` |
| 前端持有 8 槽 + banner + 轮次 | `store.ts`（`programSlots`、`repairRounds`、`banner`） | ✅ 重绘请求可以直接带上 |
| 播放器 | `template/animation-template.html` | ⚠️ Draw 命令**没有实体 id**（只有 `SIM.bodies.id`），点选物体成本高 |

**结论**：管道成本低（3 天量级），缺口集中在三处：
① 没有"续跑"入口（`runPipeline` 是一次性 generator，跑完即散）；
② 历史没有版本链；
③ 画面元素不可选（只能靠"时间点 + 描述"定位）。

## 4. 两种失败态，入口要分开

自愈失败不等于"有画面可指"：

| 形态 | 判定 | 教师能看到什么 | 入口应该给什么 |
|---|---|---|---|
| **可播**（8 槽齐全，带 banner） | `delivery.playable === true` | 有画面、有播放器 | 时间点 + 画面区域 + 描述（可重绘） |
| **不可播**（skeleton，缺槽） | `playable === false` | 只有代码/诊断 | 代码定位 + 描述（重绘可能仍失败，先补槽） |

这一点现在没被区分——`banner` 两种都挂，但"指出某处画错了"只对第一种成立。
**MVP 只在可播态开重绘入口**；不可播态给"重跑一次"或"看诊断"。

## 5. 方案：分三期

### P0 · MVP「重绘单点」（3–4 人日）

**目标**：教师在自己看得见的问题上，补充一句，重画一版，对比后采纳。

- **入口**：动画页 banner 下方 →「指出问题并重绘」（仅 `playable` 时出现）。
- **表单**（4 个字段，不许多）：
  1. 类别（必选）：画法/几何 · 物理/数据 · 清洗/格式 · 渲染/判据
  2. 时间点（可选，滑块取当前 `t`）
  3. 哪里（可选，一句话："斜面顶部""读数面板第二行"）
  4. 期望（必填，一句话："块底边应贴斜面，不要悬空"）
- **服务端**：`POST /api/rework`（SSE，与 `/api/run` 同源同校验）
  - 入参：`runId`（可选，仅用于留档）、`problem`、`images`、`base:{slots}`、`feedback`、`scope`
  - `scope: 'scene_code'`（默认）→ 只重发 `stateAt / drawFrame / VIEW / readouts` 中与类别相关的槽位
  - 复用 `buildRepairTask` 的骨架，插入 `【教师意见（优先级高于自动诊断，但不得违反硬性约束）】`
  - 合并 → `runDryRun` → 事件流复用 `repair_round` / `dryrun_done`（前端零改动即可显示）
- **成果展示**：新版**不覆盖**旧版，两版并存，按钮「采纳这版 / 丢弃」。
- **判据**：仍过 C1–C9；不过 → 照旧挂 banner，并附一句"已按你的意见重绘，但未通过 C3/C7……可能不是画法问题"。
- **留档**：`history.db` 记一条 `parent_run_id` + `rework: { feedback, scope, adopted }`；
  开源日志加 `feedback` 段。

**MVP 明确不做**：点选物体、区域框选、多问题、重解、截图回灌、自动改卡。

### P1 · 「分流与多问题」（5–6 人日）

- 四类病灶路由：C/D 类不调模型，落"问题工单"（进 `audit_log` 或独立表）；
- 物理类（B）→ **重解链**：显式勾选 + 二次确认（"会改答案，原答案将保留为历史版本"）；
- 多问题清单（≤5 条），每条独立锚点（时间点 + 描述）；
- 区域标注：播放器暴露"当前帧命令的 bbox"，前端画矩形 → 传给模型（成本中等，因为要读命令 envelope，不改 SDK）；
- 截图回灌（仅 `supportsVision`）：把当前帧 canvas 截图作为图像输入——**可选**，先测一轮再决定；
- 反馈 → 卡片归因统计：哪张 `wb_el_*` 被投诉最多（这是 v1.1.16 "卡手术"的直接证据来源）。

### P2 · 「闭环数据」（2–3 天）

- 投诉 → 卡片改进建议报告（只读，不自动改卡）；
- 教师反馈样本脱敏导出（给后续 prompt/卡迭代当回归集）；
- 与 v1.1.16 的 A/B 打通：反馈命中卡 → 填进 §9.2「卡片手术」表的"证据"列。

## 6. 难度拆解（按层）

| 层 | 工作 | 难度 | 人日 |
|---|---|---|---|
| 契约 | rework 请求/事件形状、`parent_run_id`、反馈字段 | 低 | 0.5 |
| 服务端 | `/api/rework`（SSE）+ 复用合并/复检 | 中 | 1.5 |
| 回灌文本 | `buildReworkTask`（原题+解法+STEP+答案+8 槽+教师意见+允许改的槽位） | 中 | 1 |
| 前端 | 表单、时间锚点、两版对比、采纳/丢弃 | 中高 | 2 |
| 留档 | history 版本链、observations、开源日志 | 中 | 1 |
| 门禁 | 新增 2–3 步（`rework` 契约、越权拒绝、未涉及槽位逐字节不变） | 中 | 1 |
| 手测 | 3 题 × 2 轮 | 低 | 1 |

**MVP 合计 ≈ 3–4 人日**（不含 P1 的分流、多问题、区域标注）。
**完整版 ≈ 7–10 人日**，另加 20% 风险准备金。

> 说明：本项目是单人维护 + 门禁驱动，人日按"能进 `verify-all` 的完成度"估，
> 不含打磨文案与 UI 细节的时间。

## 7. 风险表

| # | 风险 | 概率 | 影响 | 触发条件 | 应对 |
|---|---|---|---|---|---|
| R1 | **归因错误**（把渲染/清洗问题当画法） | 高 | 高 | 教师说"比例不对/格式乱了" | 类别必选；C/D 类不进模型；重绘后再失败就提示"可能不是画法问题" |
| R2 | **改坏已通过的部分** | 中 | 高 | scene_code 内部耦合（VIEW.bodies ↔ drawFrame 读的键） | 沿用 `CHECK_TO_SLOTS` 的联动表；合并后必须复检；未涉及槽位逐字节断言 |
| R3 | **版本混乱**（三版并存，导出/历史对不上） | 高 | 中 | 教师连点三次重绘 | 单一"当前采纳版"指针；`parent_run_id` 链；导出烧 provenance |
| R4 | **成本膨胀**（每次带全 8 槽 + 解法 ≈ 15–25k tokens） | 中 | 中 | 重解链 + 多轮 | 只重绘时只带目标槽 + 原题 + 答案；重解才带全链；轮次上限 3 |
| R5 | **越权/提示注入**（教师写"忽略校验""直接通过"） | 低 | 高 | 反馈文本进 prompt | 判据在本地，模型关不掉；反馈放在独立区块并写明"不得违反硬性约束"；限长 |
| R6 | **不可复现**（同反馈两次不同） | 中 | 中 | 模型非确定性 | 记录 model + promptHash + 轮次；两版都留，不静默选 |
| R7 | **隐私/版权**（反馈里写学生姓名、校名） | 低 | 中 | 样本导出 | 复用 `redactValue` / `collectSecrets`；表单提示 |
| R8 | **判据争议死循环**（教师说对、C1 说错） | 中 | 中 | 反复重绘仍不过 | 提供"判据争议"出口：记工单 + 开发模式，不改代码 |
| R9 | **UI 拥挤**（动画页已有 banner/导出/播放） | 中 | 低 | 再加批注面板 | 抽屉式，默认收起；只在 playable 出现 |
| R10 | **清洗问题被当成模型问题** | 中 | 中 | "掉格式" | P1 加"清洗前后对比"入口，让教师先看到是清洗动的手 |

**最高优先级：R1 与 R3。** 这两个不解决，功能上线后会变成"每次投诉都改代码、改完不知道哪版对"。

## 8. 需要你拍板的六个点

| # | 决策 | 选项 | 我的建议 |
|---|---|---|---|
| 1 | 默认只重绘，还是允许重解？ | A 只重绘（重解需勾选）/ B 全量打回 | **A**：重解会改答案，破坏"锁定前四槽"的对照口径 |
| 2 | 反馈是否强制分类？ | 必选 / 可选 | **必选**：不分流就无法决定发不发给模型 |
| 3 | 版本策略 | 并存采纳制 / 直接覆盖 | **并存**：旧 ROADMAP 已定"不静默替换" |
| 4 | 轮次上限 | 3 / 5 / 无限 | **3**，与自愈一致；超过提示"不是画法问题" |
| 5 | MVP 是否含区域框选 | 含 / 不含 | **不含**：先时间点 + 文字，区域留 P1 |
| 6 | 清洗类问题是否单开面板 | 是 / 否 | **是**（P1）：否则永远被误当成模型问题 |

## 9. 与 v1.1.16 的关系（重要）

- v1.1.16 的定位是"测试与内容为主，代码只做收口"。**这个功能不属于 v1.1.16**：
  它要改服务端、前端、历史库、门禁，是完整一轮功能开发。
- 但它和 v1.1.16 的 Phase 1 **强相关**：A/B 剥离时，教师看到坏画面想"手动指一下"的冲动，
  正是这个功能的需求来源。建议把本期收集到的**教师口头反馈**先按 §7 的四类记下来，
  不实现功能，先把"归因分类"跑通——这本身就是 P0 表单的原型。
- 建议排期：**v1.1.17**（或 v1.2 的第一个功能），与"场景卡"分开，不要混在一轮里。

## 10. 最小可行验证（不写功能也能先做的三件事）

如果不想马上开工，这三件事可以先用零代码验证需求是否成立：

1. **拿 3 条真实反馈做归因**：请教师对着现有 banner 版本口述三条"哪里不对"，
   按 A/B/C/D 分类。若 C/D 占比过半，说明**先修清洗与视口比做重绘更值**。
2. **测一次"人工回灌"**：手工把 `buildRepairTask` 的输出改一段教师意见，走一遍现有自愈管道，
   看模型是否真能按"时间点 + 描述"改对。这一步只用命令行，不改代码。
3. **量一次成本**：一条重绘请求的 token 与耗时，和自愈一轮对比。若超过 25k tokens，
   MVP 就必须做"只带目标槽"的裁剪版本。

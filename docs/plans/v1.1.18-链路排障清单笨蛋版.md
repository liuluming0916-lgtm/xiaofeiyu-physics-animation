## 0. 先看懂：这道“自动出动画”的流水线是怎么跑的

可以把软件想成一条**七道工序的流水线**。你把题目（文字/图片）放进去，最后出来一个能播放的动画网页。

| 工序 | 通俗解释 | 谁来做 |
|---|---|---|
| 1. 读题 | 看图、看题，写一个标题，记下“图里有什么、谁在左谁在右”，并判断用到哪些动画元件/场景 | AI |
| 2. 解题 | 把这道题解一遍，写出过程与结论 | AI |
| 3. 分步讲解 + 物理分析 | 一边把讲解切成“第 1 步、第 2 步…”，一边算出每个物体每一段的运动公式（x(t)、y(t)） | AI，两件事同时做 |
| 4. 画动画 | **只写“怎么画”**：地面、斜面、滑轮、物块、绳…… | AI |
| 5. 本地检查 | 用程序检查动画代码有没有语法错、物体有没有瞬移、时间对不对……（C1–C9） | 本地程序，不调 AI |
| 6. 自愈修复 | 如果第 5 步没过，把“哪里错了 + 上一版画法”发回给 AI，让它重画 | AI，只在没过时跑 |
| 7. 步骤对齐 | 把“第 1 步、第 2 步…”对到动画时间上，点某一步就跳到那一段 | AI |

> 关键变化：v1.1.17 起，**AI 不再写“运动代码”**，只写“画图代码”。
> 运动（物体在什么时刻到哪里）由第 3 步的物理分析表 + 本地程序生成。
> 这样 AI 就不可能把运动写错——这是这次重构最大的好处，但也是下面很多问题的根源：
> **“运动”和“画图”被拆开了，很多旧地方还在按“AI 什么都写”的规矩办事。**

### 0.1 八个“槽位”是什么

最终交给播放器的动画程序，仍然固定是 **8 个盒子（槽位）**：

```
PROBLEM   题目文字
STEPS     分步讲解（只有标题和公式）
ANSWERS   答案（v6 起故意留空）
VIEW      时长、镜头、物体列表
setup     开场准备
stateAt   每一时刻物体的位置
drawFrame 每一帧怎么画
readouts  读数/曲线
```

这次重构后，**`ANSWERS` 是故意空着的**：答案不再塞进动画程序，C7（答案复现检查）也退役了。
空着不是“漏填”，是“这个盒子现在不用了”。

### 0.2 10×6 的“布局纸”与“物理米”

这是最容易把人绕晕的一点：

- **物理米**：题目里的真实长度。比如物块走了 1.2 m、斜面长 3 m。
- **布局纸**：不管题目多大，画面永远是一张 **10 × 6 的纸**。所有东西都按“纸上的格子”来画。
- 同一个物块，在“1 米长的题”和“100 万米长的题”里，画出来**一样大**。

所以动画代码里：

- `state.<key>.cx / cy` 是**纸上的位置**，画图用它（`key` 是 `block_A` 这类语义名；旧的 `e0/e1` 已退役）；
- `state.<key>.x / y` 是**物理米**，只给读数、曲线、检查用；
- **C1 现在不再因为“画图用了 `.x/.y`”直接判失败**：那条旧规则（`physical-coord-in-draw`）
  在 B6 已经删掉了。但 scene_code 的正确写法仍是 `cx/cy`；C1 现在只管“语法 / 接线 / 有没有读不存在的字段”。
- 旧文档里“用 `.x/.y` 就判失败”是 v1.1.18 早期的口径，**已过时**。


### 0.3 知识卡是什么

知识卡就像你给 AI 准备的**小抄**：

- **常驻卡**：每道题都塞给它（动画规范、多段运动规范）；
- **元件卡**：题目里出现“物块/小球/弹簧”这类会动的东西才塞对应的一张；
- **场景卡**：题目里出现“斜面/传送带/滑轮/电路”这类布景才塞对应的一张。

小抄写得好，AI 画得就稳；小抄写的是旧规矩，AI 就会按旧规矩画错。

### 0.4 “门禁”是什么，为什么它会“假绿”

门禁就是**自动检查清单**：每次改完代码，跑 **56 项**检查，全绿才允许打包。
它像飞机起飞前的检查单：油量、襟翼、灯光……一项项打勾。

但这次的问题是：**检查单上的某些项目，检查的是“旧飞机”**。
新飞机换了发动机、换了仪表，检查单却还在按旧仪表打勾——所以“全绿”不等于“新飞机能飞”。

这在软件行业叫 **假绿（false green）**：
> 不是检查报错了，而是**该检查的东西根本没被检查**，所以显示绿色。

## 2. P0 详解：这四条不修，1.1.18 不能算“能用”

### P0-1：答案盒子故意空着，但两个“门卫”还要求八个盒子都填满

**你会看到什么**

- 题目跑完，动画页没有动画，或者页面报：
  `槽位 ANSWERS 缺失或为空（§3.2 审计 2）`
- 点“导出网页”，失败，提示：
  `槽位缺失或为空：ANSWERS（§3.2 要求 8 个都非空）`

**实际发生了什么**

v6 的新流程故意把 `ANSWERS` 留空（答案在“解题过程”和“分步讲解”里，不再塞进动画程序）。
播放器本身、清洗器、运行时都已经改成“`ANSWERS` 可以为空”。

但是还有两个地方没改：

1. **动画页的“门卫”**（`web/src/lib/host-protocol.ts`）——
   它在把程序交给播放器之前，会检查“8 个盒子是不是都不为空”。它仍然把空 `ANSWERS` 当成缺件。
2. **导出页的“门卫”**（`core/export/page.mjs`）——
   它在生成单文件网页之前，也检查“8 个盒子都不为空”，同样把空 `ANSWERS` 当成缺件。

结果就是：**播放器说“可以”，门卫说“不行”**。动画页和导出页各被一个门卫挡住。

**打个比方**

学校换了新表格，第 8 栏“备注”改成“可以不填”。
你已经按新规矩空着了，但教务处两个收表老师还拿着旧规矩，说“8 栏都必须填，空着不收”。
表格本身没问题，是收表的人没换规矩。

**为什么门禁没发现**

- 检查单里“空 `ANSWERS` 能不能播”这一项，只测了**播放器**（模板 HTML），
  没测动画页真正调用的那个“门卫”。
- 导出检查一直用 q01 这道旧样例题，它的 `ANSWERS` 是**有内容**的；
  从来没有用 v6 新生成的“空 `ANSWERS`”去试过导出。

所以门禁绿着，但两个真实入口都过不去。

**修好后的样子**

- 动画页能正常收到 v6 程序，哪怕 `ANSWERS` 是空的；
- 导出网页能成功，不再报“ANSWERS 缺失”；
- 回归测试里会固定加一条：“用 v6 生成物（空 ANSWERS）跑一遍动画页和导出”。

### P0-2：你在设置页改了提示词/规则，但真正跑题时拿的是“旧复印件”

**你会看到什么**

- 你在“设置 → 提示词卡”里把“解题”改成你习惯的写法，保存成功；
- 下一道题跑出来，AI 还是按**原来的**提示词解题；
- 你在“本地规则卡”里加了一条清洗规则，也保存成功，但跑题时完全没生效；
- 奇怪的是，知识卡（新建/停用卡片）却生效了。

**实际发生了什么**

每次开始跑一道题，软件应该做一件事：

> 把当前的“提示词 + 清洗规则 + 知识卡 + 端点配置”**复印一份**，这道题从头到尾只看这份复印件。
> 这样你跑到一半改设置，不会把这道题弄乱；改动从下一题开始生效。

这个“复印件”在代码里叫**规则快照（rules snapshot）**。

问题在于：真正跑题的入口 `/api/run` **没有把这份复印件交给流水线**。
流水线拿不到复印件，就只能用内置的、出厂默认的提示词和规则。
知识卡是另外一条路加载的，所以知识卡生效，提示词和规则不生效。

**打个比方**

你给助教一本**新教案**，让他按新教案上课。
助教嘴上说“收到”，但上课时从抽屉里拿出了**旧教案**——因为教务处没把新教案放进他的文件夹。
你改的是文件夹外面的展示柜，他拿的是文件夹里的旧本子。

**为什么门禁没发现**

门禁里所有“改了提示词会生效”的测试，都是**直接调用流水线，并手动把复印件塞进去**。
它们没有走真实的 `/api/run` 那道门。
规则服务的测试只测了“提示词能存、能读、能恢复默认”，但**没有一次带着规则真的跑一道题**。

所以测试里“改了就生效”，真实软件里“改了不生效”。

**修好后的样子**

- 在设置页改提示词/清洗规则，下一题真的按新内容跑；
- 跑到一半改，不影响正在跑的那道题（这是原本的设计目标）；
- 日志里能看出这道题用的是哪一版规则。

**证据（给程序员）**

- [`tools/rules-service.mjs:514`](../../tools/rules-service.mjs#L514)（config 里没有 `rulesSnapshot`）
- [`core/orchestrator/pipeline.mjs:107`](../../core/orchestrator/pipeline.mjs#L107)（只认 `config.rulesSnapshot`）
- [`tools/rules-service.mjs:747`](../../tools/rules-service.mjs#L747)（`loadRulesWorkspace` 只在 `/api/status` 用了）
- [`tests/prompt-overrides-selftest.mjs:321`](../../tests/prompt-overrides-selftest.mjs#L321)（直接调流水线）

### P0-3：自愈的“修复说明”还在教旧坐标，越修越错

**你会看到什么**

- 第一次画出来有错（比如物体位置不对），软件进入“小肥鱼正在完善…”；
- 修了一轮、两轮、三轮，还是不过；
- 最后要么带警告交付，要么直接失败；
- 有时修完比原来更糟（物体跑到画布角落、比例不对）。

**实际发生了什么**

“自愈”不是让 AI 随便重画，而是把两样东西发给 AI：

1. 上一版 `drawFrame`（画图代码）；
2. 检查报告里“哪里错了”。

但发给 AI 的**修复说明（repair 提示词）**还是旧版写的：

> “位置只从 `state.<key>.x / .y` 读”
> 示例：`Draw.box([state.e0.x, state.e0.y + 0.1], 0.2, 0.2)`

而 v6 的新规矩是：

> `x / y` 是物理米，**不许拿来画**；画图必须用 `cx / cy`（10×6 纸上的位置）。

更糟的是，C1 检查会**硬拦**“画图里出现 `state.*.x / y`”。
所以 AI 照着修复说明写，等于**主动撞到那条硬拦**。
它不是不努力，是说明书给错了。

**打个比方**

学生第一次用旧地图走错了路。你把他叫回来，说“这次按这张新地图走”，
结果递给他的是**同一张旧地图**。他再走一次，还是错；你再说“再走一次”，循环三次。

**为什么门禁没发现**

自愈的测试里，假 AI 在“修复轮”**直接返回了正确的 `cx / cy`**（测试作者手动写对了）。
测试只检查“调用了几次、是不是只改 drawFrame、最后有没有通过”，
**没有检查发给 AI 的修复说明到底写了什么**。

所以测试里的自愈一次就过，真实模型照着旧说明写就过不了。

**修好后的样子**

- 修复说明里只出现 `cx / cy` 和 10×6 布局单位；
- 修复示例不再出现 `state.e0.x / y`、不再写死 `0.2 / 0.2`；
- 画图错误修一轮就能收敛，而不是撞三次墙。

**证据（给程序员）**

- [`core/prompts/repair.mjs:20`](../../core/prompts/repair.mjs#L20)（system）
- [`core/prompts/repair.mjs:32`](../../core/prompts/repair.mjs#L32)（示例）
- [`core/prompts/repair.mjs:55`](../../core/prompts/repair.mjs#L55)（字段映射）
- [`core/dryrun/dry-run.mjs:2388`](../../core/dryrun/dry-run.mjs#L2388)（C1 硬拦）

### P0-4：两张“每道题都发”的常驻知识卡，还在教旧坐标

**你会看到什么**

- 有些题画面明显不对：物块掉到画布角落、地面画在奇怪的位置、比例忽大忽小；
- 自愈时怎么改都改不对；
- 你打开“知识卡”看，卡片内容看起来“挺有道理”，但和软件的新规矩对不上。

**实际发生了什么**

知识卡里有两张**常驻卡**，每道题都会塞给 AI。
它们的正文还是 v1 的写法：

- “位置只从 `state.<key>.x / .y` 读”
- “世界坐标：单位米”
- “长度用题面的米数”
- “阶段边界用固定世界坐标”

而第 4 步“画动画”的正式指令说的是：

- “`cx / cy` 是 10×6 纸上的布局坐标，画东西一律用它”
- “`x / y` 是物理米，只给读数用，不要拿去画”

两张纸同时放在 AI 面前：一张说“用 x/y”，一张说“别用 x/y”。
AI 往往会跟“更具体、更像示例”的那张——也就是常驻卡。
只要它跟了，C1 就硬拦。

**打个比方**

考试时你发了两页说明：
第一页写“本次画图用 10 厘米方格纸，按格子画”；
第二页写“长度一律用米”。
学生如果按第二页画，把 0.4 米的物块画成 0.4 厘米，监考老师（C1）还判他“用了错误坐标”。
这不是学生笨，是两页说明互相打架。

**为什么门禁没发现**

知识卡的门禁只检查了**卡片的代码示例**（`code_examples`）能不能过 C1 静态检查，
**没有检查卡片正文**。
常驻卡没有代码示例，所以正文里的“用 x/y、用米”从来没有被任何检查读过。
而且 C1 静态检查也查不出“正文在教旧规矩”。

**修好后的样子**

- 两张常驻卡重写成 v6 口径：`cx/cy`、布局单位、元件固定布局尺寸；
- 卡正文里不再出现“位置只从 x/y 读”“世界坐标”“长度用题面的米数”；
- 增加一条检查：常驻卡正文出现这些旧措辞就报错。

**证据（给程序员）**

- [`core/knowledgecard/data-v2/92-animation-core.json:10`](../../core/knowledgecard/data-v2/92-animation-core.json#L10)
- 同文件 `:22`（“阶段边界用固定世界坐标”）

## 3. P1 详解：不一定每道题都中，但会稳定拉低成画率 / 增加等待 / 让排障变难

### P1-1：场景卡只改了一半，旧坐标和新坐标混着用

18 张场景卡里：

- **8 张**还写着“按读题几何用固定世界坐标画”“坐标是米”：
  地面、圆弧轨道、滑轮、平行板、光线、透镜、光斑、坐标轴框；
- **2 张**半迁移：斜面、传送带（示例像布局单位，但正文还有旧措辞）；
- **8 张**已经改成“布局”：导轨、电场、磁场、天体轨道、气缸、玻璃管、导线、电表。

**结果**：同样是“画一个地面”，有的卡说“用米”，有的卡说“用布局”。
AI 只能猜。猜小了，汽缸就“偏细”；猜偏了，卡销就对不齐；猜高了，物体就悬空。

**打个比方**

同一本实验手册，前 8 页用“厘米”，后 8 页用“格”，中间 2 页两种混着写。
学生做实验时只能凭感觉，做出来的装置比例当然不稳。

**为什么门禁没发现**：卡片正文不参与检查，只有代码示例参与。

**修法**：把剩下 8 张 + 2 张半迁移统一改成布局单位；在卡校验里加一条“正文不得出现旧坐标措辞”。

### P1-2：只是“小警告”，却被送去重画 3 次

检查分两种：

- **硬拦（blocking）**：不过就不能交付，比如语法错、时间对不上；
- **警告（warning）**：可以交付，但有小毛病，比如画面某处不够稳。

v6 的自愈逻辑里有一个判断：

> 只要结论不是“完全通过”，并且不是“物理错误”，就进入“重画 drawFrame”循环，最多 3 轮。

问题是：**只有警告、没有硬拦**的题，结论是“带警告通过（pass-with-warnings）”，
它也不是“完全通过”，于是也被送去重画 3 次。

我做的确定性测试：让检查只返回一条警告，结果 `drawFrame` 被调用了 **4 次**（首画 + 3 次修复），
`repair_round` 有 **3 轮**。这 3 轮完全是白跑的，还多花 3 次模型调用。

**打个比方**

学生作业只是字写得有点潦草（警告），老师说“可以交”。
但教务系统一看“不是满分”，就自动把作业退回重写 3 次。每次重写还可能把原本对的答案改错。

**为什么门禁没发现**：修复分类的测试只测了“分类函数”，没测“带警告时会不会进循环”。

**修法**：只有“存在硬拦的画图错误”才进重画；只有警告就直接交付，并在界面上保留警告。

### P1-3：`pi` 这个符号，解析器认识，生成代码时不认识

物理里经常写 `2πt`、`sin(πt)`。
你让 AI 写“物理分析表”，它写：

```
x: 2*pi*t
```

解析器说“可以，`pi` 是合法常量”。
但把这张表变成动画程序时，生成器只把大写的 `PI` 换成 `Math.PI`，**小写的 `pi` 忘了换**。
于是生成的代码里留着 `2*pi*tt0`，而 JavaScript 不认识 `pi`。

我做的测试：

- 解析：通过；
- 生成：`x0 = 2*pi*tt0`；
- 本地检查：C1 报“引用未声明的名字 pi”，C2 报“pi is not defined”；
- 自愈：分类成物理错误，重跑两轮 analysis，还是同样的写法，修不掉。

**打个比方**

菜谱上写“加 π 克盐”，厨房的罐子上写的是“PI”。
备菜员（解析器）说“有，就是那罐”，炒菜师傅（生成器）却只认“PI”三个字母，看到“π”就说“没有这个”。
菜当然做不出来。

**为什么门禁没发现**：生成器的测试里没有 `pi` 这个用例；解析器的测试里有，但两边没串起来。

**修法**：生成时把 `pi` 也换成 `Math.PI`；加一条“解析通过 ⇒ 生成代码能跑”的测试。

### P1-4：AI 按“一行一个”写多选，程序只读到第一个，还不报错

读题阶段要 AI 判“这道题用到哪些动画元件、哪些场景”，可以多选。
提示词说“可多选”，模型很可能这样写：

```
【动画元件】
block
ball
【场景】
belt
ground
【判定依据】...
```

但解析器的逻辑是：读到标签后，**只把紧接着的第一行内容收进来**，然后就把“待接收”状态关掉。
于是：

- `elements` 只有 `block`，`ball` 丢了；
- `scenes` 只有 `belt`，`ground` 丢了；
- 而且 `problems` 是空的——**程序不觉得自己漏了，它以为只有这些**。

我做的测试就是这个结果：只解析出 `block` 和 `belt`，`ball` / `ground` 静默消失。

**后果**：该注入的“小球卡”“地面卡”不注入；AI 没看到画法，画出来就缺件或比例不对。
你看到的是“怎么少画了一个东西”，但日志里没有任何“漏判”提示。

**打个比方**

表格上写“可多选”，学生一行写一个答案。
收表老师只看第一行，后面的行当没看见，还在表上盖“已收齐”。
不是学生没写，是收表的人只读了一行。

**为什么门禁没发现**：测试只用了“逗号分隔在一行”的写法（`block, ball`），没测“一行一个”。

**修法**：标签后的连续内容行都收进来，或显式支持 `-` 列表；漏掉的词要出现在 `problems` 里。

### P1-5：物理分析里的“元件类型”写错一个字母，就查不到尺寸，但没人提醒

物理分析表里有一行：

```
type: block
```

这里的 `block` 不是随便写的，它是“元件尺寸表”里的编号。
尺寸表里 `block` 对应“宽 0.4、高 0.3”；`ball` 对应“半径 0.08”。

如果 AI 写成：

```
type: block_A
```

解析器**不检查这个词在不在尺寸表里**，照样通过。
生成 state 时查不到 `block_A` 的尺寸，于是 state 里没有 `w / h`。
但知识卡又告诉 AI：“画物块用 `state.e0.w / state.e0.h`”。
AI 照做，读到的是 `undefined`，画图代码算出 `NaN`，检查报错。

更麻烦的是：这类错误被归类为“物理错误”（C3），自愈会去重跑物理分析，
但模型往往还是写 `block_A`，所以两轮之后还是失败。

**打个比方**

你去仓库领“0.4×0.3 的物块”，单子上写的是“block_A”。
仓库里只有“block”这个货号，管理员不说“没这个货号”，而是给你一个空盒子。
你拿空盒子去装配，装出来当然是坏的；而主管还以为“是装配工的问题”，让他重新装配两次。

**为什么门禁没发现**：解析测试只测“字段格式对不对”，没测“type 在不在尺寸表里”。

**修法**：解析时校验 type；不认识就明确报错，或按 `block` 降级并给警告；不要让它静默变成空尺寸。

### P1-6：`x / y` 到底是“物块中心”还是“物块左下角”，两边理解不一样

物理分析表里写：

```
x: 0
y: 0
```

这句话的意思是“物块在原点”。但“原点”指哪里？

- 如果指**物块中心**：画的时候中心放在 (0,0)；
- 如果指**物块左下角（接触点）**：画的时候中心要往右移半个宽、往上移半个高。

生成器现在按“接触点”处理：`cx = x + w/2`、`cy = y + h/2`。
但 analysis 提示词没有明确说“x/y 是接触点”，模型很可能按“质心/中心”写。
于是物块会整体**向右偏半个身位、向上偏半个身位**。

这不是每道题都明显，但会让“物块和斜面/地面的接触”看起来差一点，
也可能让 C6（边界跳变）或 C4（帧间突变）报一些莫名其妙的警告。

**打个比方**

你说“把椅子放在教室的 (0,0)”，你指的是椅子中心；
搬椅子的人理解成“椅子左下角对齐 (0,0)”，于是整把椅子往右上方挪了半把椅子的距离。
你们说的都是“放在 (0,0)”，但指的参照点不同。

**修法**：在 analysis 提示词里明确“x/y 是接触点/参考点”，或者把生成器改成按质心；两边必须统一。

### P1-7：水银柱卡要“两个液面”，但物理分析根本没让 AI 算这两个数

水银柱卡（`mercury`）的写法是：

```
Draw.polygon([[0, state.e0.yA], ... [0, state.e0.yB], ...])
```

它要求 state 里有 `yA`（液面 A 高度）和 `yB`（液面 B 高度）。
但 analysis 的提示词只要求 `x / y` 两个位置，**没有要求 `yA / yB`**。
解析器虽然“支持” `ya/yb` 这两个可选字段，但 AI 根本不知道要写。

结果：模型命中水银柱卡后，读 `state.e0.yA` 得到 `undefined`，画图算出 `NaN`，检查失败。
自愈也修不了，因为物理分析表里本来就没有这两个数。

**打个比方**

实验报告模板要求填“上液面高度、下液面高度”，但数据记录表只有“液面高度”一栏。
学生只能空着，最后报告算不出来。

**修法**：要么在 analysis 提示词/示例里补 `ya/yb`，要么先把水银柱卡封存，明确“暂不支持”。

### P1-8：程序算出了“物体活动范围”，但没告诉画图 AI

程序会根据物理分析表算出一个“活动范围”：

> 这个物块从纸上的 0.8 走到 9.1；导轨至少要画到 9.1 以外。

这个范围在 `core/stage/frame.mjs` 里算出来了，但**没有传给第 4 步“画动画”的提示词**。
AI 只看到“10×6 的纸”，看不到“物体实际走到哪”。
于是它可能把导轨画到 5、把汽缸画得很细，物体一运动就“跑出容器”。

**打个比方**

你知道火车从 0 公里开到 900 公里，但给绘图员的说明只写“画一条铁路”，没写“要覆盖 0–900 公里”。
绘图员画了 500 公里，火车后半程就开出图了。

**修法**：把 `frame/range` 作为数据写进 scene_code 的 user 消息（只给范围，不写“这题应该怎么画”）。

### P1-9：导出网页的“出处信息”丢了两个指纹

导出的单文件网页顶部有一行“出处信息”：

```
模板 v… · SDK v… · model: … · prompt: … · knowledgecard: …
```

其中 `prompt` 是提示词的指纹，`knowledgecard` 是知识卡的指纹。
有了它们，才能知道“这个动画是用哪一版规则生成的”。

但现在真实运行导出时，这两个值传的是 `undefined`，于是网页上写“未记录”。
其实软件内存里**已经有**这两个值（解题页收到过），只是导出时没带上。

**打个比方**

学生的实验报告封面要写“教材版本、实验手册版本”，
封面印好了，但提交时没填，最后写“未记录”。
不是没有版本，是交的时候忘了抄。

**修法**：导出时把 `run.promptHash` 和 `run.knowledgecard.hash` 带上；确实没有才写“未记录”。

### P1-10：日志还不够“详尽”，出事时像黑匣子少了一半通道

你之前要求：1.1.18 的日志，除 API Key 外尽量详尽。
现在的“开源日志”已经有：题目、模型、每一轮门禁、每次模型对话、8 个槽位、解题过程。
但还缺：

- `analysis`（物理分析）的正文——`SOLUTION_STAGES` 里还是旧的 `answers`；
- 读题判了什么（元件/场景/表外词）；
- 知识卡实际注入了哪几张、多少字；
- 步骤耦合的 `stepTimes/timeMap`；
- `promptHash` / `knowledgecardHash`；
- 槽位名还是旧的 `PARAM / PROBE`，没有 `setup / readouts`；
- 告警横幅对象被 `String()` 成 `[object Object]`。

**打个比方**

飞机黑匣子应该记录高度、速度、航向、发动机参数。
现在只记了高度和对话，速度、航向、发动机没接进来。
飞机没事时看不出差别；一旦出事，调查员拿不到关键通道。

**修法**：把上述事件/哈希/时间映射补进日志的 JSON 与 HTML；槽位名换成 v6 的 8 个。

### P1-11：跑到一半切到设置页，回来按钮变灰、点不动

你在解题页点“开始生成”，然后切到“设置”页看东西。
React 会把解题页卸载，`useRun` 的清理函数只做一件事：**取消网络请求**。
但它没有把“正在运行”这个状态改回“未运行”。

服务端可能已经发了“已取消/已结束”的事件，但解题页已经卸载，没人接收。
你切回解题页，界面仍然以为“还在跑”，于是“开始”按钮是灰的，动画入口也可能点不了。

**打个比方**

你离开厨房时把火关了，但灶台上的“正在加热”灯没复位。
你回来看到灯还亮着，就不敢再按开始键。

**修法**：离开页面时除了取消请求，也把运行状态复位；或者回到页面时检查并恢复。

### P1-12：自愈时程序组装失败，会直接“炸掉”，而且物理修复的错误被静默吞掉

正常主链里，如果模型输出拼不成 8 个槽位，程序会发一条明确的错误：
“模型输出无法切成 8 个槽位”，然后正常结束。

但在**物理修复**和**画图修复**这两条支路里，组装程序的动作没有包在“出错处理”里。
如果修复轮返回空内容/坏内容，程序会直接抛异常，整条流水线以“运行崩溃”结束，
而不是“这一轮修复失败，带警告交付”。

更隐蔽的是：物理修复里调用的子阶段（读题/解题/分析/画图）如果报错，
这些错误事件被收集进一个 `silent` 数组，**没有转发给界面**。
界面只看到最后一条 `run_done(error)`，不知道是哪一步、为什么。

**打个比方**

主路出事故，交警会立牌子“前方事故，绕行”。
支路出事故，没有牌子，直接封路；你在车里只看到“前方无法通行”，不知道发生了什么。

**修法**：修复轮也复用主链的错误处理（`stage_error(dry_run)` + `dryrun_done` + `run_done`）；
子阶段的错误要转发，不能静默收集。

### P1-13：“内置知识层封死”只封了旧仓库，新仓库没封

> **2026-10-24 状态：一半。** v1 卡/提示词已归档、v1 读题退出运行时/编辑器——
> 这部分完成了；但 **v2 卡仍不封死**，打包脚本仍从 v1 `data/` 生成“封死包”，
> 打包检查单还点着旧包的名字。
> **用户裁决：封包要封 v2，但不能影响用户在软件端编辑**——待实现。
> 详见 [`v1.1.18-链路排障进度-笨蛋版.md`](v1.1.18-链路排障进度-笨蛋版.md) §2。

软件打包时，内置知识卡应该“封死”在程序里，用户不能随便改。
现在的“封死”机制（`OD_BUILTIN_BUNDLE`）用的是 **v1 的旧卡**：

- 编译包 `builtin-bundle.generated.mjs` 是从 `core/knowledgecard/data/`（v1，33 条）生成的；
- 真正在跑的 v2 卡在 `core/knowledgecard/data-v2/`（31 张），v2 库**根本不读这个编译包**；
- 门禁的“封死”测试只验了 v1 编译包和 v1 `data/` 一致，没有验 v2。

所以：**旧仓库上了锁，新仓库门开着；检查单还在检查旧仓库的锁。**

**打个比方**

学校搬了新校区，旧校区的门锁好了，新校区的门没锁；
保安检查表上写“旧校区门已锁”，于是打勾。
家长以为“校区都锁好了”，其实新校区是开的。

**修法**：要么让编译包从 `data-v2/` 生成、让 v2 库支持 `OD_BUILTIN_BUNDLE`；
要么明确“v2 不封死”，把旧编译包和旧检查删掉/降级，不能继续误导。

## 5. 为什么一次冒出这么多问题？——不是“谁写错了”，是“搬家后旧地址还在用”

v1.1.17 同时换了四件大事：

| 旧规矩 | 新规矩 |
|---|---|
| AI 写 8 个槽位（包括运动） | AI 只写 `drawFrame`（画图） |
| `ANSWERS` 填答案 | `ANSWERS` 故意空着 |
| 画面用物理米 | 画面用 10×6 布局纸；物理米只给读数 |
| 知识卡 v1（keys/考点） | 知识卡 v2（元件/场景） |

这就像学校同时换了**校区、课表、教材、门禁系统**。
大部分老师已经按新校区上课了，但：

- 两个门卫还拿着旧校区的地图（P0-1）；
- 教务处的“新教案”没送进教室（P0-2）；

所以这不是“某一个人写错了一个字”，而是**一次大搬家后，旧地址没有全部清理**。

## 7. 小抄：以后看到这些词，不用怕

| 词 | 一句话解释 |
|---|---|
| 槽位 | 动画程序的 8 个固定盒子 |
| `ANSWERS` | 答案盒子；v6 起故意空着 |
| `drawFrame` | “每一帧怎么画”的那段代码 |
| `stateAt` | “每一时刻物体在哪”的那段代码，由程序生成 |
| C1–C9 | 本地检查的编号；C1 管语法/坐标/接线，C3 管数值，C5 管时长…… |
| 硬拦 / 警告 | 硬拦 = 不过不能交付；警告 = 可以交，但有小毛病 |
| 自愈 | 检查没过时，把错误发回给 AI 重画 |
| 知识卡 | 给 AI 的小抄；常驻卡每题都发 |
| 提示词 | 给 AI 的“阶段说明书” |
| 规则快照 | 开跑时给这道题复印的一份设置，跑动中不改 |
| 假绿 | 检查显示绿色，但该检查的东西其实没被检查 |
| 布局单位 | 10×6 纸上的格子，不是米 |
| 指纹（hash） | 一小段字符，用来标识“这是哪一版规则/卡片” |

## 0. 一句话结论

**“重构示例题目”最值钱的做法，不是重写那 15 道回归题，而是建一个“示例题库”：**
选 8–10 道真实题目，每题配一份能过 C1–C9 的完整程序；
**1 篇放提示词里当“常驻范例”，1–2 篇按题型条件注入，其余 6–8 篇只做评测、不进提示词。**

这样既真的改变 AI 看到的东西，又不会把提示词预算吃光，还能用同一套题量出“改之前/改之后”的差别。

工作量：**约 16–28 人日（3–5 周，单人）**。
如果只改提示词里那一篇范例，**3–5 人日**；如果只重写 15 道回归题，**8–12 人日，但不直接改变 AI 的输出**。

## 1. 先对齐：代码里的“示例题目”有三种，作用完全不同

| 名字 | 在哪里 | 谁看它 | 作用 |
|---|---|---|---|
| **15 道回归题** | `tests/regression-15/q01…q15.mjs` | 只有机器（门禁、Dry-Run） | 机器自检：改了代码有没有把旧功能弄坏 |
| **“一页范例”** | `core/prompts/golden-example.mjs` | **AI 每次都看** | 告诉 AI“一份合格的 8 槽位程序长什么样” |
| **应用里的演示题** | `web/src/lib/demo-questions.ts`（目前只有 q01） | 老师（界面演示） | 让老师不配模型也能看看效果 |

### 最容易误会的一条

**那 15 道题，AI 一行都没看过。** 它们只是“机器自检样本”。

你自己的交接清单里写得很清楚：

> `tests/regression-15/` 那 15 道题只是“机器自检样本”，**不要当作质量基准**；
> 用户明确说过它们不可信。真正的基准是用户自己的压测题集，等他给。
> —— `交接清单（第9期）.md:177-178`

所以：

- 你如果只是“把 15 道题重写一遍”，AI 的输出**不会变**——因为它根本看不到。
- 你如果改的是 `golden-example.mjs`（一页范例），AI 的输出**立刻会变**——因为它每次都在提示词里。
- 你如果建一套“自己的压测题集”，那才是你交接清单里等的那个“真正的基准”。

## 2. 我的判断：你说的“示例题目”大概率是“用户自己的压测题集”

结合你之前说的“15 道题不可信，真正的基准是我自己的题”，我理解你要的是：

> **用你自己的物理题，建一套“既是教学示例、又是质量基准”的题库。**

这套题库有三个用途，不要混在一起：

| 用途 | 放哪里 | 数量 | 说明 |
|---|---|---|---|
| **常驻范例** | `core/prompts/golden-example.mjs` | 1 篇 | 每道题都看到；只教“形状”，不教具体物理 |
| **条件范例** | 世界书 / 条件段 | 1–2 篇 | 题型相近时才注入；教“这类题怎么组织” |
| **评测集** | `examples/`（新目录） | 6–8 篇 | **不进提示词**；只用来量通过率、错误类型、修复轮次 |

一句话：**提示词里只放 1–2 篇，其余留在评测集**。
不要把所有好题都塞进提示词——预算会爆，注意力会散，而且你会失去“没见过的题”这个尺子。

---

## 3. 为什么不建议“重写 15 道回归题”

| 原因 | 说明 |
|---|---|
| **AI 看不到** | 它们在 `tests/` 里，不在提示词里；重写不会改变输出 |
| **它们是“机器自检”，不是“教学样例”** | 很多题为了覆盖判据写得很复杂（q02 光是几何推导就一屏），不适合当“照抄的范文” |
| **会丢掉回归覆盖** | 这 15 道题各自盯着 C1–C9 的某个角落；重写等于换掉温度计，旧基线全废 |
| **内容工作量很大** | 一道完整 8 槽位题要写题面、解析、步骤、答案、VIEW、setup、stateAt、drawFrame、readouts；还要过 C1–C9。8–12 人日只是“改”，不包含“选得对不对” |

**建议**：15 道回归题先保留不动；新建 `examples/` 作为“教学示例 + 评测集”。两套东西各干各的。

## 4. 推荐方案：一个示例题库，三种用途

### 4.1 目录与单一事实来源

```
examples/
├─ index.json                 # 题目清单：id/title/类型/难度/元件/模式/用途
├─ q-conveyor-basic.mjs       # 8 槽位完整程序（与 regression-15 同形状）
├─ q-incline-block.mjs
├─ q-pulley-system.mjs
├─ ...
└─ README.md                  # 每道题“教什么、为什么选它、常见错误”
```

- 每题一个 `.mjs`，`export default { id, title, mode, tags, slots }`，与 `tests/regression-15` 同形状，复用现有切分/Dry-Run 工具；
- `index.json` 是清单，构建期生成前端要用的 TS（如果要在应用里展示）；
- 提示词只从 `index.json` 里标了 `prompt: "constant"` / `prompt: "conditional"` 的题取；
- 评测脚本读全部题，**不**把内容塞进提示词。

### 4.2 三种用途的具体规则

| 用途 | 取几篇 | 放哪里 | 约束 |
|---|---:|---|---|
| 常驻范例 | 1 | `golden-example.mjs`（固定前缀） | 必须最短、最干净、C1–C9 全绿；只教形状 |
| 条件范例 | 1–2 | 世界书条件段 / `scene_code` 任务段 | 按 `concepts/tags` 命中；只在该题型出现；不能重复常驻范例的形态 |
| 评测集 | 6–8 | 只在 `examples/` | 不进提示词；用来量通过率/错误类型/修复轮次 |

### 4.3 为什么“常驻只放 1 篇”

- 固定前缀**逐字节稳定**，改一次 `promptHash` 就变，所有题的缓存失效（一次性的，但要知道）；
- 一篇完整程序约 3–5k 字；放 3 篇就是 10–15k 字，**每道题都付这个钱**；
- 模型真正需要的是“形状”：8 个槽位、裸赋值 `SIM`、`RETURN`/`context`、`bodies`、`readouts`。一篇足够；
- 物理的差异交给“条件范例”和元件卡。

### 4.4 为什么“条件范例”不超过 2 篇

- 条件段也吃预算（正文 30000 + 示例 10000 的池子）；
- 同一形态反复出现会让模型注意力涣散（这是 `动画代码打回率治理方案.md` 里已经量过的）；
- 2 篇足够覆盖“力学”和“场/电”两大类；波/光/热用元件卡 + 常驻范例即可。

## 5. 选题矩阵：8–10 道怎么选

不要按“我觉得这道题好”选，按**覆盖**选。建议一张表，每行一道题：

| 维度 | 取值 | 目的 |
|---|---|---|
| 大类 | 力学 / 场与电 / 波光热 | 覆盖三类画法 |
| 过程 | 单段 / 多段（2–4 段） | 覆盖 `STEPS` 与 `phases` |
| 模式 | NUMERIC / SYMBOLIC | 覆盖 `value: null` 的符号题 |
| 元件 | 每题 3–6 个官方元件 | 覆盖 30 个元件里的高频项 |
| 图表 | 有 / 无 | 覆盖 `readouts` 与曲线 |
| 难度 | 简单 / 中等 / 较难 | 1 简单 + 2 中等 + 1 较难；不要全是难题 |
| 用途 | 常驻 / 条件 / 评测 | 常驻 1、条件 1–2、评测 6–8 |

推荐的首批覆盖（可按你的题库替换）：

1. 传送带 + 物块（常驻范例；已有 q01，可精简）
2. 斜面 + 物块（条件范例；力学高频）
3. 连接体 / 滑轮（条件范例候选）
4. 碰撞 / 板块相对滑动（多段、C6 边界）
5. 圆周 / 圆弧轨道（几何与切向）
6. 带电粒子在磁场（场与电）
7. 电磁感应 / 导体棒（场与电、多过程）
8. 波形 / 振动（波光热）
9. 折射 / 透镜（光）
10. 气体 / 热学（热）

> 原则：**宁可 8 道覆盖全，不要 20 道都是力学。**

## 6. 一道“合格示例”的标准

每题必须同时满足：

- [ ] 8 个槽位齐全，标记正确；
- [ ] `dryRun` 判定 **pass**（不是 pass-with-warnings）；
- [ ] 不使用 `Draw.raw`；
- [ ] 不写像素量、不写数值答案在画布上；
- [ ] `stateAt` 是 O(1)（解析式或查表，不现场积分）；
- [ ] `SIM.bodies` 声明刚体，不手画 v/a 箭头；
- [ ] `SIM.duration` = STEPS 末步 `t1`；
- [ ] `readouts` 的 key/label 与 `ANSWERS` 对得上；
- [ ] 题面是**真实老师会出的题**，不是玩具；
- [ ] 有“这道题在教什么”的 3–5 条说明；
- [ ] 有“最容易错的地方”的 2–4 条说明；
- [ ] 如果进提示词：长度 ≤ 5k 字，且与常驻范例形态不重复。

## 7. 制作流程（从一道题到一条示例）

1. **你给题**：题面文字（最好有图/答案），以及“这题你最想让 AI 学会什么”。
2. **跑一遍**：用软件正常解题 → 动画 → Dry-Run，拿到候选 8 槽位程序。
3. **过检**：C1–C9 必须 pass；不过就修，修完记录“错在哪、怎么改”（这条以后可以进修复提示词）。
4. **冻结**：把通过的 8 槽位存成 `examples/q-xxx.mjs`，不要每次重新生成。
5. **打标签**：大类/过程/模式/元件/难度/用途（常驻/条件/评测）。
6. **写说明**：教什么、最容易错什么、为什么选它。
7. **进提示词**：只有标了 `prompt` 的 1–3 篇进；其余只进评测。
8. **跑对比**：改提示词前先跑 10–20 道真实题做基线；改完再跑同一批，比通过率/错误类型/修复轮次。

> 第 2–4 步可以用软件本身完成；第 3 步的“修”可能要找代码的人，但记录错误的格式要统一。

## 8. 评测怎么做（否则“调教”没有方向盘）

### 8.1 先建基线，再改

- 用 **10–20 道真实题**（不是 15 道回归题）跑一遍当前版本；
- 记录：`verdict`、每条 C 检查的 pass/warn/fail、修复轮次、常见错误码（如 `arrow-missing-mag`）、人工评分（画面是否合理，1–5 分）。

### 8.2 改完再跑同一批

- 同一批题、同一端点、同一参数；
- 对比：一次通过率、平均修复轮次、每类错误的数量、人工评分；
- 如果只有“感觉好一点”，没有数字，就不算完成。

### 8.3 留出“没见过的题”

- 8–10 道示例里，**至少 3 道不要进提示词**；
- 用它们检验“是不是只学会了照抄例子”；
- 如果进提示词的题很好、没进的题没变，说明示例没有泛化。

### 8.4 观测从哪来

- 现有 `开源日志/<runId>.json` 已经有：门禁哪条拦住、对话、8 槽位代码、解题过程；
- 可以写一个小脚本，把一批 run 的 `verdict` / `checks` / 错误码汇总成 CSV；
- 不建议这一版就做“大屏 KPI”；先把“改前/改后同一批题”的对比跑出来。

## 9. 工作量

| 工作 | 人日 | 说明 |
|---|---:|---|
| 选 8–10 道题 + 写/改 8 槽位 | 8–15 | 可复用现有 15 道里合适的 3–5 道；每题 1–1.5 天 |
| 提示词接入（常驻 1 + 条件 1–2） | 3–5 | 预算、条件注入、`promptHash`、缓存 |
| 评测脚本 + 基线 + 对比 | 3–5 | 读开源日志 / Dry-Run 报告，出汇总 |
| 门禁与文档 | 2–3 | “示例必须过 C1–C9”、示例库清单、README |
| **合计** | **16–28** | 约 3–5 周（单人全职） |

### 如果只做小步

| 做法 | 人日 | 效果 |
|---|---:|---|
| 只改 `golden-example.mjs` | 3–5 | 直接改变 AI；只有一篇，泛化有限 |
| 只重写 15 道回归题 | 8–12 | 机器自检更贴近真实；**AI 输出不变** |
| 只加应用演示题 | 2–3 | 老师看得到更多例子；**AI 输出不变** |
| 建 6 道示例 + 1 常驻 + 1 条件 + 4 评测 | 10–16 | 最小可用的“调教闭环” |

## 10. 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **过拟合示例** | 模型只学会照抄常驻范例 | 留 3 道以上“不进提示词”的题做留出集 |
| **提示词预算爆** | 多篇完整程序把正文/示例池吃光 | 常驻只 1 篇；条件 ≤2 篇；其余只做评测 |
| **`promptHash` 变** | 改常驻范例会让所有题缓存失效一次 | 接受一次性成本；不要频繁改 |
| **示例本身教错** | 没过 C1–C9 的“范文”会教出错误写法 | 每题必须 `dryRun` pass；进提示词前跑 `_golden-probe` |
| **评测噪声** | 模型随机性、端点差异 | 同端点、同参数、同一批题；记录多次结果 |
| **15 道回归题被顺手改坏** | 旧基线失效 | 示例库与回归集分开；回归题不动 |
| **“示例题目”定义不清** | 做错对象，白干 | 先确认你说的到底是哪一类（见 §11） |

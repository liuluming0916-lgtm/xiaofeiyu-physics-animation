## 1. P0 —— 会直接让用户拿不到动画 / 让配置改了不生效

### P0-1 v6 程序的 `ANSWERS` 是空串，但下游两处校验仍按“8 槽全非空”拒绝

**现象**

- live 动画页：`validateProgramPayload()` 直接返回
  `槽位 ANSWERS 缺失或为空（§3.2 审计 2）`，`AnimationPage` 收到后设置 `templateError` 并**不再注入 iframe**。
- 导出网页：`buildExportPage()` 返回
  `export.bad-slots：槽位缺失或为空：ANSWERS（§3.2 要求 8 个都非空）`，整次导出失败。

**证据**

- v6 有意把 `ANSWERS` 置空：`core/analysis/generate.mjs:323-324`（`ANSWERS: ''`）。
- 清洗器/运行时/模板都已放行空 `ANSWERS`：
  - `core/cleaner/marker-split.mjs:192`、`core/cleaner/to-program.mjs:58`
  - `sdk/runtime/animation-runtime.mjs:1454-1457`
  - `template/animation-template.html:1732-1735`
- **两处没跟上**：
  - `web/src/lib/host-protocol.ts:173-183`
  - `core/export/page.mjs:90-96`
- 确定性探针（Node）：
  - `validateProgramPayload({ slots: {...ANSWERS:''}, mode:'BOTH' })` → `槽位 ANSWERS 缺失或为空（§3.2 审计 2）`
  - `buildExportPage({ slots: {...ANSWERS:''}, ... })` → `false export.bad-slots ... ANSWERS`

**为什么门禁没拦住**

- 门禁 ⑳ 只测了**模板 HTML 里的 `applyProgram`**（`tests/host-protocol-selftest.mjs:342-345` 明确测了空 `ANSWERS`），
  没测 React 侧真正调用的 `validateProgramPayload`。
- 门禁 ㉛ 的导出用例一直用 `q01.slots`（`ANSWERS` 非空，`tests/export-selftest.mjs:149` 起），
  没有用 v6 生成物（空 `ANSWERS`）跑过。

**修法方向**

- 两处都改为“只要求 7 个槽位非空；`ANSWERS` 允许空串”，并加 v6 生成物的回归。
- 修完后应有一条“v6 程序能从 live 注入到动画页”和一条“空 ANSWERS 能导出”的断言。

### P0-2 `/api/run` 没有把规则快照传给流水线：提示词卡 / 本地清洗规则在真实运行里不生效

**现象**

用户在设置页改「提示词卡」或「本地规则卡」并保存成功，下一次解题**仍然用内置正文 / 内置清洗规则**。
知识卡会生效（走 v2 库），提示词与清洗规则不会 —— 正是“前后 key 对不上”。

**证据**

- `tools/rules-service.mjs:514-528` 构造 `config` 时只有
  `endpoint / apiKey / regexRules / mode / knowledgecardEntries / knowledgecardVersion / knowledgecardVocab / devMode`，
  **没有 `rulesSnapshot`**。
- `core/orchestrator/pipeline.mjs:107-119`：`promptTexts` 与清洗规则都只从 `config.rulesSnapshot` 取。
- 整个 `rules-service.mjs` 里 `loadRulesWorkspace` 只在 `/api/status` 调用（`:747`），`/api/run` 没调用。
- 因此 `snapshot.rules` 恒为 `{ revision:null, promptTexts:null }`，`getPrompt()` 永远返回内置对象。

**为什么门禁没拦住**

- 门禁 ㉔（提示词编辑器）、㉗（第 6 期总装）、㉘（规则服务）里，
  真正“改动生效”的断言都是**直接调用 `runPipeline` 并手动传 `rulesSnapshot`**（如
  `tests/prompt-overrides-selftest.mjs:321-330`、`tests/phase6-acceptance-selftest.mjs:340`）。
- 门禁 ㉘ 只测了 `/api/prompts`、`/api/cleaning` 的读写，**没有一次带规则跑 `/api/run`**。

**修法方向**

- `handleRun` 在开跑前 `loadRulesWorkspace({ dir })`，把 `loaded.snapshot` 作为 `rulesSnapshot` 传进 `runPipeline`（每题一份，跑动中改只影响下一题）。
- 新增一条真实 HTTP 回归：写覆盖 → POST `/api/run` → 断言发出去的 system 消息里是覆盖正文；清洗规则同理。

### P0-3 自愈修复提示词仍在教 v1 坐标：`state.<key>.x / .y`，与 C1 硬拦直接冲突

**现象**

drawFrame 因画图错误进入自愈后，修复请求的 system 与 user 都告诉模型：

- `core/prompts/repair.mjs:20`：`位置只从 state.<key>.x / .y 读`
- `core/prompts/repair.mjs:55`：`位置用 state.<key>.x / state.<key>.y`
- `core/prompts/repair.mjs:32`：示例 `Draw.box([state.e0.x, state.e0.y + 0.1], 0.2, 0.2)`

而 v6 的 scene_code 已改成布局坐标：

- `core/prompts/scene-code.mjs:22-24`：`cx/cy` 是布局坐标，`x/y` 是物理米“不要拿去画”
- `core/dryrun/dry-run.mjs:2386-2400`：drawFrame 里出现 `state.*.x/y` ⇒ C1 `physical-coord-in-draw` **硬拦**

结果：修复模型照着 repair 提示词写，正好再次触发 C1，3 轮盲改不收敛。

**为什么门禁没拦住**

- `tests/analysis-repair-selftest.mjs` 的假模型在“修复轮”直接返回了正确的 `state.e0.cx / cy`（`:38`），
  只断言“调用 2 次 / 只改 drawFrame / 最终 pass”，**没有检查 repair 请求正文**。

**修法方向**

- repair 的 system + user 映射 + 示例全部改成 `cx / cy` 与 10×6 布局单位；明确“物理米只给读数和 analysis”。
- 回归里捕获 repair 请求，断言包含 `cx/cy`、不包含 `state.e0.x`。

### P0-4 两张常驻 v2 动画规范卡仍是 v1 口径，且**每道题都注入**

**现象**

`core/knowledgecard/data-v2/92-animation-core.json:10`（常驻 `constant:true`）写着：

- “位置只从 `state.<key>.x / .y` 读”
- “世界坐标…单位米”
- “长度用题面的米数”

同一文件的 `:22` 还写“阶段边界用固定世界坐标”。

这两张卡由 `triggerKnowledgecardV2()` 的 `constant:true` 分支无条件注入 `scene_code`，
且注入位置在「本阶段指令」之后（`tests/analysis-pipeline-selftest.mjs:177-178` 还专门断言了顺序）。

**影响**

模型同时看到“用 cx/cy”和“用 x/y”两套指令；只要它跟了常驻卡，就触发 C1 硬拦。
这不是“卡内容不够好”，是**硬判据与常驻指令互相打架**。

**为什么门禁没拦住**

- `tests/knowledgecard-v2-contract-selftest.mjs:229-251` 只把 `code_examples` 过 `lintSlot`；
  `lintSlot` 是 C1 静态检查，**不检查卡片正文**，也不校验“正文是否与 v6 坐标口径一致”。
- 常驻卡没有 `code_examples`，所以正文完全没被任何门禁读过。

**修法方向**

- 两张常驻卡整体重写为 v6 口径：`cx/cy` 布局坐标、元件固定布局尺寸、地面/边界用布局单位。
- 增加一条“卡正文不得出现 `state.<key>.x/.y 读` / ‘世界坐标’ / ‘题面的米数’”的负向断言（至少对常驻卡）。

最终表现为“汽缸偏细 / 卡销对不齐 / 物体悬空”这类画面缺陷。

**修法**：把剩余场景卡统一改成布局单位；示例里的数值按 10×6 纸重标；在卡校验里加“不得出现‘世界坐标/坐标是米’”的检查。

### P1-2 `pass-with-warnings` 也会进 drawFrame 自愈，白跑 3 轮

- `core/orchestrator/pipeline.mjs:1188`：
  `drawAllowed = report.verdict !== 'pass' && classifyRepair(report).mode !== 'physical'`
- `classifyRepair()` 只看 `blocking && status==='fail'`（`core/repair/classify.mjs:37-40`）；
  C4/C6/C8/C9 是 warning（`contracts/spec/frozen-keys.mjs` 的 `CHECK_SEVERITY`），
  所以**只有告警时 `mode === 'none'`**，`drawAllowed` 仍为 true。
- 探针结果（假 dryRun 返回 `pass-with-warnings` + 一条非阻塞 C4）：
  `scene_code` 被调用 **4 次**，`repair_round` **3 轮**，`run_done.rounds=3`。

影响：每道“带告警”的题都多 3 次模型调用；如果模型照着 P0-3/P0-4 的旧坐标改，还可能把本来能看的画面改坏。
**修法**：`drawAllowed` 只在 `classifyRepair(report).mode === 'draw'` 时为 true；`mode==='none'` 直接交付告警。

### P1-3 analysis 接受 `pi`，生成的 stateAt 却留下裸 `pi` ⇒ C1/C2 确定性失败

- 解析器白名单：`core/analysis/expr.mjs:42-43` 同时认 `PI` 与 `pi`；
  提示词也写“常量 pi”（`core/prompts/analysis.mjs:70-72`）。
- 生成器只替换大写：`core/analysis/generate.mjs:64` 是 `\bPI\b`，**没有 `pi`**。
- 探针（`x: 2*pi*t`）：解析 `ok`，生成 `x0 = 2*pi*tt0`；Dry-Run `C1 unknown-global: pi`、
  `C2 termination:runtime: pi is not defined`，随后进入物理修复（2 轮）也修不掉。

**修法**：`toJsExpr` 同时替换 `pi`（保持大小写），并在 `tests/analysis-generate-selftest.mjs` 加一条“解析通过 ⇒ stateAt 能跑”的断言。

### P1-4 `parseJudgementV2` 遇到“标签下一行开始的多行列表”只收第一项，且不报错

- `core/knowledgecard/v2/prompt.mjs:83-88`：第一行非空内容吸收后就把 `pending` 置空。
- 探针：
  ```
  【动画元件】
  block
  ball
  【场景】
  belt
  ground
  ```
  结果 `elements=['block']`、`scenes=['belt']`、`problems=[]`；`ball`/`ground` **静默丢失**。
- 提示词又要求“可多选”（`core/prompts/templates.mjs:306-313`），模型按列表写很常见。

**修法**：标签后的连续非字段行都并入当前段（或显式支持 `-` 列表）；丢失的词必须在 `problems` 里可见。

### P1-5 `analysis.type` 不校验词表/几何表；未知 type 生成不出 `w/h/r`，但卡仍教模型读 `.w/.h`

- `core/analysis/parse.mjs:206-208` 只限制长度，不校验是否属于元件几何表。
- `core/analysis/geometry.mjs:56-58` 未知 type 回退 `UNKNOWN`（无 `w/h/r`）。
- 生成器 `core/analysis/generate.mjs:228-236` 只把几何表里有的字段写进 state。
- 探针（`type: block_A`）：解析 `ok`；state 里 `type:"block_A"`，无 `w/h`；
  drawFrame 用卡里的 `state.e0.w` ⇒ C2/C3 失败。
- 更麻烦的是分类：C3 被归为物理错误，重跑 analysis 也修不掉，最后带告警或失败。

**修法**：parse 阶段把 type 与 `contracts/element-geometry-v2.json`（或 v2 词表）对齐；
未知 type 明确报 `element-type-unknown`，或给出可诊断的降级（例如按 `block` 几何 + warning）。

### P1-6 `analysis` 的 `x/y` 到底是“接触点”还是“质心”没有定义，生成器却按接触点加偏移

- `core/prompts/analysis.mjs:58` 只说“以核心运动起点或题目自然原点为 (0,0)”，没定义 x/y 指向物体哪个点。
- `core/analysis/generate.mjs:223-225` 用 `centerOffset(type)` 把 x/y 当接触/参考点，再加 `w/2,h/2`（block 是 bottom）。
- 元件卡却写 `state.<key>.x/.y` 是“物理接触点”（`93-elements.json:10` 等）。

如果 analysis 把 x 当质心（模型通常会），生成出的 `cx` 会整体右移 `w/2`、上移 `h/2`。
这是“前后 key 语义对不上”的另一类，不是拼写错误。

**修法**：在 analysis 提示词里明确“x/y 是接触/参考点（bottom-left 或 bottom-center）”，或把生成器改成按质心；
两边选一个并在 C1 里加语义断言。

### P1-7 水银柱卡要求 `yA/yB`，analysis 提示词却不产出 `yA/yB`

- 卡：`core/knowledgecard/data-v2/93-elements.json:452` 明确“`yA` 与 `yB` … 由 analysis 分别算出”，示例直接读 `state.e0.yA/yB`。
- 解析器确实支持 `ya/yb` 可选字段（`core/analysis/parse.mjs:289-307`），
  但 analysis 提示词没有要求输出 `ya/yb`（`core/prompts/analysis.mjs` 全文没有）。
- 结果是：模型命中 `mercury` 卡后，拿不到 yA/yB ⇒ undefined/NaN ⇒ C2/C3；重跑 analysis 也不会补。

**修法**：要么在 analysis 提示词与示例里补 `ya/yb`，要么先把 `mercury` 卡封存并说明“暂不支持”。

### P1-8 `layoutRange()` 算了但没人用：scene_code 拿不到运动元件的活动范围

- `core/stage/frame.mjs:103-121` 计算 `range`（导轨/地面该比它更宽）。
- `core/prompts/scene-code.mjs:53` 的 JSDoc 声明了 `stage`，但实现 `buildSceneCodeUser` 的解构里没有它，
  也没有任何地方读取 `stage.frame/range`。
- `core/orchestrator/pipeline.mjs:381-386` 的 `stageInputs.scene_code` 也没有传 `stage`/`range`。

于是模型只能凭 10×6 纸和题面猜“导轨要画多长”，q06/q09 的“汽缸偏细/卡销对不齐”与此同源。

**修法**：把 `stageOfAnalysis()` 的 `frame/range` 写进 scene_code 的 user 消息（只给数据，不加单题意见）。

### P1-9 导出页 Provenance 丢了 promptHash / knowledgecardHash

- `web/src/pages/AnimationPage.tsx:374-375`：
  只有演示源（`handwritten`）才写哈希，真实运行传 `undefined`。
- `core/export/page.mjs:154-180` 因此把 `prompt` / `knowledgecard` 写成“未记录”。
- 但 store 里其实有 `run.promptHash` 与 `run.knowledgecard.hash`（`web/src/state/store.ts` 的事件处理已存）。

**修法**：导出时把这两个真实值带上；只有确实缺值才写“未记录”。

### P1-10 开源日志还不够“详尽”，且仍带 v1 槽位名

- `core/observability/open-log.mjs:72`：`SOLUTION_STAGES = ['read_problem','solve','breakdown','answers']`，
  v6 的 `analysis` 不在里面，日志的“解题过程”段会漏 analysis。
- `:457`：`slotNames` 仍是 `PARAM / PROBE`，没有 `setup / readouts`（虽然会按实际键追加，但顺序与命名仍是旧的）。
- 日志没有记录 `judgement_done`、`knowledgecard_done`、`coupling_done`、`diagram_done`、
  `promptHash` / `knowledgecardHash`，也没有 `displayTiming`。
- `:300`：`banner: clampText(String(runDone.banner))` 对对象会变成 `[object Object]`。

这正是 v1.1.18 “除 API Key 外尽量详尽”的待办；建议把上述事件/哈希/时间映射补进 record 与 HTML。

### P1-11 `useRun` 卸载只 cancel、不复位 running：切到设置页/重新挂载后按钮永久禁用

- `web/src/hooks/useRun.ts:24-28`：cleanup 只 `handleRef.current?.cancel()`，没有 `failRun` 或 `startRun` 复位。
- 服务端即使随后发 `cancelled`/`run_done`，组件已卸载，没有消费者写 store。
- 回来后 `run.running` 仍是 true；`App` 的动画入口与解题页按钮都可能被禁用。

**修法**：cleanup 里调用 `failRun('已离开页面，运行已取消')` 或把 `running` 复位为 false；补一条 UI 回归。

### P1-12 修复轮的程序组装失败会抛出流水线；物理修复的阶段错误被静默吞掉

- 物理修复：`core/orchestrator/pipeline.mjs:1145-1155`，`scene_code` 返回空串时
  `generateProgramSlots`/`buildProgramFromText` 抛 `ProgramBuildError`，没有 try/catch。
- draw 修复：`:1240-1250` 同样没有 catch。
- 物理修复用 `enq = (ev) => silent.push(ev)`（`:1099`），`executeStage` 产生的 `stage_error`
  全被丢进 `silent`；`:1102-1143` 只发 `run_done(error)`，没有 `stage_error`，前端看不到原因。
- 结果：一条本可走“带告警交付”的题，可能直接以 `run.crashed` 结束，且错误阶段被写成 `solve`。

**修法**：修复轮的组装失败复用主链 `ProgramBuildError` 分支（`stage_error(dry_run)` + `dryrun_done` + `run_done`）；
`enq` 改为把阶段错误转发给前端，而不是静默收集。

### P1-13 “内置知识层封死”只封了 v1，v2 库没封；编译包仍是 v1 数据

- `tools/build-builtin-bundle.mjs:27` 的 `BUILTIN_DIR` 仍是 `core/knowledgecard/data`（v1），
  `:53` 写 `generatedFrom: 'core/knowledgecard/data'`。
- `core/knowledgecard/builtin-bundle.generated.mjs:6` 里的 `BUILTIN_BUNDLE` 就是 v1 的 33 条卡（3 常驻 + 30 元件/场景，带 `keys` / `insertion_slot`），
  与当前 `data-v2/` 不是同一份。
- v2 库 `core/knowledgecard/v2/store.mjs` 不读 `OD_BUILTIN_BUNDLE`，只读 `data-v2/*.json`；
  所以打包版实际没“封死”v2，而门禁 ㊴ 只验 v1 编译包与 v1 `data/` 一致。
- `tools/pack-payload.mjs` 的 `MUST_HAVE` 仍点名 v1 编译包，没有断言 `core/knowledgecard/data-v2/93-elements.json` 在载荷里。

**修法**：要么把编译包改成从 `data-v2/` 生成并让 v2 store 支持 `OD_BUILTIN_BUNDLE`，
要么明确“v2 不封死”，删掉/降级旧编译包与 ㊴ 的误导性断言。二者选一，不能继续“绿着但封的是旧层”。

## 0. 一句话

主链是 **v6**：`read_problem → solve → breakdown ∥ analysis → couple → scene_code → dry_run → repair`。
模型调用 6 次（read_problem / solve / breakdown / analysis / couple / scene_code），dry_run 与 repair 是本地/条件阶段。
**知识卡只注入 `scene_code`（主链的 repair 复用同一槽）；图片在不同阶段不是同一张；用户补充信息只进了三个阶段。**

---

## 1. 实际调用顺序

```text
read_problem
  → solve
  → breakdown ∥ analysis        （真正并发；都只依赖 solve）
  → couple                     （只吃 analysis + breakdown 步骤；跑在画图之前）
  → scene_code                 （只写 drawFrame）
  → dry_run                    （C1–C9 + Worker）
  → repair                     （未通过才跑；画图错误只重画，物理错误重跑主链）
```

> ⚠ 事件里的 `stage_start.total` 不一致：模型阶段取 `promptIds.length`（5），
> `couple` / `dry_run` / `repair` 取 `PHASE5_STAGES.length`（8）。
> 这是已知的进度条口径问题（P2-3），不是模型链路错误。

## 2. 逐阶段 I/O 表

### 2.1 `read_problem`（模型，第 0 步）

| 项 | 内容 |
|---|---|
| 输入文本 | 题面 `problem.text`、`description`、`knownConditions`、判定词表 |
| 输入图片 | **原题图**（全部） |
| 注入 | 固定前缀：`read_problem_v2` 角色 + 输出纪律（**无骨架/无 SDK**）；条件段：本阶段指令 + **无知识卡** |
| 输出 | 读题正文（标题 / 几何 / 示意图范围 / 动画元件 / 场景 / 判定依据） |
| 去向 | ① 标题 → `run_label`、`PROBLEM` 兜底；② 几何 → `analysis`、`scene_code`、`repair`；③ 判定 → 卡片触发；④ 示意图框 → 裁图 |
| 失败 | 视觉门控（不支持看图且有图）直接停；模型错误 `stage_error` |

### 2.2 `solve`（模型）

| 项 | 内容 |
|---|---|
| 输入文本 | 题面、`description`、`knownConditions`、参考答案（`reference.text`） |
| 输入图片 | **原题图 + 参考答案图片** |
| 注入 | 固定前缀：`solve` 角色；条件段：本阶段指令（有参考解析时换 `systemWithReference`）+ **无知识卡** |
| 输出 | 解题过程（有参考解析时是“按解析整理”，不是重算） |
| 去向 | `breakdown`、`analysis`；`run_done.solution.solve` 日志 |
| 失败 | 参考解析与题目不一致 ⇒ `stage_error(reference.mismatch)`，**停在 solve 之后** |

> 注意：`solve` **不拿 `read_problem` 的几何**。图题只能靠原图 + 用户补充描述；这是 q04 读图不稳的一个结构性原因。

### 2.3 `breakdown`（模型，与 analysis 并发）

| 项 | 内容 |
|---|---|
| 输入文本 | 题面、`solve` 全文 |
| 输入图片 | **无** |
| 注入 | 固定前缀：`breakdown` 角色；条件段：本阶段指令 + **无知识卡** |
| 输出 | 步骤表（`title / tex`，**不带时间**） |
| 去向 | `couple` 的步骤输入；`STEPS` 槽位；`scene_code` 的 `steps`（仅当 couple 通过校验） |
| 失败 | 与 analysis 并发；任一方失败 ⇒ 整题 `run_done(error)` |

> 缺口：`breakdown` **不拿 `read_problem` 几何、也不拿补充描述**。讲解若需要“谁在左/右、斜面朝哪”，只能从 solve 猜。

### 2.4 `analysis`（模型，与 breakdown 并发）

| 项 | 内容 |
|---|---|
| 输入文本 | 题面、`solve` 全文、`read_problem` 几何、`description`、`knownConditions`、**参考答案原文**（有则给）、只读 `physical` 尺寸表 |
| 输入图片 | **原题图**（全部） |
| 注入 | 固定前缀：`analysis` 角色；条件段：本阶段指令 + **无知识卡** |
| 输出 | `assumption`（可选）+ `=== 元件运动表 (MOTIONS) ===`（逐元件、逐段 `x(t)/y(t)`） |
| 去向 | ① 解析成 `analysisParsed`；② 生成 `stateAt / VIEW / setup / readouts`；③ 格式化后给 `couple`、`scene_code`、`repair`；④ `run_done.analysisText` |
| 失败 | `analysis.invalid` ⇒ **立即停**，不进 couple/scene_code；没有重试（物理修复在程序生成之后才可能发生） |

> 关键口径（2026-10-24 起）：`analysis` 的 `x/y` 是**质心**（米）；
> 数值权威顺序写进指令：**参考答案 > 解题过程 > 题图**，数值照抄、不从题图重读。
> 现状：`analysis` 拿原题图 + 参考原文；`scene_code` 拿的是裁图，两者看到的图不同。

### 2.5 `couple`（模型，跑在 scene_code 之前）

| 项 | 内容 |
|---|---|
| 输入文本 | 题面、`analysis` 全文、`breakdown` 步骤、`T_phys`、上一次不合法反馈 |
| 输入图片 | **无** |
| 注入 | 固定前缀：`couple` 角色；条件段：本阶段指令 + **无知识卡** |
| 输出 | `step / sub / t0 / t1` 行式表 |
| 去向 | ① `stepTimes` / `displayStepTimes` / `timeMap` / `displayDuration`；② `run_done`；③ `scene_code` 的 `steps`（仅通过校验时） |
| 失败 | 重试 1 次；仍失败 ⇒ **均分兜底**，但兜底表**不喂给 scene_code** |

> 设计：couple 不吃 `read_problem`、不吃 `solve`、不吃补充描述。它只做“步骤 ↔ 物理时间”的对齐。

### 2.6 `scene_code`（模型，只写 `drawFrame`）—— **优化中**

| 项 | 内容 |
|---|---|
| 输入文本 | 题面、`analysis` 全文、`read_problem` 几何、`stateMap`（id→key）、`steps`（仅 stepTimes 通过时）、`t0States`（t=0 布局坐标） |
| 输入图片 | **裁出的示意图**（PNG 裁剪成功）或**整幅原题图**（裁剪失败/JPEG）；纯文字题无图 |
| 注入 | 固定前缀：`scene_code` 角色 + **SDK 签名摘要**（无骨架）；条件段：本阶段指令 + **命中的元件/场景卡**（含 2 张常驻规范卡） |
| 输出 | `drawFrame` 函数体 |
| 去向 | `stateAt/VIEW/setup/readouts` 由 analysis 生成；`drawFrame` 进 8 槽位 → dry_run → 动画页/导出 |
| 失败 | C1–C9 未过 ⇒ 分类修复（画图 ≤3 轮 / 物理 ≤2 轮） |

**当前注入的“束缚”清单**（供 §10 讨论，不在本轮改）：

- 10×6 布局纸、布局单位；
- `state.<key>.cx/cy` 位置 + `anchor`（bottom/top/center）；
- `state.x/y` 是物理米，只给读数；
- 尺寸/构图由模型定；
- 7 条规则（位置只从 state 读、只调 `Draw.*`、不写字、不画 v/a、静止件摆放、颜色由 category、一屏画完）；
- 5 层 user 注入（题面 / analysis / steps / stateMap / t0States / 读题几何）。

### 2.7 `dry_run`（本地）

| 项 | 内容 |
|---|---|
| 输入 | 8 槽位程序、`meta`（BOTH / tPhys / boundaries） |
| 输出 | `verdict`、`checks`（C1–C9 + 扩展）、`diagnostics`、`program`、`labelAvoid` |
| 去向 | `repair` 分类、`run_done`、`dryrun_done`、导出/动画页 |
| 失败 | 阻塞失败 ⇒ repair；仅告警 ⇒ 直接交付（不空转 3 轮） |

### 2.8 `repair`（模型，条件阶段）

| 模式 | 输入 | 输出 | 去向 |
|---|---|---|---|
| 画图修复 | 题面、`analysis`、`read_problem`、`stateMap`、失败项、上一轮 `drawFrame`；图 = 裁图/整图 | 新 `drawFrame` | 重新组装 → dry_run |
| 物理修复 | 题面/补充描述/参考（solve 用）、`read_problem`、`solve`、`breakdown ∥ analysis`、`scene_code` 全重跑 | 全新 8 槽位 | 重新组装 → dry_run |

> 画图修复复用 `scene_code` 的知识卡槽；`repair` 自身**不拿 `description`**（缺口，见 §8）。
> 物理修复会重跑 `read_problem` 与 `solve`，所以补充描述会重新进入（因为 solve 现在收它）。

### 2.9 `manual-draw`（`startAt=draw`，手动“只重画”）

| 项 | 内容 |
|---|---|
| 输入 | 上一版 8 槽位、`analysisText`、`readProblem`、`stateMap`、失败项、上一轮 drawFrame |
| 输入图片 | **无** |
| 注入 | `repair` 提示词；**知识卡段为空** |
| 输出 | 新 `drawFrame`，最多 3 轮 |
| 去向 | 重新组装 → dry_run → `run_done` |

> 缺口：手动重画**看不到示意图、看不到卡片**。与主链的 scene_code 不是同一套输入（见 §8）。

## 4. 注入层（所有阶段共用）

| 层 | 内容 | 是否含题目信息 |
|---|---|---|
| 固定前缀 | 阶段角色 + 输出纪律；`scene_code`/`repair` 额外带 **SDK 签名摘要** | **不含**（跨题逐字节稳定） |
| 条件段 | `【本阶段指令：…】` + `【世界书·…】`（仅 scene_code） | 指令固定；卡片随题命中 |
| 任务段 | `buildUser()` 拼的题面/前序产物 + 图片（单独编码进 user） | 含 |

- `promptHash` 只覆盖固定前缀 + 模板/SDK 版本；**不含** user、卡片、图片。
- `knowledgecardHash` 覆盖卡片集合；与 `promptHash` 分开。
- 日志（open-log）记录**每次模型调用的 messages 原文**（system + user；图片只留张数/长度），所以“注入了什么”可从日志逐字复核。

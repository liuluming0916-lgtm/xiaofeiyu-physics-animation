## 0. 一句话结论

**这不是“加一个页面 + 调一次模型”的活，而是三个子系统：**

1. **让发布版真的能写卡、存卡**（现在其实存不了，见 §1.1）；
2. **让卡片能“试画”**（卡片是提示词知识，不是可执行组件，预览要另搭一条受控链路）；
3. **让远程卡片能安全地浏览、安装、更新、发布**（未审核的提示词 + 不可信代码 + 国内网络）。

按本项目现有的门禁标准（每个功能要有取证、发布构建验证、负例），**完整 v1.2 约 38–56 人日（最可能 45 左右），单人全职约 8–11 周**；如果业余做，按每周 2–3 个有效工作日折算，日历时间要翻倍。

**建议不要一口气做“大 v1.2”**，而是同一个版本号下拆三个可独立验收的里程碑：

| 里程碑 | 内容 | 累计人日 | 累计日历（单人全职） |
|---|---|---:|---:|
| **M1 写卡 + 预览** | 手动写卡、校验、试画、保存、导入导出 | 18–26 | 4–5 周 |
| **M2 + AI 帮写** | 自然语言起草、自动修复、人工确认 | 26–38 | 6–8 周 |
| **M3 + 卡片仓库** | 浏览、详情、安装、更新、投稿、镜像 | 38–56 | 9–11 周 |

M1 结束就已经“能用”了；M2/M3 是在同一个闭环上叠加，不需要推倒重来。

## 0.1 大白话版：这些“卡”到底是什么

把软件想象成一个**会画物理动画的学生**。它画之前，会先翻一叠“小抄”。这些“小抄”就是卡片。

| 名词 | 大白话 | 现在软件里有没有 |
|---|---|---|
| **元件卡** | 只讲**一个东西怎么画**：传送带长什么样、小球怎么画、箭头怎么画。一张卡只讲一件。 | 有，30 张，一个元件一张 |
| **物理规范** | 讲**这类题必须守什么**：比如“下滑块的加速度要沿斜面分解”。它不教画法，教物理。 | 内置库里现在没有；用户层可以自己写 |
| **场景卡（旧说法）** | 一张卡讲**整道题/整个场景怎么摆**：斜面、滑块、箭头、标注全包。 | 没有；当初就是因为“场景太多写不完”被放弃 |
| **场景卡（路线图里的说法）** | 不包画法，只讲**几个元件之间的关系和顺序**：谁挨着谁、谁先动谁后动。 | 没有；路线图排到 v1.2 之后 |
| **复合卡** | 把好几个元件“打包”成一张卡。 | 没有；我不建议 v1.2 做，容易误伤 |
| **写卡助手** | 一个**工作台**：你写卡、软件帮你检查、右边小黑板试画、满意了存下来。 | 现在只有一个灰色的禁用按钮 |
| **卡片仓库** | 一个**卡片图书馆**：看别人写的卡、看图、点安装。 | 没有 |
| **试画** | 用卡片里的示例代码，搭一个**很小的假题**跑一下，给你看几张快照。它不是整道题的动画。 | 没有；这次要做 |
| **门禁** | 发版前自动跑的一堆检查。 | 有 40 多套；这次要加 5 套 |
| **落盘** | 真的写进硬盘，关掉软件还在。 | 发布版现在缺这一步 |
| **沙箱** | 一个隔离的“练习房”，代码在里面跑，坏了不影响主程序。 | 有；但它防的是“写错的代码”，不是“故意搞破坏的代码” |
| **人日** | 一个人干一天。 | — |

> **三个最容易混的词：**
> - **词条 = 卡片**。代码里叫 `worldbook entry`，界面上叫“卡片”，是同一个东西。
> - **元件 = 画面里的一个对象**（物块、传送带、箭头）；**元件卡 = 教 AI 怎么画这个对象的一张说明**。
> - `category: scene_modeling` 是“这张卡进动画槽”的分类名，**不是场景卡**。

### 关于“场景卡”，我的理解

- 你在 Gemini 对话里说的“场景卡片”，是**一张卡包一整个场景**（斜面 + 滑块 + 箭头全教）。你后来说“这要写茫茫多的场景”，所以改成“元件卡片”。这个理解我完全同意，v1.2 **不回到“一场景一卡”**。
- 路线图里还留着另一个更窄的“场景卡”：它**不教画法**，只教“几个元件怎么摆、什么顺序”（比如“斜面题里，块要贴着斜面；先画地面再画斜面”）。它不是“一场景一卡”，更像“关系小抄”。这个我也建议 **v1.2 不做**，先把元件卡和仓库跑顺。
- 所以：**v1.2 只做元件卡**；场景卡（两种含义都算）不在本期。你要是想的就是“元件卡”，那我们就对齐了。

> ⚠ 代码里有个字段叫 `category: scene_modeling`，中文容易被翻成“场景建模”。它只是“这张卡进动画槽”的分类名，**不是**“场景卡”。30 张元件卡全都是这个分类。这个名称很容易误会，下面统一叫“动画卡分类”。

### 这次 v1.2 到底给你什么

1. **一个能用的工作台**：新建一张元件卡 → 填“什么时候用 / 怎么画 / 最容易错什么” → 点检查 → 右边试画 → 保存 → 下次跑题真的会用它。
2. **一个 AI 帮手**：你说“我想要一个圆润的黄色小球，半径 0.1 米，有高光”，它写草稿；软件检查不过就自动改；你满意才保存。
3. **一个卡片仓库**：看别人写的卡，有图有说明，点安装；也可以把自己的卡打包发出去。

## 1. 现状核查：决定工期的三件事

### 1.1 发布版现在其实**不能保存词条**（这是第一块要补的地基）

代码事实：

- 设置页的词条编辑器只改内存，没有调用任何 `/api/worldbook`：
  `web/src/pages/SettingsPage.tsx` 里没有 `fetch` / `rules-api` / `saveWorldbookPack`。
- 设置页顶部自己写着“要真正写回 `ai-rules/worldbook/`，请去『规则』页”：
  `web/src/pages/SettingsPage.tsx:207`。
- 规则页在发布构建里被摇掉：
  `web/src/App.tsx:170` 的 `!RELEASE && page === 'rules'`。
- 构建期快照文件自己写着“落盘这一步是缺的——不谎报”：
  `web/src/lib/worldbook-demo.ts:9-14`。
- 但发布门禁却断言“设置页在发布包里 = 词条编辑对用户开放”：
  `tests/release-switch-selftest.mjs:155-159`。

**结论**：v1.1.2 的“词条编辑对用户开放”目前只开放了“看和改内存”，没有开放“存”。v1.2 的第一件事不是写 AI，而是把**写卡 → 校验 → 落盘 → 重启后还在**这条链路真正接到发布版。否则“写卡助手”没有落点。

> 建议先在你手上的 v1.1.7 安装包里核实一次：改一条卡、点保存、重启，看 `%APPDATA%\physics-animation-studio\data\ai-rules\worldbook\` 里有没有文件。如果没有，这个洞就是实锤。

### 1.2 卡片是“提示词知识”，不是“可执行组件”

现在的“元件卡”是 `worldbook` 词条（`core/worldbook/store.mjs` 的 §9.1 字段）：

- `content`：给模型看的正文（判据 / 状态与画法 / 最常错 / 生成后自检）；
- `code_examples`：给模型照抄的代码片段；
- `elements`：这张卡对应哪个官方元件 id；
- 运行时**不会**把卡片当成一个组件去渲染。

30 张元件卡（`core/worldbook/data/93-elements.json`）的 `code_examples` **只有 `drawFrame`**，没有 `stateAt`：

```
drawFrame: `
  Draw.box([state.x, 0.15], 0.4, 0.3);
`
```

而“试画”至少需要 `stateAt` + `drawFrame` 两段，否则 `state.x` 是 `undefined`，C3 直接判 NaN。

**结论**：预览不是“把卡里的代码跑一下”这么简单，需要：

1. 给卡片补一个**可执行的示例状态**（`stateAt`）；
2. 把卡片示例装进一份**合法的 8 槽位程序**（复用 `tools/build-animation-cards.mjs:568` 的 `verifyElement()` 已经在做的事）；
3. 走 **Dry-Run Worker** 跑一遍，拿回绘制命令；
4. 在画布上回放命令（不是在前端 `eval` 卡片代码）。

### 1.3 远程卡片不是“拉个 JSON 列表”那么简单

三个硬问题：

- **不可信代码**：`core/dryrun/vm-context.mjs:8-10` 明确写着“这不是安全边界（防范的是有 bug 的代码，不是恶意代码）”。把下载来的卡片代码直接丢进现有 Dry-Run 试画，等于把“防 bug”的沙箱当成“防恶意”的沙箱用——**不能这么干**。
- **不可信提示词**：卡片的 `content` 会进模型上下文。一张恶意卡可以写“忽略以上要求”，诱导模型产出坏代码。Dry-Run 能兜住“坏代码”，兜不住“教错物理”。
- **国内网络**：`raw.githubusercontent.com` 不稳定；jsDelivr / Gitee 镜像各有可用性问题；不能假设“拉一次就一定成功”。

**结论**：仓库端要同时做**信任分层、静态校验、哈希、大小上限、缓存、多源回退、撤销名单**；不能照搬 Gemini 的“网页里点一下 Install 就装进本地”那么轻。

## 2. 范围与边界

### 2.1 本期做（v1.2）

**A. 写卡助手（本地）**

- 手动新建 / 编辑 / 复制 / 删除 / 导入 / 导出**元件卡**；
- 字段校验 + 触发词试触发 + 示例代码 C1 检查；
- **试画**：把 `stateAt` / `drawFrame` 装进一份 8 槽位示例程序，Worker 跑一遍，画布回放；
- **AI 起草**：自然语言描述 → 结构化草稿 → 校验 → 错误回传修复（最多 2 轮）→ 人工确认 → 保存；
- 写卡日志（失败可复盘，延续 v1.1.7 的口径）。

**B. 卡片仓库（远程）**

- 应用内浏览卡片名称 / 作者 / 标签 / 简介；
- 详情页：正文、示例代码、作者提供的预览图、试触发；
- 安装 / 更新 / 卸载 / 冲突处理 / 本地修改保护；
- 多源（GitHub raw / jsDelivr / Gitee / 自定义）+ 缓存 + 离线可看；
- 撤销名单（revoked）。

**C. 发布（半自动）**

- 发布前检查；
- 生成投稿文件夹：`card.json` + `manifest-entry.json` + `preview.png` + 说明；
- 一键复制 manifest 条目 / 打开 GitHub 新建文件页；
- 不做内置账号、不做静默上传。

**D. 仓库模板与 CI**

- registry schema、示例卡、PR 模板、GitHub Actions 校验、许可证说明。

### 2.2 本期不做（明确写出来，防止范围失控）

| 不做 | 原因 |
|---|---|
| **复合卡 / 拼接卡**（一张卡画“斜面 + 块 + 箭头”） | 引擎按 `elements ∩ 模型元件` 命中，一张卡声明多个元件会**误命中**；现有文档也明确“一张卡一个元件”（`docs/改词条与导入导出.md:76`）。真要做，需要新命中规则 + 新预览策略，单开 v1.3。 |
| **场景卡** | ROADMAP 已排到 v1.2 之后；它管“关系与顺序”，和元件卡是两层，不能混。 |
| **内嵌浏览器 / 社区站点 / 广告** | 远程 UI 不受你控制、引入登录/Cookie/隐私/广告合规问题；应用是本地优先、无账号的。要看社区，用系统浏览器打开即可。 |
| **自动更新 / 静默安装** | 卡片会改世界书；必须人工确认、先备份、可回滚。 |
| **云同步 / 账号体系** | v1.2 不做；卡片仓库是静态 JSON，不需要账号。 |
| **改 C1–C9 判据** | 判据是信誉所在；本期只在外面加“卡片级校验”，不动判据本身。 |
| **直接 GitHub OAuth 发布**（可选项） | 见 §4.6；建议放到 v1.2.1/v1.3，先做无 token 的投稿包。 |

### 2.3 两个必须对用户说清的预期

1. **试画通过 ≠ 这张卡在真题里一定画对**。试画只证明“这张卡的示例能画出东西、不违反 C1”；它不证明“模型看了这张卡就会用”。真正的验收仍然是拿一道题跑一遍。
2. **AI 产出必须人工确认**。不自动保存、不自动发布；AI 只是把“写初稿”从 20 分钟降到 2 分钟。

## 3. 总体架构

```
┌─────────────────────────────────────────────────────────────┐
│ 渲染进程（React，发布版也包含）                              │
│  写卡助手页：我的卡片 / 卡片仓库 / 编辑器 / 预览 / AI 面板   │
│  · 不直连 GitHub（CORS + 代理 + 不可信内容）                 │
│  · 不执行卡片代码（只回放服务端返回的绘制命令）              │
└──────────────────────────┬──────────────────────────────────┘
                           │ 同源 /api/cards/*
┌──────────────────────────▼──────────────────────────────────┐
│ 本机服务（tools/rules-service.mjs，127.0.0.1）               │
│  core/cards/                                                 │
│   ├─ validate.mjs      卡片级校验（字段 / id / 自检 / 大小） │
│   ├─ preview.mjs       抽示例 → 合成 8 槽 → dryRun → 选帧     │
│   ├─ compose.mjs       结构化草稿 → 词条 content             │
│   ├─ authoring.mjs     提示词生成 + 模型调用 + 修复循环       │
│   ├─ registry.mjs      manifest 解析 / 校验 / 多源 / 缓存     │
│   ├─ install.mjs       安装 / 更新 / 冲突 / 卸载              │
│   └─ publish.mjs       发布检查 + 投稿包                      │
│  复用：core/worldbook/*、core/dryrun/*、core/gateway/*        │
└──────────────────────────┬──────────────────────────────────┘
                           │
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
  ai-rules/worldbook/   data/card-studio/   GitHub / jsDelivr
  （卡片真正落盘处）     （配置/缓存/日志）    / Gitee（只读）
```

**三条硬边界：**

1. **卡片仍然落 `ai-rules/worldbook/*.json`**，不另起一套存储。这样现有世界书引擎、导入导出、备份、跑题注入全部照用。
2. **远程卡片在“浏览”阶段不执行代码**。只做静态校验 + 展示作者提供的预览图；本机作者自己的卡才跑 Dry-Run 试画（见 §4.3 的信任分层）。
3. **前端不解析/执行模型或卡片返回的代码**。预览只回放服务端 Dry-Run 产出的命令记录（纯数据）。

## 4. 功能方案

### 4.1 页面信息架构

导航保留现有的「写卡助手」位置（发布版目前是 disabled 占位，`web/src/App.tsx:80-88`）。

页面内三个页签：

| 页签 | 内容 |
|---|---|
| **我的卡片** | 内置卡（只读）/ 我写的卡 / 已安装的社区卡；搜索、筛选、启用/停用、导入导出 |
| **卡片仓库** | 远程 registry 列表、详情、作者预览图、安装/更新；未配置仓库时显示引导 |
| **写卡** | 新建 / 编辑；左侧表单，右侧试画 + 校验；顶部“让 AI 起草” |

不建议把“写卡”再拆一个顶级导航：卡片相关的动作都在这一页，减少导航项。

> ⚠ 不要用“把规则页整页放进发布版”来省事：规则页还带着 Prompt 编辑器、清洗规则、端点导入导出这些开发工具，且依赖另一个启动入口；给老师会既危险又难懂。写卡助手要自己做一层面向单卡的 UI。

### 4.2 手动写卡

#### 卡片类型

先只做两类，UI 上明确分开：

| 类型 | 槽位 | 有试画 | 说明 |
|---|---|---|---|
| **元件卡** | `scene_code` | ✅ | 一张卡一个官方元件；v1.2 的主角 |
| **物理规范** | `solve` | ❌ | 纯文字知识；手动可写，AI 暂不生成 |

#### 字段与默认值

元件卡新建时直接填好：

```json
{
  "origin": "user",
  "category": "scene_modeling",
  "enabled": true,
  "constant": false,
  "recursive": false,
  "insertion_slot": ["scene_code"],
  "order": 1000,
  "priority": "normal",
  "concepts": [],
  "tags": [],
  "secondary_keys": { "logic": "AND_ANY", "list": [] }
}
```

用户只需要填：

- 标题、元件（从官方 30 个 id 里选）、触发词；
- “什么时候用”“最常错什么”“生成后自检”；
- `stateAt` 示例、`drawFrame` 示例。

`concepts` / `tags` 放在“高级（可选）”里：

- 留空 = 只按元件命中（现有 30 张卡就是这样，`via: element`）；
- 填了考点 = 只有这题确实考这个元件时才注入（`via: element+concept`）。
- UI 必须用一句话解释这个差别，否则老师会以为“填得越多越容易被命中”。

#### ID 规则（先定死，后面省很多事）

- 本地未发布：`local.<slug>`（例：`local.belt-basic`）；
- 发布后：`<github-owner>.<slug>`（例：`liuluming.belt-basic`）；
- 保留前缀：`wb_`（内置）、`ds-`（蒸馏）、`sys.`；
- 正则：`^[a-z0-9][a-z0-9-]{0,31}\.[a-z0-9][a-z0-9-]{2,47}$`，总长 ≤ 64；
- **创建后 id 不可改**；要改就“另存为新卡”。这样文件、仓库、已安装记录不会对不上。

#### 保存容器

- 新建卡默认一卡一文件：`ai-rules/worldbook/<id>.json`；
- 如果编辑的是旧的多卡包（一个文件多条），**保留原文件、只替换那一条**，不要拆包；
- 下载安装的卡固定一卡一文件，方便更新/卸载不误伤同包其他卡；
- 保存走现有 `saveWorldbookPack()`：整批校验 + 原子写 + 备份（`core/worldbook/editor.mjs:92`）。

#### “复制内置卡”的语义要分清

现有 `copyBuiltinEntry()` 生成的是**同 id 覆盖副本**（`core/worldbook/editor.mjs:183`），适合“改内置”。

写卡助手默认应该是**另存为新卡**：

- “基于这张内置卡新建” → 复制内容、换新 id `local.<slug>`、`origin: user`；
- “覆盖内置（高级）” → 保留同 id，明确提示“以后软件升级也不会覆盖你的版本，但你会一直挡住内置更新”。

这个区别不写清，老师会不小心把所有内置卡都覆盖掉。

### 4.3 校验与试画

#### 校验流水线

一次“检查”按顺序跑，任何一步失败都**不静默跳过**：

1. **字段校验**：`validateEntry()`（`core/worldbook/store.mjs:124`）；
2. **id / 类型策略**：保留前缀、内置 id 冲突、`constant`、`origin`、大小；
3. **结构校验**：必须有「生成后自检」小节 + ≥1 段 `code_examples`（`core/worldbook/coverage.mjs:24`）；
4. **示例抽取**：从 `code_examples` 里按 `stateAt:` / `drawFrame:` 提取代码；用与门禁 W17 同一条正则，避免两处漂移；
5. **C1 静态检查**：`lintSlot({ code, slot, entry })`（`core/lint/contract-lint.mjs`）；
6. **Dry-Run**：把示例装进 `BASE_SLOTS`，跑一遍 C1–C9；
7. **画法有效性**：`maxCommandsPerFrame > 0`（一条命令都没画出来 = 画法没生效）；
8. **试画帧**：取 5 帧命令记录返回前端。

#### 合成 8 槽位示例程序

直接复用 `tools/build-animation-cards.mjs:558` 的 `BASE_SLOTS`：

```js
{
  PROBLEM: '（校验占位）',
  STEPS: 'title: s\ntex: x\nt0: 0\nt1: 2',
  ANSWERS: 'symbol: x\nvalue: 1\nunit: m\nat_t: 2\nstep: 1',
  VIEW: 'SIM = { duration: 2 };',
  setup: 'const g = 10;',
  readouts: "return [{ label: 'x', value: 1, unit: 'm' }];",
  stateAt: <卡片示例>,
  drawFrame: <卡片示例>
}
```

这套已经在 `verifyElement()` 里对 30 张内置卡逐张跑过，是**现成的、被证明可用的**预览底座。

> 实现时把 `BASE_SLOTS` / 试画逻辑抽到 `core/cards/preview.mjs`，让 `tools/build-animation-cards.mjs` 反过来 import 它；不要让 `core/` 反向依赖 `tools/`（那是构建脚本，不是运行时依赖）。

#### 30 张内置卡要补 `stateAt`

现在 `93-elements.json` 的 `code_examples` 只有 `drawFrame`。两种做法：

- **推荐**：改 `tools/build-animation-cards.mjs` 的 `buildElementCards()`，把 `state` 和 `draw` 都写进 `code_examples`（`stateAt:` + `drawFrame:`），重新生成 93。
  - 好处：预览有状态；模型也能同时看到“状态怎么给”和“画法怎么写”，正好治“state 键名不一致”这个头号打回点。
  - 代价：要重跑生成器、更新内置 bundle、更新与 hash/内容相关的门禁。
- 不推荐：从 `content` 里的“stateAt 里写：…”反解析。脆、容易和正文漂移。

#### 预览渲染

服务端返回的是**纯数据**：

```json
{
  "ok": true,
  "verdict": "pass",
  "duration": 2,
  "envelope": { "minX": -0.2, "minY": 0, "maxX": 1.2, "maxY": 1.2 },
  "frames": [
    { "t": 0, "records": [ { "op": "box", "cx": 0.6, "cy": 0.15, "w": 0.4, "h": 0.3 } ] }
  ],
  "diagnostics": []
}
```

前端用 `AutoView.fit(envelope, viewport)` + `replayToCanvas(ctx, records, transform, { grid: false })` 回放。

- 需要把 `sdk/runtime/animation-runtime.mjs` 复制一份到 `web/src/lib/`（可以照现有 `worldbook-engine.js` 的“逐字节副本 + 构建期校验”做法），并配一个只声明用到函数的 `.d.ts`；
- 5 帧循环播放（每 400–600ms 一帧），静态卡就显示一帧并标注“静态”；
- 画布不显示文字（现有 `HIDE_CANVAS_TEXT = true`），所以只有文字标注的卡会看起来“空”——UI 要提前说明，否则用户以为坏了。

#### 信任分层（关键安全决策）

| 卡片来源 | 浏览时是否执行代码 | 试画 |
|---|---|---|
| **本机作者自己写/改的卡** | 是（本机代码，和模型生成代码同一信任级） | ✅ Worker Dry-Run |
| **AI 刚生成的草稿（未保存）** | 是（同上） | ✅ Worker Dry-Run |
| **从仓库下载的社区卡** | **否** | ❌ 浏览时只显示作者提供的 `preview.png` |
| **已安装的社区卡，用户点“试画”** | 需二次确认 | 默认不跑；确认后仍走 Worker，并明确提示“这是社区代码” |

原因见 §1.3：现有 `vm` 上下文不是安全边界。远程卡片的代码在“浏览”阶段一律不执行，预览图由作者在发布时本地生成、随仓库分发。这样：

- 浏览远程卡 = 看图 + 看正文 + 试触发（纯文本匹配），没有代码执行面；
- 本机作者仍然有实时试画，不影响写卡体验；
- 发布时强制要求元件卡带 `preview.png`（见 §4.6），仓库里的每张元件卡都有图可看；物理规范卡不需要。

### 4.4 AI 帮写

#### 产出结构化草稿，不让模型直接写整篇词条

让模型直接输出一整条 `worldbook` 词条（含 `id`、`content`、`code_examples`）失败率会很高：字段多、Markdown 长、代码 JSON 转义容易坏。

改为让模型只输出**卡片草稿**：

```json
{
  "title": "传送带（基础）",
  "element": "belt",
  "keys": ["传送带", "履带"],
  "when": "题面或配图里出现传送带、履带时画这一件。",
  "stateAt": "return { x: 0.5 };",
  "drawFrame": "Draw.belt([0, 0.2], [4, 0.2], { ticks: 16 });",
  "pitfalls": ["刻度数太少，看不出带在动"],
  "selfCheck": [
    "stateAt 返回的键名与 drawFrame 里读的完全一致。",
    "坐标是米，没有像素量与像素比例。"
  ]
}
```

服务端再做四件事：

1. **解析 + 容错**：容忍 Markdown 代码围栏（\`\`\`json）、前后闲话、LaTeX 反斜杠（复用 `core/distill/index.mjs` 的 `firstJsonObject` / `repairBackslashes` 思路）；
   - 代码字符串里的换行必须转义；如果模型输出了裸换行导致 JSON 坏掉，**把原文回传让它重发合法 JSON**（算一轮），不要写“宽松解析器”去猜——猜错会把代码改坏。
2. **校验**：`element` 必须是官方 id；`keys` 2–8 个字面词；代码抽出来跑 C1；
3. **修复循环**：把**具体错误**（规则号 + 行号 + 原话）回传给模型，最多 2 轮；仍不过就把草稿和错误一起还给 UI，**不保存**；
4. **组装**：用固定模板拼 `content`，保证「生成后自检」标题一定在、格式一致：

```
# 元件·<title>（<group>）

## 判据
<when>

## 状态与画法
- stateAt 里写：<...>
- drawFrame 里写：<...>

## 这条元件最常错的地方
- <pitfall>

## 生成后自检（必须逐条在代码中体现）
- [ ] <selfCheck>
```

这样模型只负责“物理 + 画法”，格式由程序保证。

#### 提示词生成，不手写

提示词由三份**单一事实来源**生成：

| 来源 | 提供什么 |
|---|---|
| `contracts/worldbook-concepts.json` | 30 个官方元件 id + 名称 + 分组 |
| `sdk/signature-summary.json` | 全部 `Draw.*` / `Phys.*` 签名与短说明 |
| `core/worldbook/data/93-elements.json` | 每个元件的 `stateAt` / `drawFrame` 最小示例（补完 stateAt 之后） |

生成物再配一条门禁：

- 必须包含**全部**官方元件 id；
- 必须**不含**表外 id（例如 `text` 不是官方元件，只能作为 SDK 原语说明，不能进 `elements` 列表）；
- 必须包含全部 SDK 函数名；
- 提示词 hash 稳定、可记录。

#### UI 与调用

- 右侧或顶部一个“让 AI 起草”面板：描述 + 可选贴一道会用到它的题；
- 进度分三段显示：“正在写（第 1 轮）”→“检查没过，按错误修（第 2 轮）”→“完成/仍失败”；
- 可取消（`AbortController`，服务端同时中止模型请求）；
- 结果以**表单字段**呈现，不是一坨 JSON；用户可改；
- 明确标注“AI 草稿，尚未保存”；
- 不自动保存、不自动发布。

模型选择：

- 不新增 `stageModels` 阶段（会动端点契约和 8 阶段枚举），默认复用 `scene_code` 端点；
- UI 给一个“用哪个模型”下拉，列出已配置端点，默认选 `scene_code`；
- 没有端点/Key 时，显示“去连接设置”，不静默退回演示。

成本：

- 提示词约 5k–8k tokens，输出约 1.5k–3k tokens；
- 一张卡通常 1 次成功，坏一点 2–3 次；
- 在 UI 上写“按你的端点计费”，不写死金额。

日志：

- 每次生成落一份 `data/card-studio/logs/<时间>-<id>.json`：提示词 hash、模型、耗时、轮次、每轮错误、最终草稿；
- 落盘前脱敏（Key / 绝对路径），与 v1.1.7 的开源日志同一口径；
- 面板上给“打开写卡日志”入口。

### 4.5 卡片仓库

#### 仓库布局（静态，零后端）

```
fatfish-cards/
├─ registry.json              # 索引清单（唯一入口）
├─ cards/
│  ├─ liuluming.belt-basic.json
│  └─ ...
├─ previews/
│  ├─ liuluming.belt-basic.png
│  └─ ...
├─ schema/registry.schema.json
├─ README.md                  # 给老师：怎么在软件里浏览/安装
├─ CONTRIBUTING.md            # 给作者：怎么投稿
├─ LICENSE                    # 卡片内容的许可（建议 CC BY 4.0）
└─ .github/workflows/validate.yml
```

- 一张卡 = 一个 `od-worldbook` 包，**恰好 1 条 entry**；
- 复用现有 `buildExportPack()` / `packToText()`，不新增卡片文件格式；
- 预览图是 PNG（不接受 SVG，避免脚本/外链风险），建议 480×360，≤200KB；
- `registry.json` 是唯一索引，应用只认它，不扫目录。

#### registry.json 形状

```json
{
  "format": "od-card-registry",
  "version": 1,
  "updatedAt": "2026-10-19T12:00:00Z",
  "cards": [
    {
      "id": "liuluming.belt-basic",
      "title": "传送带（基础）",
      "summary": "水平传送带 + 表面刻度，适合传送带模型。",
      "author": "liuluming",
      "version": "1.0.0",
      "minAppVersion": "1.2.0",
      "schemaVersion": 1,
      "category": "scene_modeling",
      "slots": ["scene_code"],
      "elements": ["belt"],
      "concepts": [],
      "tags": [],
      "keywords": ["传送带", "履带"],
      "file": "cards/liuluming.belt-basic.json",
      "sha256": "…",
      "bytes": 5321,
      "preview": "previews/liuluming.belt-basic.png",
      "previewSha256": "…",
      "license": "CC-BY-4.0",
      "reviewed": true,
      "createdAt": "…",
      "updatedAt": "…"
    }
  ],
  "revoked": [{ "id": "someone.bad-card", "reason": "教错受力方向", "at": "…" }]
}
```

字段理由：

- `file` 是**相对路径**，镜像可以整体换 base；绝对 URL 一律拒绝（防 SSRF / 防清单被篡改后指向别处）；
- `sha256` 保证下载内容与清单一致；哈希不符不缓存、不安装；
- `minAppVersion` 防止新卡用了旧版没有的 SDK 函数；
- `schemaVersion` 防止词条 schema 变更后的不兼容；
- `reviewed` 是人工审核标记，应用显示“官方审核 / 社区未审核”徽章；
- `revoked` 让维护者能下架有问题的卡，应用拒绝新装并提示已安装用户。

#### 多源与缓存

应用配置一组 base URL，按顺序尝试：

```json
{
  "sources": [
    { "name": "jsDelivr", "baseUrl": "https://cdn.jsdelivr.net/gh/<owner>/<repo>@main", "kind": "jsdelivr" },
    { "name": "GitHub raw", "baseUrl": "https://raw.githubusercontent.com/<owner>/<repo>/main", "kind": "github" },
    { "name": "Gitee 镜像", "baseUrl": "https://gitee.com/<owner>/<repo>/raw/main", "kind": "gitee" }
  ]
}
```

- 默认顺序建议 **jsDelivr → GitHub raw → Gitee**；jsDelivr 在国内通常比 raw 稳，但有缓存延迟；
- 每个源 5s 连接 / 15s 总超时；失败自动下一个；
- 清单缓存 10 分钟；卡片文件按 `sha256` 永久缓存；预览图按 `sha256` 永久缓存；
- 断网时显示“当前是 2026-10-19 12:00 的缓存”，并提供“重试 / 换源”；
- 手动刷新加 cache-busting 查询参数（jsDelivr 缓存较顽固）；
- 网络层用**可注入的 fetch**：Electron 里用 `net.fetch`（走系统代理），Node 测试里用全局 `fetch`。否则老师机器上的代理设置对应用无效。

#### 安装 / 更新 / 冲突

安装前：

1. 校验清单字段、id、大小、`minAppVersion`、`schemaVersion`；
2. 下载卡片文件，校验 `sha256` / `bytes`；
3. 解析为 `od-worldbook` 包，必须恰好 1 条，`validateEntry` 通过；
4. **强制策略**：`origin: 'user'`、`constant: false`、`priority: 'normal'`、`order >= 1000`、id 不以 `wb_` 开头、不得与内置 id 冲突；
5. C1 静态检查示例代码（不执行）；
6. 写入前备份同 id/同文件旧版本。

冲突处理：

| 情况 | 行为 |
|---|---|
| 没装过 | 直接装，写 `<id>.json` + 侧车记录 |
| 同 id、同 `sha256` | 显示“已安装”，不重复写 |
| 同 id、不同版本、本地未改 | 提示“有更新”，确认后备份 + 覆盖 |
| 同 id、本地已改（`entryHash` 变了） | 默认**不覆盖**，提供“另存为新卡 / 强制覆盖（先备份）” |
| id 与内置冲突 | 拒绝，提示换 id（不允许社区卡覆盖内置） |

侧车文件 `data/card-studio/installed.json`：

```json
{
  "format": "od-card-installed",
  "version": 1,
  "cards": {
    "liuluming.belt-basic": {
      "version": "1.0.0",
      "sha256": "…",
      "file": "liuluming.belt-basic.json",
      "source": "https://cdn.jsdelivr.net/gh/liuluming/fatfish-cards@main",
      "installedAt": "…",
      "entryHash": "…",
      "reviewed": true
    }
  }
}
```

- `entryHash` 用 `worldbookHashOf([entry])` 或 `canonicalJson(canonicalizeEntry(entry))` 的哈希；
- 用户编辑后 `entryHash` 变化 → UI 标记“本地已修改”；
- 卸载：删侧车记录 + 删/改对应包文件（多卡包只删那一条），先备份。

#### 安全策略（远程内容）

| 风险 | 策略 |
|---|---|
| 超大文件 / DoS | 清单 ≤1MB、卡片 ≤128KB、预览图 ≤200KB、单卡 content ≤20k 字符、示例 ≤10k 字符 |
| 路径穿越 | `file` 必须是相对路径，不含 `..`、不以 `/` 开头、不含 `?` / `#`；解析后必须仍在 base 路径下 |
| 哈希不符 | 拒绝缓存、拒绝安装，点名“期望/实际” |
| 未知版本 | `format` / `version` / `schemaVersion` 不认识就拒绝，提示“请升级软件” |
| 恶意代码 | 浏览不执行；安装只做 C1 静态检查；本机试画需用户确认；`Draw.raw` 对社区卡直接拒绝 |
| 提示词注入 | 未审核徽章 + 首次安装确认 + 应用内可一键停用/删除；门禁仍兜住代码层 |
| 预览图伪造 | 标注“作者提供的预览图”；审核卡由维护者核对；撤销名单 |
| 撤销卡 | 清单 `revoked`；已安装的显示警告并建议停用 |

### 4.6 发布

#### 发布前检查（比保存更严）

- 类型必须是元件卡 / 物理规范；
- id 必须是 `<author>.<slug>`，作者标识已配置；
- `constant: false`、`origin: user`；
- 有「生成后自检」小节；
- `stateAt` + `drawFrame` 能通过 C1 + Dry-Run；
- 画法命令数 > 0；
- 不含 `Draw.raw`；
- 内容/示例长度在上限内；
- 有 `license`、`summary`；
- 能生成预览图（元件卡）；
- 不含 Key、绝对路径、内网地址。

#### 投稿包（无 token，推荐先做这个）

点“发布”后，在 `文档\物理解题动画\卡片投稿\<id>\` 生成：

```
card.json               # od-worldbook 包，1 条 entry
manifest-entry.json     # 可直接粘进 registry.json 的条目
preview.png             # 元件卡必须；物理规范不需要
README.txt              # 三步投稿说明
```

UI 提供：

- “打开文件夹”
- “复制 card.json”
- “复制 manifest 条目”
- “打开 GitHub 新建文件”（`https://github.com/<owner>/<repo>/new/main?filename=cards/<id>.json`）
- “打开投稿说明”

这条路不需要在软件里存 GitHub Token，也不需要 OAuth；对老师最安全。缺点是最后一步要手工粘贴/提 PR。

不会用 GitHub 的老师：把整个投稿文件夹发给维护者（QQ / 邮件 / 群里），由维护者合并即可。软件不需要为此做账号体系；`README.txt` 里写清“把文件夹发给谁”。

#### 可选：直接建 PR（建议 v1.2.1 之后）

如果一定要“在软件内发布”，两条路：

| 方案 | 工作量 | 风险 |
|---|---:|---|
| **GitHub Device Flow OAuth** | +4–6 人日 | 要注册 OAuth App；国内网络要能通 github.com；Token 要用 `safeStorage` 加密存本机 |
| **用户填 fine-grained PAT** | +2–3 人日 | 体验差、Token 泄露风险高；只建议作为高级选项 |

直发的流程：设备码 → 用户浏览器授权 → 取 Token（加密存）→ 取登录用户 → 必要时 fork → 建分支 → PUT 文件 → 建 PR。要处理 409 冲突、速率限制、Token 失效、撤销入口。

**建议**：v1.2 先做投稿包；直发等仓库跑起来、确实有人抱怨“粘贴太麻烦”再加。

### 4.7 仓库模板与 CI

- `schema/registry.schema.json`：清单字段、id 正则、必填项、`additionalProperties: false`；
- `.github/workflows/validate.yml`：
  - checkout 卡片仓库；
  - checkout 主仓库到固定 tag（或下载 release 里的 `cards-lint`）；
  - 跑 `node tools/cards-lint.mjs registry.json cards/`；
  - 校验：schema、id 唯一、文件存在、sha256/bytes 一致、预览图 PNG 魔数/尺寸、`elements` 在官方表内、C1 示例、`minAppVersion`；
- PR 模板：一张卡、一个元件、自检、预览图、许可证、物理正确性声明；
- CI 可以用 `github.event.pull_request.user.login` 校验 id 前缀是否匹配作者（防冒名）；
- `tools/cards-lint.mjs` 放主仓库，卡片仓库 CI 复用同一份，避免两套校验漂移。

### 6.3 为什么不是“两周”

两周能做出的东西：一个能调模型、把返回 JSON 塞进 `ai-rules/worldbook/` 的页面。它会缺：

- 发布版真实落盘（现在没有）；
- 试画（卡片是提示词，不是组件）；
- 远程内容的信任分层（现有 vm 不是安全边界）；
- 缓存/多源（国内网络）；
- 冲突/回滚/本地修改保护；
- 门禁与发布构建验证。

这些不是“polish”，是“能不能给老师用”的分界线。

## 7. 验收与门禁

### 7.1 新增门禁（建议 5 套）

| 门禁 | 盯什么 |
|---|---|
| **卡片工作室** | 字段/ID/自检/大小策略；单卡保存/多卡包保留；备份；复制内置不改 id；删除恢复 |
| **卡片试画** | 30 张内置卡全部有 `stateAt` + `drawFrame` 且能画出命令；合成槽位正确；帧记录可 JSON 序列化；坏代码给诊断不崩；超时/内存可区分 |
| **AI 帮写** | 提示词含全部官方元件 id、不含表外 id、含全部 SDK 函数；假端点返回坏 JSON 能修复；2 轮上限；失败不落盘；日志脱敏 |
| **卡片仓库** | 清单版本/重复 id/路径穿越/哈希不符/超大/未知元件/`minAppVersion`/撤销；多源回退；缓存离线；安装/更新/冲突/本地修改/卸载 |
| **发布** | 发布检查；投稿包文件齐全；manifest 条目与卡一致；无 Key/绝对路径；预览 PNG 合法 |

### 7.2 要改的现有门禁

- `tests/release-switch-selftest.mjs:115-120`：现在断言“发布版写卡助手是 disabled 占位”。v1.2 必须改成“发布版有 CardStudioPage、导航可点”；否则新页面会被这条旧断言挡住。
- `tests/electron-shell-selftest.mjs`：新增数据目录/菜单项；确认发布版仍能起服务。
- `tools/verify-all.mjs`：挂载新门禁；`tools/verify-coverage.mjs` 的“所有检查脚本都被挂载”会强制你接上。
- 内置卡 hash / 内容相关断言：补 `stateAt` 并重生成 `93-elements.json` 后，`worldbookHash`、覆盖率、逐字节断言会变，要一起更新。

### 7.3 验收场景（用户视角）

1. **手动**：发布版新建一张“传送带”卡 → 填字段 → 点“检查”1 秒内出结果 → 试画出现传送带 → 保存 → 重启软件还在 → 贴一道传送带题，“试触发”显示命中。
2. **AI**：输入“一个圆润的质点小球，半径 0.1 m，亮黄色，带高光” → 生成草稿；第一版若用了 `Draw.ball` 或缺 `mag`，自动回传错误并修好；用户点“采用”后试画可见；不点保存，`ai-rules/worldbook/` 不落盘。
3. **仓库**：配置测试仓库 → 列表出现卡片 → 详情看到作者预览图 → 安装 → “我的卡片”出现 → 断网仍能从缓存打开 → 哈希改一位，安装被拒并说明原因。
4. **发布**：对本地卡点“发布” → 生成投稿文件夹 → 复制 manifest 条目 → 打开 GitHub 新建文件页；文件夹里没有 Key/绝对路径。
5. **门禁**：`node tools/verify-all.mjs` 全绿；`OD_RELEASE=1` 构建产物有写卡助手、没有规则页；打包后 `--selftest` 通过。

## 8. 风险清单

| 风险 | 影响 | 缓解 |
|---|---|---|
| **现有 vm 不是安全边界** | 远程卡代码若执行，可能逃逸 | 浏览远程卡不执行代码；远程预览用作者 PNG；本机卡才跑 Dry-Run；社区卡试画需确认 |
| **提示词注入** | 恶意卡诱导模型产出坏代码/教错物理 | 未审核徽章、首次确认、可停用/删除、Dry-Run 兜代码层、撤销名单 |
| **国内网络** | 清单/卡片拉不到 | 多源 + 缓存 + 可配置 base + 手动刷新 + 清晰的离线态 |
| **模型输出不稳定** | AI 起草反复失败 | 结构化字段 + 少样本 + 2 轮修复 + 失败保留草稿 + 可手动改 |
| **内置卡重生成** | hash/覆盖率/逐字节断言红 | 一次性改生成器 + 重生成 + 更新门禁；不要手改产物 |
| **范围膨胀** | 复合卡/社区/广告/直发把版本拖垮 | 本文 §2.2 的“不做”清单写进版本说明 |
| **发布版旧口径** | 用户以为能存，其实存不了 | P0 先补；设置页改成“去写卡助手”或只读 |
| **仓库审核** | 卡片质量参差 | PR 模板 + CI + `reviewed` 徽章 + 撤销名单；不要承诺“所有卡都审核” |

## 9. 需要你拍板的事

1. **版本节奏**：  
   - A（推荐）：一个 v1.2，但按 M1/M2/M3 三个里程碑验收；  
   - B：拆成 v1.2.0（写卡+预览）/ v1.2.1（AI）/ v1.2.2（仓库），每版可独立发布。

2. **发布方式**：  
   - A（推荐）：投稿包 + 手工 GitHub PR，不存 Token；  
   - B：内置 GitHub Device Flow 直发（+4–6 人日，需要 OAuth App，国内网络可能不通）；  
   - C：用户填 PAT（+2–3 人日，安全风险高，不推荐）。

3. **卡片范围**：  
   - A（推荐）：v1.2 只做**元件卡**（`scene_code`），物理规范继续手动/设置页；  
   - B：同时做物理规范 + 元件卡（AI 提示词要分两套，+2–3 人日）。

4. **复合卡**：  
   - A（推荐）：v1.2 不做；一张卡一个元件；  
   - B：要做，需要先改命中规则（`elements` 全部命中 or 新增 `components`）+ 新预览策略，+5–8 人日，且会碰现有 30 张卡。

5. **许可证**：卡片内容用 **CC BY 4.0**（署名）还是 **CC BY-SA 4.0**（署名 + 相同方式共享）？这会影响仓库 `LICENSE` 和投稿模板。

6. **仓库地址**：GitHub owner/repo 定了吗？如果还没定，应用先做成“未配置仓库”的空态；定下来后只需填配置，不用改代码。

7. **ROADMAP 里 v1.2 还挂着的“半开源”和“反馈重绘”**：  
   - 建议移到 v1.3；本次只做写卡 + 仓库，否则这个版本会失控（反馈重绘要动 `scene_code` 重入和槽位保留，另算 5–8 人日）。

## 10. 与 Gemini 方案的取舍（明确回应）

| Gemini 的点 | 采纳 | 说明 |
|---|---|---|
| GitHub/Gitee 当静态卡片库，`manifest.json` 索引 | ✅ | 但字段要更严：哈希、大小、版本、相对路径、撤销 |
| 应用内浏览 + 一键安装 | ✅ | 安装前要校验、备份、冲突处理；不静默覆盖 |
| 自然语言让 AI 写组件 | ✅ | 但卡片是词条，不是任意 JS 组件；要结构化输出 + 校验闭环 |
| 右侧小画布实时预览 | ✅（仅本机卡） | 远程卡不执行代码；远程预览用作者 PNG |
| 内嵌浏览器打开社区 + 广告 | ❌ | 远程 UI/登录/Cookie/隐私/广告合规；本期不做 |
| 复合构件（Composite） | ❌（v1.2） | 现有命中规则会误命中；一张卡一个元件 |

| “老师满意就点保存进本地卡库” | ✅ | 但必须人工确认；AI 不自动保存 |
| “0 元成本” | ✅ | 静态仓库 + jsDelivr/Gitee 镜像，确实零后端；但国内网络要有多源和缓存 |

## 1. 提示词审计

### 1.1 提示词是怎么拼的（非程序员版）

模型每次看到的不是“一段话”，而是三层：

```text
① 固定前缀（system 的开头）
   角色 + 输出纪律 + （只有动画/修复阶段）SDK 签名摘要
   —— 每道题都一样，用来命中缓存、省钱

② 条件段（system 的后半）
   本题命中的知识卡 + 本阶段指令
   —— 命中什么卡，就注入什么卡；本阶段指令是“这一步要做什么”

③ 任务段（user）
   题面 + 图片 + 已知条件 / 分析表 / 讲解步骤
   —— 每道题不同
```

对应到代码：

- 固定前缀：[fixed-prefix.mjs](../../core/prompts/fixed-prefix.mjs)、[templates.mjs](../../core/prompts/templates.mjs)
- 阶段指令：[analysis.mjs](../../core/prompts/analysis.mjs)、[couple.mjs](../../core/prompts/couple.mjs)、[scene-code.mjs](../../core/prompts/scene-code.mjs)、[repair.mjs](../../core/prompts/repair.mjs)
- SDK：[signature-summary.md](../../sdk/signature-summary.md)
- 拼装：[fixed-prefix.mjs](../../core/prompts/fixed-prefix.mjs) 的 `assemblePrompt()`

**结论：分层是干净的。** 固定前缀不含题目信息；SDK 只给“要写代码”的两个阶段；图片只在 user；system/user 分工正确。

### 1.2 八个阶段一张表

| 阶段 | system 负责 | user 给什么 | 有 SDK？ | 当前主要问题 |
|---|---|---|---|---|
| `read_problem_v2`（读题） | 标题、几何、裁图范围、动画元件、场景、判定依据 | 题面文字 + 图片 + 两张词表 | 否 | **词表外实体没有抽象规则**（q05 救护车） |
| `solve`（解题） | 解题角色 + 6 条解题规范；带参考答案时换成“按解析整理” | 题面 + 参考答案/解析 + 补充条件 | 否 | 基本一致；规范条数注释写错（6 vs 5） |
| `breakdown`（分步） | 把解题过程讲成几步，一步一段物理过程 | 题面 + 解题过程 | 否 | 基本一致 |
| `analysis`（物理分析） | 只写分段运动表 x(t)/y(t)，不写答案/不画图 | 题面 + 读题几何 + 解题过程 | 否 | **连续性规则与 branch 例外读起来像打架** |
| `couple`（步骤耦合） | 把讲解步骤对齐到物理时间轴，标 `sub` | 分析表 + 讲解步骤 + T_phys | 否 | **`T_BRANCH` 未定义；最后一句漏 `sub`** |
| `scene_code`（动画代码） | 只写 drawFrame；世界坐标、不写字、不画 v/a | 分析表 + state 映射 + 读题几何 + 步骤时间 | **是** | **地面示例写死 y=0；轨迹没有硬要求** |
| `repair`（自愈） | 只修 drawFrame，不碰物理 | 上一轮 drawFrame + 失败项 + 读题几何 | **是** | **地面示例同样写死 y=0；没有 branch 规则** |
| `read_problem`（v1 读题） | 旧版，仍保留在扩展提示词/测试里 | 题面 + 图片 | 否 | 已退役；不影响主链路，但审计时要说明 |

> `read_problem` v1 已退役；主链路用 `read_problem_v2`。旧版保留是为了旧测试/旧包，不在本次“必须改”范围。
>
> 设置页允许用户覆盖某个阶段的 **system 正文**；覆盖只影响“条件段”，不改固定前缀、不改 `promptHash`。本清单审计的是**内置默认值**；如果你自己覆盖过，以你覆盖后的文本为准。

### 1.3 提示词问题清单

#### P-01 🔴 读题没有“词表外实体怎么办”

**证据**：[templates.mjs](../../core/prompts/templates.mjs) 的 `read_problem_v2` 只写：

> 【动画元件】只能从词表里逐字取 id；判不出写“无”。不要自造、不要改写。

**实际后果**：q05 的救护车不在词表里，模型如实写了 `【动画元件】无`；画图模型只能自己把它画成一个方块。你后来裁决“单方块即可”，但这是**运气**，不是提示词的保证。

**建议**（不补词表别名）：

> 如果运动主体是“车辆 / 人 / 动物 / 机器”等词表没有的实体，按它的**运动方式**抽象成最接近的 `block`（平移）或 `ball`（转动/抛体），并在【判定依据】里说明“词表无此实体，按运动抽象”。不要写“无”。

这条属于**读题提示词工程**，不是补词表别名；你之前说的“过度工程”仍然不做。

#### P-02 🔴 `couple` 最后一句漏了 `sub`

**证据**：[couple.mjs](../../core/prompts/couple.mjs) 第 84 行：

> 只输出 step / t0 / t1 的行式表。

但上面的规则和示例都要求 `sub`（第几小问）。模型最后看到“只输出 step/t0/t1”，可能把 `sub` 省掉，导致步骤没有小问归属。

**建议**：改成“只输出 step / sub / t0 / t1 的行式表”。这是一行字，风险很低。

#### P-03 🔴 `scene_code` / `repair` 的地面示例与规则打架

**证据**：

- [scene-code.mjs](../../core/prompts/scene-code.mjs) 规则 5 说“地面/支撑面画在运动元件附近……不要硬贴 y=0”；
- 同一个文件的示例却是 `Draw.ground(-2, 8, 0);`；
- [repair.mjs](../../core/prompts/repair.mjs) 的示例也是 `Draw.ground(-2, 8, 0);`。

**实际后果**：q05 的地面就是 y=0；q08 的电路/地面也容易被画到 y=0。模型会优先照抄示例，而不是读规则。

**建议**：示例改成：

```js
Draw.ground(-2, 8, state.block_A.y - 0.3);
```

或明确写“y 按题图/按物块位置，不要默认 0”。`Draw.ground` 的 y 参数本身是可选的，默认 0 是 SDK 的便利，不是题目的物理。

#### P-04 🟡 `couple` 的 `T_BRANCH` 不是真实符号

**证据**：[couple.mjs](../../core/prompts/couple.mjs) 第 37 行：

> 分支前的主过程步骤到 `T_BRANCH` 为止；分支后的步骤从 `T_BRANCH` 开始。

实际 `setup` 生成的是 `T_BRANCH_1` / `T_BRANCH_2`…，而 `couple` 阶段模型看到的是 analysis 表，不是 setup。它不知道 `T_BRANCH` 是什么。q08 A 重跑碰巧把 step3/step4 时间写对了，但这是运气，不是契约。

**建议**：改成“到分支段的 `t0`（analysis 表中 `branch: true` 那一段的 `t0`）为止”。  
**你的裁决**：记录在案，**1.1.19 后期 prompt / 卡面工程再改**，不为 q08 单独重跑。

#### P-05 🟡 `analysis` 的连续性规则与 branch 例外读起来像打架

**证据**：[analysis.mjs](../../core/prompts/analysis.mjs)：

- 规则 3：“同一元件相邻两段在交界时刻位置必须相等；速度也必须连续。”
- 规则 6.5：“分支段的位置允许与上一段末位置不同（从 c 回到 b）。”

两条都对，但规则 3 没有写“branch 除外”，模型可能先按规则 3 把 c 和 b 硬接起来，结果又回到 q08 的老问题。

**建议**：规则 3 末尾加一句“（`branch: true` 的分支段除外，见 6.5）”。

#### P-06 🟡 `repair` 没有 branch 规则

**证据**：`repair` 只修 drawFrame，不碰 stateAt/VIEW；但如果 branch 题的 drawFrame 失败，模型不知道 `T_BRANCH_n`，可能把两段轨迹连成一条，或只画一个粒子。

**建议**：在 repair 的规则里加一句：

> 如果分析表有 `branch: true`，`setup` 会提供 `T_BRANCH_n`；修复时保持分段轨迹，不要把两段连起来。

q08 没有触发 repair；这条是给以后的条件变更题兜底。

#### P-07 🟡 `scene_code` 没有硬性要求画轨迹

**证据**：[scene-code.mjs](../../core/prompts/scene-code.mjs) 规则 8 说“分支前只画主过程轨迹，分支后只画当前分支轨迹”，但**没有说用 `Draw.trace`**。q08 的 drawFrame 没有画轨迹虚线；你明确“忽略”，所以 q08 不受影响。但 q07 的粒子轨迹会用到 `trace_path` 卡，这条会变成实际需求。

**建议**：如果要画轨迹，明确写“用 `Draw.trace(pts)` 画已走过的轨迹，只画到当前 t”；如果暂时不要求，就写“轨迹可选”。  
**你的裁决**：q08 的轨迹/箭头忽略；这条可以作为 q07 之前的待定项。

#### P-08 🟡 “场景卡最多 1 张”与代码/提示词不一致

**证据**：

- [templates.mjs](../../core/prompts/templates.mjs) 的 `read_problem_v2` 说【场景】可多选；
- [项目现状与路线.md](../../项目现状与路线.md) 第 139 行写“最多 1 个”；
- 代码实际不限制；q04 同时命中 3 张场景卡（传送带、滑轮、坐标轴框），已验收。

**建议**：把文档改成“一题可命中 1–3 张场景卡”；不要为了“最多 1”去改代码，否则 q04 的 axis_box 可能被丢掉。

#### P-09 🟡 `couple` 的“纯概念步骤可以不写”与 branch 规则

**证据**：[couple.mjs](../../core/prompts/couple.mjs)：

- 规则 3：“纯概念步骤可以不写（不写 = 点它不跳动画）。”
- 规则 7：“条件变更 / 另一情形的步骤必须写时间。”

规则 7 是更具体的例外，但两条挨着，模型可能把 q08 第 3 问当“纯概念步骤”省掉（这正是 q08 最初的事故）。

**建议**：规则 3 加一句“条件变更的步骤除外，见规则 7”。

#### P-10 🟢 固定前缀里的“死代码”与注释

**证据**：

- [templates.mjs](../../core/prompts/templates.mjs) 的 `ROLE_AND_OUTPUT_RULES` 被 `fixed-prefix.mjs` import 了，但实际 `partsFor()` 用的是 `STAGE_ROLES`，没有用它；
- `buildTemplateSkeleton()` 仍导出，但 `partsFor()` 现在把 `skeleton` 设为空串。

**影响**：不影响模型输出，也不影响 `promptHash`；只是注释说“它是固定前缀的一部分”，与实际不符。  
**建议**：要么删掉/合并，要么在注释里写“历史保留，已不参与前缀”。属于代码卫生，不是物理问题。

#### P-11 🟢 `solve` / `breakdown` / `analysis` 的主体口径是清楚的

- `solve` 带参考答案时切换 system，避免“既复述又重算”；
- `breakdown` 一步一段物理过程，覆盖全题；
- `analysis` 的数值权威顺序（参考答案 > 解题过程 > 题图）、质心口径、表达式白名单都写清了。

这三段没有发现必须改的硬伤；只有 `SOLVE_RULES` 注释写“6 条”但实际 5 条，属于文字小错。

#### P-12 🟢 SDK 注入范围正确

- 只有 `scene_code` / `repair` 收 SDK 签名摘要；读题/解题/分步/分析/耦合都不收；
- 实测省掉约 37% 的无效前缀字数；
- SDK 签名摘要与导出面由门禁 ② 钉住。

**唯一要配合修的是**：`Draw.ground` 示例 y=0（P-03）和 `Draw.trace` 没有硬要求（P-07）；SDK 本身没有问题。

### 2.2 五张红卡（必须改）

#### B-08 `wb_el_trace_path`（轨迹）

**它会误导什么**：正文要求“用 `context.at(tt)` 采样历史，只画到当前 t”，示例却是：

```js
Draw.trace([[0, 0], [state.trace_path_A.x, state.trace_path_A.y]]);
```

- 没有 `context.at`，轨迹只会是“起点 + 当前点”的一条直线；
- `trace_path_A` 很可能不存在（轨迹是跟随件，没有独立 state），直接报错。

**建议**：示例改成真正的采样：

```js
const pts = [];
for (let tt = 0; tt <= t; tt += 0.02) {
  const s = context.at(tt);
  pts.push([s.ball_A.x, s.ball_A.y]);   // ball_A 换成真实运动元件 key
}
Draw.trace(pts);
```

**为什么现在要改**：q07 是方波电场/磁场的粒子轨迹，正需要这张卡；q08 你没有要求轨迹，但 q07 会踩。

#### C-05 `wb_sc_belt`（传送带）

**它会误导什么**：卡里一边说“带面顶的 y 尽量接近物块 `state.<key>.y`”，一边在自检里写“没有读 `state`”。要贴合物块就必须读，两条只能二选一；模型可能把带子画在 y=0，或者乱读一个不存在的 key。

**建议**：改成：

> 允许读 `state.<key>.y` 来对齐带面；带子本身不随时间移动，只有 `tickPhase` 动。

#### C-06 `wb_sc_wire`（导线/电路）

**它会误导什么**：卡说“导线、电源、开关、电阻、变阻器都画在这里”，但示例只有一个矩形导线 + 一个电流箭头；没有电池、开关、电阻、变阻器的符号。q06 的“电路没画对”和 q08 的电路示意图都与此有关。

**建议**：用现有图元补四个小示例（不新增 SDK）：

- 电池：两条竖线，一长一短；
- 开关：一段斜线 + 缺口（闭合时补上斜线）；
- 电阻：`Draw.curve` 画锯齿，或小矩形；
- 滑动变阻器：电阻 + 箭头；
- 电容：两条平行短线。

这是**画法卡**问题，不是提示词能单独救的；q06 的电路改正可以并到这里一起做。

#### C-15 `wb_sc_celestial_orbit`（天体轨道）

**它会误导什么**：卡说“中心天体在焦点”，示例 `Draw.ellipse([0, 0], 1.2, 0.8)` 把椭圆中心放在 (0,0)；如果中心天体也画在 (0,0)，它就在椭圆中心，不是焦点。

**建议**：示例改成“椭圆中心沿长轴偏移 `c = sqrt(a² - b²)`，中心天体放焦点”，并明确“不要把中心天体放在椭圆中心”。

#### C-17 `wb_sc_gas_tube`（玻璃管/U 形管）

**它会误导什么**：卡里说“水银柱由 `mercury` 元件卡画”，但 `mercury` 卡和词表都已封存；遇到 U 形管/液柱题，场景卡会注入、水银柱卡不会，模型没有画液柱的依据。

**建议**：三选一：

1. 卡顶写明“本卡只画管壁；液柱暂不支持”；
2. 同时封存 `gas_tube`，直到 `mercury` 解封；
3. 给一个“用 `Draw.polygon` 画液柱示意”的替代写法。

q03 本期是 placeholder；但卡的口径要先一致。

### 2.3 十六张黄卡（建议改，可一次批改）

#### 2.3.1 “由场景给”旧口径（6 张）

涉及：`wb_sc_incline`（C-01）、`wb_sc_pulley`（C-04）、`wb_sc_meter`（C-07）、`wb_sc_electric_field`（C-09）、`wb_sc_magnetic_field`（C-10）、`wb_sc_gas_tube`（C-17）。

它们都写了类似“顶点/位置/场区范围/管口开闭由场景给”。**场景卡不会给具体数值**；数值只能来自题面/题图。建议统一改成“按题面/题图给”。  
（`wb_sc_wire`（C-06）也有“接线柱位置由场景给”，但它是红卡，已在 2.2 单独处理。）

#### 2.3.2 连接件示例用了不存在的 state key（3 张）

涉及：`wb_el_spring`（B-04）、`wb_el_rope`（B-05）、`wb_el_light_rod`（B-07）。

它们示例写 `state.spring_A` / `state.rope_A` / `state.light_rod_A`，但弹簧/绳/杆是连接件，可能没有独立 state；q04 的绳两端是滑轮/物块，照抄会 `undefined`。  
建议：示例改成从两个真实端点取，或明确写“`xxx_A` 只是占位，换成实际 key”。

#### 2.3.3 固定数值/比例示例（2 张）

- `wb_el_conductor_rod`（B-06）：示例半长写死 0.5 m；导轨间距 0.4 m 时棒会伸出去。建议注明“0.5 是示意，按导轨间距改半长”。
- `wb_sc_cylinder`（C-16）：示例 `Draw.box` 画封闭矩形；气缸通常一端开口。建议用三条线（左壁、底、右壁），或说明“封闭矩形只是示意”；卡销用一个小方块/短线示意。

#### 2.3.4 措辞把正确做法写成“最常错”（2 张）

- `wb_el_piston`（B-10）：“最常错”下面写“活塞与气缸使用一套坐标；活塞厚度可以自由裁量”——这两句是正确做法，不是错误。建议改成“不要各画一套坐标；厚度不要写死到看不见”。
- `wb_anim_conventions`（A-01）：
  - “静止基准只画一次，不要逐帧换位置”容易被理解成“只画第一帧”；drawFrame 每帧都执行，建议改成“静止基准每帧照画，但坐标不要随帧变”；
  - “可以读 `context.at(t)`，不要写 `context`”两句放在一起像自相矛盾；建议改成“不要写 `context` 槽位；可以读 `context.at(t)` 采样历史”。

#### 2.3.5 其余黄卡（4 张）

- `wb_sc_axis_box`（C-14）：“量程盖不住数据”是真实风险；模型只画轴框，数据曲线由 `Draw.chart` 画，框和 chart 的量程不一致就会跑出框。建议在卡里写“`xLen/yLen` 要包住 `Draw.chart` 的数据范围”。
- `wb_sc_ground`（C-02）：示例 `Draw.ground(-1.5, 2.5)` 用默认 y=0；平抛/悬挂题里地面可能离物体很远。建议示例写成按物块/题图给 y，并补一句“墙面用 `Draw.line`/`Draw.polygon` 加阴影，不归 `Draw.ground`”。
- `wb_el_board`（B-02）：“没有速度时由场景卡给静态角”不准确；场景卡不给角度，建议改成“没有角度就不写 `angleDeg`”。
- `wb_sc_lens`（C-12）：标题含玻璃砖/三棱镜，示例只有 `Draw.lens`；玻璃砖是矩形、三棱镜是三角形，应该用 `Draw.polygon`。建议补两个示例，或把标题缩成“透镜”。
